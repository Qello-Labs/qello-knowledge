# PR 본문 작성 규칙

리뷰어가 diff를 열기 전에 무엇이 왜 바뀌었고 어떻게 검증했는지 1분 안에 알 수 있게 쓴다.
짧게 쓰고, 표로 정리하고, 사람이 쓴 글처럼 쓴다.

## 1. 빼는 것

| 빼는 것 | 예 |
| --- | --- |
| 도입·요약·맺음말 | 이번 PR에서는, 정리하면, 결론적으로, 리뷰 부탁드립니다, 감사합니다 |
| 표나 목록을 소개하는 문장 | 아래 표는 변경 내용을 정리한 것입니다 |
| diff와 커밋에 이미 있는 내용 | 파일별 줄 수, 커밋 메시지를 그대로 옮긴 목록 |
| 같은 내용의 반복 | 변경 내용과 위험에 같은 문장, 두 표에 같은 명령 |
| 해당 없는 항목의 설명 | `해당 없음`만 쓴다. 사유가 꼭 필요하면 한 구절로 |
| 긴 배경 설명 | Issue나 결정 기록 링크로 대신한다 |
| 이모지 | 전부. Claude Code가 마지막 줄에 붙이는 생성 표시만 예외 |

## 2. AI 말투 대신 사람 말투

표 안은 개조식(`~ 추가`, `~ 변경`)으로 쓰고, 표 밖 문장은 합쇼체로 한두 문장만 쓴다.
템플릿의 체크박스 문장은 바꾸지 않는다.

| 쓰지 않는다 | 대신 |
| --- | --- |
| ~를 통해 ~를 확보·강화·보장·도모했습니다 | 한 일을 동사로: 추가, 변경, 제거, 수정 |
| 효율적으로, 체계적으로, 원활하게, 안정적으로, 명확하게, 일관되게 | 빼거나 숫자로 쓴다 |
| 다양한, 핵심적인, 강력한, 완벽한, 손쉽게, 깔끔하게, 대폭, 크게 | 뺀다 |
| 제공합니다, 가능하도록 합니다, 역할을 합니다, ~하게 됩니다 | 한 일만 쓴다 |
| 이를 통해, 또한, 뿐만 아니라, 즉, ~라는 점에서 | 문장을 나누거나 뺀다 |
| ~에 대해서, ~에 있어서, ~을 진행하였습니다, 되어집니다 | ~를, ~에서, ~했습니다, ~됩니다 |
| 줄표(—), 괄호, 콜론으로 덧붙이는 설명 | 필요하면 문장을 나눈다 |
| 개수를 맞춘 세 항목 나열 | 있는 만큼만 쓴다 |
| 제가, 저는, 아쉽게도, 다행히 | 주어 없이 사실만 쓴다 |

| AI 말투 | 사람 말투 |
| --- | --- |
| 비밀값 검사 스크립트를 통해 저장소의 보안성을 강화했습니다. | secret scan 스크립트 추가 |
| 이를 통해 명세 ID와 ClickUp 작업을 일관되게 연결할 수 있게 되었습니다. | Issue 폼에서 명세 ID를 dropdown으로 선택 |
| 검증 결과 모든 테스트가 성공적으로 통과되었음을 확인했습니다. | `pytest` 통과(42 passed) |

## 3. 기술 용어는 영어로

억지로 옮긴 한국어 대신 개발자가 실제로 쓰는 영어 용어를 쓴다. 조사는 붙여도 된다(`hook이`, `CI가`).
코드 식별자, 경로, 명령, 설정 키는 `코드`로 감싼다. 커밋, 브랜치, 리뷰처럼 굳어진 음차는 그대로 쓴다.

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| 비밀값 검사 | secret scan |
| 사전 점검 | preflight |
| 원자적 교체 | atomic swap |
| 증분 동기화 | incremental sync |
| 멱등 | idempotent |
| 재색인 | reindex |
| 질의 | query |
| 임베딩 제공자 | embedding provider |
| 모의 입력, 가짜 입력 | mock input, fixture |
| 해시 대조 | hash 비교 |
| 기본 브랜치 | default branch |
| 병합, 되돌리기 | merge, revert |
| 쌓은 PR | stacked PR |
| 드롭다운 목록 | dropdown |
| 작업 흐름 | workflow |

표에 없는 용어도 같은 기준으로 고른다.

## 4. 표로 정리

- 섹션마다 표 하나가 기본이다. 행이 하나뿐이면 표 대신 한 줄로 쓴다.
- 열은 2~3개로 둔다. 더 필요하면 표를 나눈다.
- 셀은 한 줄이다. 셀 안에 줄바꿈이나 목록을 넣지 않는다.
- 결과 칸은 `통과`, `실패`, `미실행` 중 하나로 시작하고 필요하면 짧은 근거를 붙인다. 예: `미실행: token 미발급`

## 5. 코드 블록(선택)

리뷰어가 코드를 봐야 판단할 수 있는 변화가 있을 때만 넣는다.

- 대상: 함수 시그니처나 public API, 설정·스키마, CLI 사용법, 동작을 바꾸는 조건
- 형식: 짧은 변경은 `diff`, 새 설정이나 사용법은 해당 언어 블록
- 15줄 이내로 쓴다. 파일 전체나 diff에서 바로 보이는 단순 변경은 넣지 않는다.
- 블록 앞에 무엇인지 한 줄만 쓴다.

예:

````markdown
PR 본문의 ClickUp task ID 형식 변경

```diff
- ClickUp 작업 ID: #86c1ab2xy
+ ClickUp 작업 ID: CU-86c1ab2xy
```
````

## 6. 사실과 추측

- 실행한 검증은 명령과 결과를 그대로 쓴다.
- 실행하지 않은 검증은 `미실행`과 이유를 쓴다. "문제없을 것입니다"로 대신하지 않는다.
- 추측은 추측이라고 밝힌다.
- 수치에는 데이터 버전, 질문 세트, 모델, 표본 수를 붙인다.

## 7. 제출 전 점검

- [ ] 1절의 빼는 것이 남아 있지 않다
- [ ] 2절의 AI 말투가 없다
- [ ] 억지로 옮긴 용어 대신 영어 용어를 썼다
- [ ] 섹션 내용이 표로 정리돼 있고 셀이 한 줄이다
- [ ] 코드 블록은 필요한 곳에만 있고 15줄 이내다
- [ ] 미실행을 통과로 쓰지 않았다
