# 커밋 분할 기준

`AGENTS.md` 5절 "하나의 커밋에는 하나의 검토 목적만 담는다"의 실행 규칙이다.

## 하나의 검토 목적이란

리뷰어가 **한 번에 한 가지 질문만** 던지게 되는 단위다.

- "이 자료원의 권한 메타데이터가 맞나?" — 로더 커밋
- "이 청킹 단위가 검색에 맞나?" — 청킹 커밋
- "이 평가가 변경을 제대로 측정하나?" — 평가 커밋

한 커밋을 보며 두 가지 이상을 판단해야 하면 나눈다.

## 분할 축

우선순위 순으로 적용한다.

1. **파이프라인 단계** — 로딩 / 청킹 / 임베딩 / 저장 / 검색 / 생성 / MCP·인터페이스 / 평가
2. **타입** — 기능 추가와 리팩터링을 섞지 않는다. 포맷팅이나 이름 변경만 있는 파일은 별도 커밋으로 뺀다.
3. **자료원 단위** — GitHub, Notion, Figma, DB 스키마, API 문서처럼 자료원이 다르면 나눈다.
4. **부수 작업** — 의존성 추가, 설정 변경, 문서와 보고서는 구현과 분리한다.
5. **평가 세트** — 평가 세트와 정답 라벨은 평가 대상 변경과 항상 다른 커밋이다.

## 순서

앞 커밋만으로 import와 테스트가 깨지지 않도록 의존성의 아래에서 위로 쌓는다.

```text
계약·결정 문서 → DB 스키마·마이그레이션 → 모델·인터페이스 → 자료원 로더 → 청킹
→ 임베딩·저장 → 검색·생성 → MCP·CLI → 테스트 → 평가 세트 → 평가 보고서·문서
```

작은 버그 수정과 회귀 테스트처럼 같은 커밋이어야 검토가 쉬운 경우는 합쳐도 된다.
그때는 초안에 이유를 적는다.

## scope 선정

소문자, 숫자, 하이픈만 쓴다. 다음은 시작용 목록이며 실제로 쓰인 scope가 생기면 이 표를 갱신한다.

| scope | 대상 |
| --- | --- |
| `ingest` | 자료원 연결과 로더 |
| `chunking` | 청킹 규칙과 관계 추출 |
| `embedding` | 임베딩 제공자와 배치 |
| `store` | pgvector 스키마와 저장소 |
| `retrieval` | 하이브리드 검색, RRF, 문맥 확장 |
| `generation` | 프롬프트와 답변 생성 |
| `mcp` | MCP 서버와 도구 |
| `eval` | 평가 세트, 채점기, 평가 보고서 |
| `harness` | `AGENTS.md`, Skill, 검사 스크립트 |
| `workflow` | Issue·PR 템플릿, CI |

적당한 scope가 없으면 생략한다.

## 타입 선택

| type | 사용 |
| --- | --- |
| `feat` | 새 동작·기능 |
| `fix` | 결함 수정 |
| `refactor` | 외부 동작을 유지하는 구조 변경 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서·설계 산출물 |
| `chore` | 도구, 자동화, 의존성 |
| `ci` | GitHub Actions 워크플로 |
| `build` | 패키징, 빌드 스크립트 |
| `perf` | 성능·비용 개선 |

브랜치 prefix가 있으면 커밋 type을 맞춘다. 브랜치 타입을 벗어나는 변경이 크면 다른 작업으로 분리할지 묻는다.

## 커밋하면 안 되는 것

- `.env`, 로컬 설정, 자격 증명, 토큰
- `.venv/`, `__pycache__/`, `dist/`, IDE 파일
- 로컬 인덱스 덤프, 임베딩 캐시, 평가 원시 로그
- 스크래치 파일, 실험 코드, 주석 처리된 디버그 코드
- 다른 사람이 작업 중인 파일의 무관한 변경

발견하면 커밋에서 빼고 사용자에게 보고한다.

## 나누지 못하는 경우

한 파일 안에 여러 목적이 섞여 있으면 hunk를 자동으로 쪼개지 않는다. `git add -p`는 대화형이라
에이전트가 실행할 수 없다. 두 가지를 제안한다.

1. 한 커밋으로 합치고 커밋 본문에 두 목적을 나눠 적는다.
2. 사용자가 `! git add -p <파일>`로 직접 나눈 뒤 Skill을 다시 실행한다.
