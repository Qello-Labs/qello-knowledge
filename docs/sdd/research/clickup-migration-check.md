# ClickUp 이전 품질 확인

WBS 0.3 산출물이다. 원본 읽기 조사와 사용자가 허용한 테스트 문서 권한 실험의 결과다. Notion 원본과 ClickUp 화면·API Markdown을 비교해 RISK-01의 실제 차이를 확인했다. 권한 케이스 B·C는 현재 Workspace에서 해당 없음으로 판정했고, D는 실험하지 못했다. 근거와 사유는 4.2절에 적었다.

| 항목 | 내용 |
| --- | --- |
| 조사일 | 1차·2차 모두 2026-10-08, Asia/Seoul |
| 조사 방법 | 브라우저 Computer Use로 화면·렌더링된 DOM 관찰. ClickUp v3 Docs 단일 페이지 `content_format=text/md`, 페이지 메타데이터 트리, v2 사용자·Workspace·Space·Folder·List·Shared Hierarchy GET 조회 |

## 1. 대상 문서

문서 제목·원문 문장·사용자 이름·Workspace/Doc/Page 식별자·첨부 주소는 이 보고서에 넣지 않았다. 대조용 연결 정보는 Git 제외 작업 시트에만 있다.

| ID | 유형 | 조사한 페이지 수 | 직접 하위 페이지 / 전체 하위 페이지 | Markdown 바이트 | 비밀값 가림 |
| --- | --- | --- | --- | --- | --- |
| D1 | 기술 설계·용어 정리 | 1 | 0 / 0 | 40,878 | 0 |
| D2 | Notion DB였던 문서 | 루트 1 | 11 / 25, 메타데이터만 조사 | 167 | 0 |
| D3 | 기술 설계 | 1 | 0 / 0 | 43,063 | 0 |
| D4 | 기술 검토 첫 문서 | 1 | 0 / 0 | 33,040 | 0 |
| D5 | 기술 검토 두 번째 문서 | 1 | 0 / 0 | 4,043 | 0 |
| D6 | 회의 하위 본문 | 1 | 0 / 0 | 1,393 | 0 |
| D7 | 다른 회의 하위 본문 | 1 | 0 / 0 | 2,654 | 0 |

선택한 7개 본문 합계는 **125,238바이트**다. D4·D5는 공통 부모 페이지 아래의 서로 다른 원본에 대응하고 D6·D7은 같은 팀 Doc 컨테이너의 회의 하위 본문이다. 공통 부모와 추가 후보도 API 조회했으나 위 표본 합계에서 제외했다. 정확한 이전 방식은 확인하지 못했다. 현재 원본과 이전본의 차이는 확인했지만, 모든 차이가 가져오기 도구에서 발생했다고 단정하지 않는다.

필수 요소 중 표·헤딩·코드·링크·DB·하위 페이지·이미지는 관찰했다. D6은 원본 이미지 3개가 ClickUp 화면의 이미지 자리표시자 3개와 API의 자리표시자 3개로 나타났고, D7은 원본 이미지 1개가 ClickUp/API의 자리표시자 1개로 나타났다. 두 표본 모두 API Markdown 이미지 URL은 0개여서 HEAD 대상이 없었고 접근 가능성은 확인하지 못했다. Notion 후보 15개를 확인했으나 선택한 D6·D7에서는 토글·콜아웃·체크리스트가 0개였다. 토글 1개가 관찰된 후보는 같은 제목의 ClickUp 본문과 다른 기능명세 문서였으므로 등급을 붙이지 않았다. 회의록 DB 루트와 개별 회의 본문을 추가했지만 모든 회의 본문을 대표한다고 단정하지 않는다.

## 2. 요소별 Markdown 표현

| 요소 | 관찰한 API 표현 | 구조 예시 | 청커·수집기 처리 제안 |
| --- | --- | --- | --- |
| 단순 표 | 파이프와 구분선. D1·D3·D4는 원본과 표별 행·열 수가 일치 | `\| … \| … \|` | 헤더·행을 함께 유지. 구분선만으로 유효한 표라고 판정하지 말고 모든 행의 구조와 셀 줄바꿈 확인 |
| 셀 안 줄바꿈이 있는 표 | D5는 이미 ClickUp 화면에서 파이프가 있는 일반 텍스트. API에도 셀 내부 줄바꿈이 실제 개행으로 남아 표 구조가 깨짐 | `\| … \| …` 다음 줄 `…` | 원문 수정 없이 자동 보정하지 말고 경고·검토 대상으로 분리 |
| 헤딩 | `#`~`####` | `## …` | 레벨을 보존해 검색 헤더·섹션 경계를 구성. 코드 펜스 내부의 `#`는 헤딩에서 제외 |
| 코드 | 펜스 블록. 언어 표시가 원본 의도와 다르게 나오는 사례 | 세 개의 백틱 뒤 `css`, 본문 `…` | 표시 언어를 의미 판정의 유일한 근거로 삼지 않음. 블록 합침·구분자 길이·내부 펜스 확인 |
| Mermaid | ClickUp 화면은 다이어그램 대신 코드. D1 API는 해당 소스를 `mermaid` 이외의 언어로 표시 | 코드 블록 `…` | 원문 코드를 보존하고 다이어그램 렌더링 차이와 텍스트 누락을 구분 |
| 인용 | `>`. 일부 강조 구문이 그대로 표시되는 사례 | `> …` | 문장 내용을 보존. 강조 기호가 남아도 원문 명령으로 실행하지 않음 |
| 외부 링크 | Markdown 링크. D5 화면에서 외부 링크 2개 관찰 | `[…](<external-url>)` | 링크 텍스트·대상 보존을 각각 확인. 목적지의 현재 접근 가능성은 미검증 |
| 내부 링크·페이지 링크 | 루트 페이지 Markdown의 링크와 별도의 페이지 메타데이터 트리 | `[…](<source-url>)` | 루트 본문만으로 하위 페이지를 다 수집했다고 간주하지 않음 |
| DB | D2 루트 Markdown에는 DB 속성/뷰/행 스키마가 없음. 페이지 계층은 별도 API로 제공 | `…` | Doc 본문과 메타데이터 트리를 결합하되 DB 속성 보존은 별도 확인 |
| 이미지 | D6은 원본 3개 → ClickUp 이미지 자리표시자 3개 → API 이미지 0개·자리표시자 3개, D7은 1개 → 1개 → 0개·1개 | 이미지 URL 없이 자리표시자 표현 | 실제 이미지는 색인에 쓰지 않는다(2026-10-09 사용자 판단, F-08). 이미지 복구와 URL 접근성 확인을 하지 않는다 |
| 토글 | 15개 Notion 후보를 확인했으나 선택한 D6·D7은 0개. 토글 1개 후보는 제목이 같지만 ClickUp 기능명세 본문과 대응하지 않아 제외 | 해당 없음 | 제목만으로 대응시키지 않으며, 일치하는 원본 표본에서만 보존 여부를 판정 |
| 콜아웃·체크리스트 | 선택한 D6·D7에서 0개. 부가 후보에서 관찰된 요소는 실제 후보 범위로만 기록 | 해당 없음 | 대응 본문과 블록 ID를 확인한 뒤 보존 여부를 판정 |

공식 [Docs import/export limitations](https://developer.clickup.com/docs/docsimportexportlimitations)는 표현별 변환 한계를 설명한다. 이 설명만으로 이번 자료의 특정 요소가 보존됐거나 손실됐다고 판정하지 않았다.

## 3. 손실 확인

### 3.1 문서×요소 등급

등급은 0=확인한 구조 범위에서 차이 없음, 1=서식 차이, 2=내용 손실, 3=구조 차이, `-`=표본에 없음, `?`=미검증이다. 0은 **모든 문장·셀 내용의 완전 보존을 뜻하지 않는다**. 1차의 전체 문장·셀 보존 여부는 미확정이다. 2차 D6·D7에서는 이미지 내용 손실(2)을 관찰했다.

| 문서 | 표 | 토글 | 이미지 | 외부 링크 | 내부 링크 | 헤딩 | DB | 하위 페이지 | 코드 | 콜아웃 | 체크리스트 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| D1 | 0* | - | - | ? | ? | 0 | - | - | 1/3? | - | - |
| D2 | - | - | - | ? | ? | - | 3 | ? | - | - | - |
| D3 | 0* | - | - | ? | ? | 0 | - | - | 3? | - | - |
| D4 | 0* | - | - | ? | ? | 0 | - | - | 1/3? | - | - |
| D5 | 3 | - | - | ? | ? | 3 | - | - | 3 | - | - |
| D6 | - | - | 2 | ? | ? | 0* | - | - | - | - | - |
| D7 | - | - | 2 | ? | ? | 0* | - | - | - | - | - |

`0*`: D1·D3·D4는 원본 표와 API Markdown의 표 개수·행 수·열 수가 일치한 범위다. D6·D7은 페이지 제목을 제외한 본문 H2/H3 구조가 일치한 범위다. ClickUp 화면의 모든 표 셀을 통독하지 않았으므로 세 단계의 완전한 보존 검증은 미완료다.

## 4. access_scope 판별

### 4.1 API가 주는 권한 관련 정보

- 지정 Doc 메타데이터: `public=false`, `parent.type=4`(Space), `deleted=false`. `archived` 조회 값은 null/미확인으로 보존한다.
- 지정 부모 Space: `private=false`. 토큰으로 조회 가능한 Space 1개이며, 이 사실이 접근할 수 없는 비공개 Space의 부재를 증명하지 않는다.
- Shared Hierarchy 조회는 HTTP 200. API 설명의 대상은 Task·List·Folder이며 Doc 전체 공유 범위의 증거로 쓰지 않는다.
- Folder의 `permission_level`은 요청 사용자의 권한이다. `hidden`·`access`를 팀 전체 ACL로 해석할 공식 정의는 확인하지 못했다. [Get Folder](https://developer.clickup.com/reference/getfolder), [Get List](https://developer.clickup.com/reference/getlist)
- 토큰 인증 사용자의 Workspace 역할은 API 응답의 역할 수치값 1이며, [ClickUp 공식 FAQ](https://developer.clickup.com/docs/faq)의 매핑으로 Owner다. 이는 토큰 사용자의 역할이지 팀 전체 ACL의 증거가 아니다.

공식 [Search for Docs](https://developer.clickup.com/reference/searchdocspublic)와 [V3 OpenAPI](https://developer.clickup.com/openapi/ClickUp_PUBLIC_API_V3.yaml)는 현재 사용자에게 접근 가능한 Doc와 `public`, 부모 필드를 제공한다. [Shared Hierarchy](https://developer.clickup.com/reference/sharedhierarchy)는 Doc 전체 ACL 대용으로 명시되지 않는다.

### 4.3 제안

**확인한 사실:** Workspace members에게 공유된 Doc에서도 `public=false`였다. 공용 테스트 Folder와 비공개 테스트 Folder 모두 Folder API에서 `hidden=false`, `permission_level=create`, `space.access=true`를 반환했고, 두 자동 List도 `permission_level=create`, `folder.hidden=false`, `folder.access=true`를 반환했다. 따라서 이 필드 조합은 팀 전체 ACL이나 비공개 여부의 증거가 아니다. `public=true`는 테스트 Doc에서 일시 확인했지만 팀 전체 접근을 뜻한다고 일반화할 수 없다. `200`은 Owner 토큰의 조회 성공이며 팀 전원의 접근을 증명하지 않는다.

**잠정 제안:** 사람이 팀 공유를 확인한 Doc를 허용 목록으로 지정하고, Doc별로 사람 검증 허용 목록·부모·삭제/보관 상태·조회 성공을 재확인한다. 현재 확인되지 않은 자료는 판정 불가로 유지한다. 현재 요금제에서는 문서만 비공개인 Doc(C)이 생기지 않지만, 비공개 Folder(F)와 특정인 공유(D)가 남아 있어 Space 허용 목록만으로 충분하다고 단정하지 않는다. 이는 QK-SEC-001 입력 제안이며 값 체계 확정·수집 설정 반영이 아니다.

운영에서 수집 전용 계정의 시야를 제한하는 방식도 검토할 수 있지만, 확인된 Owner 역할의 한계와 D를 검증하기 전에는 채택 여부를 결정할 수 없다. [Share Docs](https://help.clickup.com/hc/en-us/articles/6325333637271-Share-Docs), [Permissions in detail](https://help.clickup.com/hc/en-us/articles/6309221065495-Permissions-in-detail)는 사용자·팀·위치 상속에 따른 권한을 설명한다.

## 6. 재현 방법과 검증 범위

### 6.1 실제 조회

ClickUp 요청은 모두 GET이었다. 지정 팀 Doc 밖의 다른 자동화 메모리 문서는 열거나 수집하지 않았다. 페이지 트리에서 식별자를 찾아 선택한 단일 페이지만 조회하여 전체 Doc 본문을 일괄 수집하지 않았다.

| API | 용도 |
| --- | --- |
| GET `/api/v2/team` | 지정 Workspace 접근 확인 |
| GET `/api/v2/team/{team}/space?archived=false` | 부모 Space의 private 확인 |
| GET `/api/v3/workspaces/{workspace}/docs?id={doc}` | 지정 Doc 메타데이터 |
| GET `/api/v3/workspaces/{workspace}/docs/{doc}/page_listing?max_page_depth=-1` | 본문 없는 페이지 계층 |
| GET `/api/v3/workspaces/{workspace}/docs/{doc}/pages/{page}?content_format=text/md` | 선택한 페이지의 Markdown |
| GET `/api/v2/team/{team}/shared` | Shared Hierarchy 응답 확인 |
| GET `/api/v2/user` | 역할 확인용 인증 사용자 ID만 저장 |
| GET `/api/v2/folder/{folder}` | 테스트 부모 Folder 신호 및 삭제 후 응답 |
| GET `/api/v2/list/{list}` | 테스트 부모의 자동 List 신호 및 삭제 후 응답 |

처음 두 번의 인증 조회 시도(각 2요청)와 인증 없는 진단 1회는 로컬 인증서 문제로 TLS 단계에서 실패했다. 기본 CA 경로가 없음을 확인한 뒤 시스템 신뢰 인증서를 지정했고, 인증서 검증을 끄지 않았다. 1차의 성공 조회 12회는 기존 기록을 유지했다(조사자 집계. 1차 호출 기록 파일에는 GET 200 10건이 남아 있다). 2차 GET은 **26회 모두 HTTP 200**이었다(1차와 별도 집계). 처음 D6로 기록한 호출 1개는 제목 대응이 맞지 않아 제외 후보 파일로 분리했으며, 확정 D6를 별도 조회했다. 제외 후보를 표본 합계에 넣지 않았다. 401/403/404/429 권한 실패는 관찰하지 못했다. 이 수치로 비공개 접근 실험의 성공을 주장하지 않는다.

`page_listing`과 단일 페이지 GET은 공식 [Page Listing](https://developer.clickup.com/reference/getdocpagelistingpublic), [Get page](https://developer.clickup.com/reference/getpagepublic)를 확인해 사용했다. 단일 페이지 호출에 확인되지 않은 하위 페이지 필터를 넣지 않았다. [호출 한도](https://developer.clickup.com/docs/rate-limits)를 넘길 규모의 작업은 실행하지 않았다.

선정한 D6·D7은 API Markdown 이미지 URL이 0개여서 첨부 URL HEAD 검사는 실행할 대상이 없었다. 따라서 이미지 접근 가능성은 미확정이다. 토큰을 다른 호스트에 보내거나 리다이렉트로 전달하지 않았다. 임베딩·생성 API 호출, 색인 실행, 유료 설정 변경은 없다.

### 6.2 집계 기준

- Notion: 렌더링된 DOM의 표 행·열, 고유 블록 식별자의 코드, 헤딩·DB·뷰를 관찰. DB의 중복 DOM 4개는 하나의 고유 블록으로 집계했다. 원본 본문을 로컬 파일로 복사하지 않았다.
- ClickUp: 렌더링된 표/코드 컨테이너와 화면 표시를 관찰. placeholder는 표 존재 신호만으로 기록하며 셀 내용으로 세지 않았다. 긴 문서 전체를 처음부터 끝까지 셀 단위로 확인한 결과는 아니다.
- API: 코드 펜스 안쪽을 제외해 헤딩·표를 집계. 펜스는 시작 문자와 길이로 닫힘을 확인했다. D5의 셀 개행 파손은 별도로 확인했다.
- 모든 자료는 현재 조회 시점의 원본이다. D6·D7 원본과 이전본은 동시점 스냅샷이 아니며, Notion·ClickUp의 버전 이력은 모든 편집 이벤트의 완전한 동시점 기록이 아니므로 이미지 차이의 원인과 시점을 전부 확정할 수 없다.

### 6.3 검증

실행 결과는 `validation.json`과 `run-result.json`에 기록한다. 2차 보고서 갱신 후 상위 저장소 preflight(텍스트 54개)와 `git diff --check`를 다시 실행해 통과했다. 별도 검증 에이전트가 최종 갱신본을 검토했다. 확인된 로컬 증거는 일치했다. 조사 당시 작업 폴더의 추적 파일은 0개였고 보고서·환경 파일 모두 제외 상태였다.

1차 파일을 보존한 상태에서 2차를 포함한 Git 제외 텍스트 조사 파일 56개에 동일 비밀값 규칙과 ClickUp 토큰 규칙을 별도로 적용한 결과 발견 0이었다. 이 공개용 보고서의 문서 제목·사용자 이름·실제 식별자 검사도 발견 0이었다. 선택한 7개 원문의 Markdown 바이트 합계는 125,238바이트이며 D1·D3·D4·D6·D7의 구조 집계와 D6·D7 이미지 관찰을 기록했다. 이 수치는 로컬 산출물 검증이며 원본 전체 보존 또는 권한 실험 완료의 증거가 아니다.

별도 검증 에이전트의 문서·로컬 증거 검토는 원본 UI 전체 재현이나 사람 승인과 구분한다. 1차 에이전트가 바이트 합계·표 형상·코드 경계·Git 제외 및 초안의 미완료 표기를 확인했다. 2차 권한·정리·GET 제한 증빙은 별도 에이전트가 검토했다. 최종 보고서·시트·API 기록·활동 기록 집계의 일관성을 별도 에이전트가 확인했다(PARTIAL). 원본 UI 독립 재현·사람 승인은 수행되지 않았다. D3 헤딩의 불일치 후보는 검증 파서 오류로 확인해 철회했고, 엄격한 Markdown 경계에서 1/21/46과 펜스 30개를 재확인했다.

정식 반영 전(2026-10-09) 조사 지시문을 쓴 Claude Code 세션이 로컬 증빙을 다시 대조했다. 선택 Markdown 7개의 실제 파일 크기 합계 125,238바이트, 2차 호출 기록 26건 모두 GET 200, 수집 스크립트의 GET 전용 여부, 테스트 항목 7개의 이름 접두와 휴지통 이동 기록, 환경 파일과 이미지를 뺀 로컬 텍스트 파일 61개의 비밀값·ClickUp 토큰 검사 0건을 확인했다. 지시문 작성자와 같은 세션의 확인이므로 독립 검증이 아니다.

**남은 조사 항목:** D의 실제 제한 상태 확인. B·C는 2026-10-09 사람이 현재 해당 없음으로 판정했다. 작업 계약 연결과 정식 반영은 #8로 마쳤고, 사람 승인(PR 리뷰)이 남았다. 1차의 긴 문서 전체 문장·셀·링크 목적지 검증 한계는 재조사 없이 보존했다. D6·D7의 이미지 차이는 확인했지만 동시점 스냅샷이 아니며 HEAD 대상이 없어 접근 가능성은 미확정이다. 테스트 Doc 3개와 Folder 2개는 UI 휴지통에서 확인했으며 내부 List 2개는 부모와 함께 정리됐다. 휴지통을 비우지 않았고, Folder/List API 삭제 상태는 확정하지 않았다. 2026-10-09 사람이 ClickUp 화면에서 테스트 Folder가 지워진 것을 확인했다. Folder 내부 항목이 별도 휴지통 행으로 표시되지 않는다는 [공식 안내](https://help.clickup.com/hc/en-us/articles/6311742742423-Restore-items-from-the-Trash)와 일치한다. 이 결과를 이유로 ClickUp 완료 상태를 바꾸지 않는다.

### 6.4 활동 기록

1·2차에서 본 기존 문서 및 탐색 후보의 기록 화면 **32개(Notion 22개, ClickUp 10개)**를 확인했다. 모든 대상의 최신 표시 버전은 작업일 이전이었으며 이번 작업일의 편집 기록은 발견하지 못했다. Notion은 Version history, ClickUp은 Settings → This page → Show page history로 열었다. 복원은 실행하지 않았다. 문서별 결과와 최신 표시 날짜는 `round2/activity-history.json`과 작업 시트에 있으며 사람 이름은 저장하지 않았다.
