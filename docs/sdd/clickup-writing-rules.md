로드맵은 이 작업의 산출물을 "sources.md 7절 확정"으로 적었지만 저장소에 `sources.md`가 없다(0.3 보고서 F-10). 그래서 이 문서를 따로 둔다.

## 1. 폴더 구조

### 1.1 Team Docs 문서 종류

`Team Docs` 바로 아래에는 아래 표의 페이지만 둔다. 새 문서는 반드시 이 중 하나의 아래에 만든다. 수집기는 문서가 `Team Docs` 바로 아래의 어느 페이지에 속하는지로 문서 종류를 정한다.

| 페이지 | 넣는 문서 | 색인 대상 후보 |
| --- | --- | --- |
| `회의록` | 회의 기록(2절 템플릿) | 예 |
| `용어집` | 팀 용어 정의(3절). 새로 만든다 | 예 |
| `Qello 기능명세서` | 기능 명세·기획 | 예 |
| `설계 문서` | 기술 설계 | 예 |
| `API Docs` | API 설명 | 예 |
| `Design Docs` | 디자인 문서 | 예 |
| `개발 규칙 문서` | 코딩·협업 규칙 | 예 |
| `ADR` | 새 ADR을 쓰지 않는다. 기존 페이지는 그대로 둔다. 하위 페이지 4개는 모두 비어 있다(2026-10-10 확인) | 아니오 |
| `관리자용` | 운영자 기능 명세 7개가 있다(2026-10-10 확인). 위치 미정(7절 O-3) | 아니오(권한 확인 전) |

- "색인 대상 후보"는 문서 종류 기준이다. 실제 수집은 QK-SEC-001에서 Doc별로 사람이 팀 공유를 확인한 뒤에만 한다(0.3 보고서 4.3절, AGENTS.md 3.1).
- ADR은 색인 대상에서 뺀다(2026-10-10 사용자 결정). 기준 원본을 백엔드 저장소 `docs/adr/`로 두고 새 ADR을 ClickUp에 쓰지 않는 것은 에이전트 해석이며, 리뷰에서 확인한다(인벤토리 F-9).
- 이 목록은 고정이다. 종류를 더하거나 빼려면 이 표를 고치고 주간 리뷰에서 합의한다. 수집기 설정도 함께 바꾼다.

### 1.2 `기타문서` 제거

`기타문서`는 분류 신호가 없어 없앤다. 2026-10-10에 확인했을 때 `기타문서`에는 하위 페이지가 없었으므로 빈 페이지만 지우면 된다. 앞으로 비슷한 페이지가 생기면 아래 절차를 따른다.

1. `기타문서` 하위 페이지 목록을 만들고, 페이지마다 1.1 표에서 옮길 곳을 적는다.
2. 맞는 곳이 없는 페이지가 있으면 옮기기 전에 팀이 정한다. 새 종류가 필요하면 1.1의 변경 절차를 따른다.
3. 팀이 목록을 확인하면 페이지를 옮기고, 빈 `기타문서` 페이지를 지운다. 지우는 일은 사람이 한다.
4. 옮긴 뒤 다른 문서에 있던 링크가 그대로 열리는지 확인한다. 페이지 이동 뒤에도 링크가 유지되는지는 공식 문서에서 확인하지 못했다.

## 2. 회의록

### 2.1 위치와 제목

- 새 회의록은 `Team Docs` → `회의록` 바로 아래에 만든다. 주차별 상위 페이지는 새로 만들지 않는다(인벤토리 F-11).
- 제목은 `YYYY-MM-DD <회의 종류>`로 쓴다. 예: `2026-10-14 정기 회의`.
- 수집기는 회의 날짜를 제목이 아니라 `일시` 필드에서 읽는다. 제목의 날짜는 사람이 목록에서 찾기 위한 것이다.
- 회의 속성(일시, 참석자)은 ClickUp 회의록 본문 위쪽의 필드 표를 기준으로 삼는다. Notion 회의록 DB는 기준으로 쓰지 않는다(0.3 F-05).
- (제안) 회의록은 ClickUp에만 쓴다. Notion은 색인 대상이 아니다(AGENTS.md 3.1).
- (제안) 회의 종류는 `정기 회의`와 `아이디어 회의` 둘로 시작하고, 필요하면 이 목록에 더한다. 주차를 남기고 싶으면 제목 뒤에 `(N주차)`를 붙인다.

### 2.2 템플릿

```markdown
| 필드 | 값 |
| --- | --- |
| 일시 | YYYY-MM-DD |
| 회의 종류 | 정기 회의 |
| 참석자 | <이름>, <이름> |
| 관련 명세 ID | <기능명세서 ID>, <기능명세서 ID> |

## 안건

1. <안건>

## 논의 내용

### <안건 제목>

<논의한 내용>

## 결정 사항

- <결정 하나와 이유>

## 액션 아이템

| 담당 파트 | 담당자 | 할 일 | 기한 | ClickUp 작업 |
| --- | --- | --- | --- | --- |
| Backend | <이름> | <할 일> | YYYY-MM-DD | <작업 링크> |

## 다음 회의

- 일시: YYYY-MM-DD

### 안건

1. <안건>

## 기타

- <추가 기록, 원본 링크>
```

- `일시`는 `YYYY-MM-DD` 형식으로 쓴다. 관련 명세가 없으면 `관련 명세 ID`에 `없음`을 적는다.
- `결정 사항`에는 한 줄에 결정 하나를 적는다. 지금은 결정이 회의 내용에 섞여 있어 "그때 뭘로 정했지?" 같은 질문의 근거를 찾기 어렵다.
- `액션 아이템`에는 한 행에 할 일 하나를 적는다. `담당 파트`는 4절에 적은 값을 쓴다. ClickUp 작업이 있으면 링크를 붙인다. 회의와 작업을 잇는 QK-CHK-003이 이 표를 쓴다.
- 화이트보드나 화면 캡처처럼 이미지로만 남긴 내용은 요점을 글로도 적는다. 이전한 회의록의 이미지는 자리표시자만 남았다(0.3 L-12, L-14).
- (제안) 헤딩에 이모지를 넣지 않는다. 절 이름이 검색 헤더로 그대로 쓰이므로 이름을 일정하게 둔다.

기존 형식과의 대응은 다음과 같다.

| 기존 형식(인벤토리 5.2) | 새 템플릿 |
| --- | --- |
| `사람` | `참석자` |
| `생성일`, `수정일`, `숫자` | 뺀다. Notion DB 속성이 이전 과정에서 남은 것으로 추정한다 |
| `일시` | `일시` |
| `장소/채널` | 뺀다. 확인한 두 문서 모두 `디스코드`였다 |
| `📚 회의 아젠다` | `안건` |
| `🗒️ 회의 내용` | `논의 내용`, `결정 사항` |
| `🌟 다음 회의까지 준비할 내용` | 다음 회의 일정은 `다음 회의`로, 준비 사항과 담당자는 `액션 아이템`으로 |
| `🌟 다음 회의에 진행할 내용` | `다음 회의` |
| `🎸 기타` | `기타` |

### 2.3 템플릿 등록

- 2.2 내용을 ClickUp 페이지 템플릿으로 저장한다([Create Doc templates](https://help.clickup.com/hc/en-us/articles/6325242385943-Create-Doc-templates)).
- (제안) 현재 요금제에서 페이지 템플릿을 쓸 수 없으면, 복사용 `회의록 템플릿` 페이지를 `Team Docs` 밖에 둔다. `Team Docs` 안에 두면 자리표시자만 있는 페이지가 문서로 색인된다.
- API로는 템플릿을 등록할 수 없다. 2026-10-10에 `Qello` Space 바로 아래(`Team Docs` 밖)에 `회의록 템플릿` Doc을 만들었다. 이 Doc을 화면에서 템플릿으로 저장하는 일은 사람이 한다.

### 2.4 기존 회의록

기존 회의 페이지 20개도 2.2 템플릿에 맞게 고친다(2026-10-10 사용자 결정, 7절 O-2). 고치는 방법과 검토 절차는 O-1에서 정한다. 수집기는 변환 여부와 관계없이 다음 기준으로 처리한다.

- 날짜는 `일시` 필드에서 읽는다.
- `일시` 필드가 없는 페이지는 회의로 세지 않는다. 1~4주차의 주차 상위 페이지 4개(인벤토리 5.1)와 본문이 빈 `Untitled` 페이지(인벤토리 F-12)가 여기에 해당한다. 실제 회의록인데 `일시`가 빠진 페이지가 있으면 변환할 때 채운다.

## 3. 용어집

`Team Docs` → `용어집` 페이지 하나에 표 하나로 둔다. 질문에 쓰인 말과 코드 식별자를 검색이 이어 주게 하는 것이 목적이다(RISK-05).

```markdown
| 용어 | 정의 | 동의어·약어·영문 | 코드 식별자·API 경로 | 관련 문서 |
| --- | --- | --- | --- | --- |
| <용어> | <한 문장 정의> | <동의어>, <약어> | `<ClassName>`, `<GET /path>` | <링크> |
```

- 한 행에 용어 하나를 적는다. 정의는 한 문장으로 쓴다.
- 한 셀에 값이 여럿이면 쉼표로 구분한다. 셀 안에서 줄바꿈하지 않고, 셀에 `|`를 쓰지 않는다(5절).
- 회의, PR, 명세에서 새 용어가 나오면 그 용어를 쓴 사람이 행을 더한다. 정의가 서로 부딪히면 용어집 담당이 정리한다(7절 O-5).
- (제안) 행은 용어의 가나다순으로 두고, 코드 식별자와 API 경로는 백틱으로 감싼다.
- (제안) 첫 항목은 기존 문서에서 후보를 뽑고, 팀이 정의를 확인한 뒤 넣는다. 에이전트가 정의를 지어서 넣지 않는다.

## 4. 파트

파트는 작업이 있는 Folder로 정한다. Custom Field는 만들지 않는다(2026-10-10 사용자 결정). 이 Workspace는 Free Forever 요금제이고, ClickUp 도움말에 따르면 이 요금제의 Custom Field 사용 한도는 60회라서 한도에 이르면 값을 더 넣지 못한다([Custom Fields uses](https://help.clickup.com/hc/en-us/articles/10993484102167-Custom-Fields-uses)).

| 작업 위치 | 파트 |
| --- | --- |
| `Android 스프린트` Folder | `Android` |
| `Backend 스프린트` Folder | `Backend` |
| `Bug Tracking`, `팀 일정` List | `Common` |

- 파트 작업은 그 파트 Folder의 List에 만든다. 여러 파트가 함께 하는 일은 파트별 작업으로 나누고 같은 명세 ID를 단다([작업 연결 규칙](../github-workflow.md)).
- 파트는 Tag나 GitHub 라벨로 만들지 않는다. 기준이 여러 곳에 있으면 `/status`의 파트별 집계(`3.G`)가 어긋난다.
- 회의록 `액션 아이템`의 `담당 파트`에는 `Backend`, `Android`, `Design`, `Common` 중 하나를 쓴다.
- `Bug Tracking`의 버그는 이 방식으로는 어느 파트 것인지 알 수 없다. 파트별 버그 집계가 필요해지면 다시 정한다.
- (제안) 디자인 작업을 ClickUp에서 관리하게 되면 `Design 스프린트` Folder를 만든다.

## 5. 공통 작성 규칙

`Team Docs`의 모든 문서에 적용한다. 근거는 0.3 보고서 3.2절의 손실 사례다.

| 규칙 | 근거 |
| --- | --- |
| 표 셀 안에서 줄바꿈하지 않는다. 내용이 길면 표 밖에 목록으로 쓴다 | L-09: 셀 안 줄바꿈이 있는 표가 API Markdown에서 표로 읽히지 않았다 |
| 다이어그램은 Mermaid 코드 블록으로 넣고, 요점을 바로 아래에 문장으로도 쓴다 | L-03: 이전한 문서에서 다이어그램이 코드로 표시됐고, API는 그 코드의 언어 표시를 `mermaid`로 주지 않았다. ClickUp에서 새로 쓴 Mermaid 블록의 언어 표시가 유지되는지는 확인하지 않았다 |
| 코드 블록 두 개를 바로 붙이지 않는다. 사이에 설명 한 줄을 둔다 | L-10: 별도의 코드 블록 경계가 하나로 합쳐졌다. L-07도 같은 가능성이 있다(미검증) |
| 헤딩 서식은 절 제목에만 쓴다. 강조하려고 일반 문장을 헤딩으로 만들지 않는다 | L-11: 일반 문구가 H4가 되어 섹션 경계가 늘었다 |
| 이미지에만 있는 정보는 글로도 적는다 | L-12, L-14: 이미지가 자리표시자로만 남았다 |

## 6. ClickUp 반영 체크리스트

에이전트가 ClickUp API로 반영한다(7절 O-1). 원본 자료원에 쓰는 일이므로 `TASK.md` Decisions에서 허용한 항목만 한다. 지금은 허용한 항목이 없다.

문서 본문을 고치는 순서는 다음과 같다.

1. 대상 페이지 원문을 API로 받아 Git 제외 폴더(`.work/0.4/`)에 보관한다.
2. 에이전트가 페이지별 변환본과 원문 대비 차이를 만든다.
3. 사람이 변환본을 검토한다. 결정 사항과 액션 아이템을 맞게 옮겼는지 특히 확인한다.
4. 승인한 페이지 중 하나를 먼저 고치고 ClickUp 화면에서 확인한다. API는 Markdown으로만 쓰므로 편집기 서식(멘션, 링크 미리보기 등)이 사라질 수 있다.
5. 문제가 없으면 나머지 승인 페이지를 고친다.

- [x] `Team Docs` 바로 아래에 `용어집` 페이지를 만든다(3절).
- [ ] 회의록 템플릿을 등록한다(2.3절). 템플릿 Doc은 만들었고, 화면에서 템플릿으로 저장하는 일이 남았다.
- [ ] 빈 `기타문서` 페이지를 지운다(1.2절). 하위 페이지가 없어 옮길 문서는 없다. 지우는 일은 사람이 한다.
- [x] 기존 회의록 20개를 2.2 템플릿으로 바꾼다. 바꾸기 전 원문을 Git 제외 폴더에 보관한다(2.4절).
- [x] 다른 문서에서 5절 규칙에 어긋나는 곳(셀 안 줄바꿈 표, 붙은 코드 블록 등)을 고친다. 다이어그램 코드 언어 표시 36개는 보류했다(6.1절).
- [x] `파트` Custom Field는 만들지 않는다(4절).
- [x] `ADR` 페이지는 바꾸지 않는다. 색인 제외는 수집기 설정(QK-ING-003)에서 한다.
- [ ] 반영한 사람이 아닌 검토자가 ClickUp을 다시 읽어 이 문서와 대조하고 결과를 이 문서에 남긴다. 식별자와 원문은 적지 않는다.

### 6.1 반영 기록(2026-10-10)

에이전트가 ClickUp API로 반영했다. 바꾸기 전 `Team Docs` 147페이지의 원문은 Git 제외 폴더에 보관했다.

API로 Markdown을 다시 쓸 때 다음이 바뀌었다. 같은 일을 다시 할 때 참고한다.

- 인용 블록 바로 다음 줄이 인용 안으로 들어갔다. 인용 블록 뒤에 빈 줄을 넣어 다시 썼다.
- 이미지 자리표시자 줄이나 글머리 목록 뒤의 번호 목록이 앞 목록에 이어 번호가 매겨졌다. 새 목록이 시작되는 `1.` 앞에 빈 줄을 넣어 다시 썼다.
- 한 줄 안의 `~` 두 개 사이가 취소선이 됐다. `\~`로 바꿔 다시 썼다.
- 따옴표로 시작하거나 끝나는 굵게(`**“…”**`)가 굵게로 읽히지 않았다. 따옴표를 굵게 밖으로 뺐다.
- 표 셀 안의 굵게는 사라졌다. 고치지 못했다.
- `@이름` 멘션은 일반 글자로 저장된다.

다이어그램 코드 블록의 언어 표시 36개는 이번에 고치지 않았다. 수집기(QK-CHK-002)가 내용으로 판별하게 한다.

이 확인은 반영한 세션 안에서 한 기계 대조다. 화면 확인은 사람이 한다(AGENTS.md 2절).
