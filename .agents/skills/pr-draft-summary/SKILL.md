# PR Draft Summary

Claude Code판(`.claude/skills/pr-draft-summary`)과 절차가 같고 호출 문법과 참조 경로만 다르다. 절차를 바꾸면 두 Skill을 함께 고친다.

구현을 마친 뒤 실제 diff에서 PR 제목과 본문 초안을 만든다. 리뷰어가 한 번 읽고 다음 세 가지를 알 수 있어야 한다.

- 왜 이 변경이 필요했는가
- 어떤 동작이 바뀌었는가
- 리뷰어가 무엇을 봐야 하는가

PR 본문은 구현 기록이나 파일별 설명이 아니다. 완전함보다 명확함, 정확함, 짧음을 앞에 둔다.
이 저장소의 PR 작성 규칙(`.agents/skills/harness-pr/references/writing-style.md`)과 `AGENTS.md` 5·7·8절을 함께 지킨다.
둘이 이 문서와 다르면 그 문서들을 따른다.

## 1. 언제 쓰는가

해당 구현 리뷰와 검증을 마친 뒤 쓴다. 다음이 바뀌었으면 크기와 관계없이 쓴다.

- 실행 코드, 테스트, 예제
- 빌드·테스트 설정
- 동작에 영향을 주는 문서(하네스 규칙, 설정 절차 포함)

커밋된 변경, staged, unstaged, 추적되지 않는 파일을 모두 포함한다.

다음은 자동으로 쓰지 않는다. 사용자가 PR 초안을 명시적으로 요청하면 이 제외보다 요청이 우선한다.

- 동작 영향이 없는 오탈자·문구 수정
- 대화만 한 작업
- 동작 영향이 없는 저장소 메타데이터 변경
- 사용자가 쓰지 말라고 한 경우

초안을 만드는 것은 브랜치 생성·전환, 커밋, push, PR 생성·수정 권한을 주지 않는다. 그 작업은 따로 승인을 받고
`$harness-commit`, `$harness-pr` 절차로 한다.

## 2. Git 맥락 수집

저장소에서 얻을 수 있는 정보는 사용자에게 묻지 않는다.

```bash
git rev-parse --abbrev-ref HEAD
git status -sb
git ls-files --others --exclude-standard
git diff --name-only
git diff --name-only --cached
git diff --stat
git diff --stat --cached
```

- 기준 브랜치는 PR 대상(보통 `main`)이다. 알 수 없으면 현재 브랜치의 upstream이나 저장소 기본 브랜치를 쓴다.
- 커밋을 보기 전에 merge base를 구한다: `git merge-base origin/main HEAD`.
- 커밋 목록: `git log --oneline --no-merges <merge-base>..HEAD`.
- merge base 이후 커밋된 변경, staged, unstaged 변경과 추적되지 않는 파일의 내용을 직접 읽는다.
  `git diff --stat`은 추적되지 않는 파일을 보여주지 않으므로 따로 읽는다.
- 커밋 메시지나 통계만 보고 판단하지 않는다.
- `TASK.md`에서 Jira 이슈, 기능명세서 ID, 팀 스프린트 ID, 완료 조건을 읽는다. 브랜치에 `gh-<번호>`가 있으면 Issue도 읽는다.

## 3. 변경 분석

1. 관련 변경이 없으면 그렇다고 짧게 보고하고 초안을 지어내지 않는다.
2. 주된 변경 종류를 정한다: 기능 추가, 버그 수정, 리팩터링, 성능 개선, 동작에 영향을 주는 문서.
3. 실제 diff로 다음을 찾는다.
   - 원래 문제나 요구사항
   - 주된 동작 변화
   - 중요한 구현 결정(결정 기록이 있으면 그 링크)
   - 호환성 위험
4. 이를 1~3문장으로 요약한다. 꼭 필요한 파일이 아니면 파일을 나열하지 않는다.
5. 호환성 위험은 diff가 다음을 건드릴 때만 적는다. 없는 위험을 만들지 않는다.
   - 공개 API, 외부 설정(`.env` 항목, CI), 저장된 데이터와 스키마·마이그레이션, 인덱스 버전, 직렬화 형식

## 4. 초안 작성

### 4.1 브랜치

이미 `AGENTS.md` 1절 형식의 작업 브랜치에 있으면 그대로 둔다. 아니면 그 형식으로 이름만 제안한다.
제안은 브랜치를 만들 권한이 아니다.

### 4.2 제목

`<type>: <한국어 요약>` 한 줄이다. `type`은 브랜치 접두사와 같고 scope와 Jira 이슈 키는 넣지 않는다.
요약은 명사형으로 끝내고 부수적인 구현 세부가 아니라 결과나 목적을 담는다.

- 좋은 예: `feat: 저장 스키마·마이그레이션·검색 질의 구현`, `fix: 동시 교체 시 청크 섞임 방지`
- 쓰지 않는 예: `로직 수정`, `코드 개선`, `여러 변경`

### 4.3 본문

순서는 `harness-pr` 작성 규칙 2절을 따른다. 그 안에서 다음을 지킨다.

1. `Closes #<번호>`(Issue가 실제로 해결될 때만), Jira 이슈 URL, 기능명세서 ID, 팀 스프린트 ID를 한 문단으로 쓴다.
2. 설명 첫 문단은 "이 PR은 ~합니다."로 시작한다. 동사는 변경 종류에 맞춘다.
   - 기능 추가: 추가합니다 — 어떤 능력이 왜 필요했는지와 바뀐 동작을 쓴다.
   - 버그 수정: 고칩니다 — 원래 증상이나 재현 방법과 어떻게 고쳤는지를 쓴다.
   - 리팩터링: 정리합니다 — 유지보수·구조 문제와 의미 있는 구조 변화를 쓴다. 근거 없이 동작이 좋아졌다고 쓰지 않는다.
   - 성능 개선: 개선합니다 — 병목과 최적화를 쓰고, 수치는 측정했을 때만 조건과 함께 쓴다.
   - 문서: 갱신합니다 — 무엇이 어떻게 달라지는지 쓴다.
3. 리뷰어가 diff만으로 알 수 없는 결정과 트레이드오프는 결론과 결정 기록 링크로 쓴다.
4. 완료 조건 표(`확인한 것 | 결과`)는 `AGENTS.md`가 요구하므로 유지하되 간결하게 쓴다.
   - `TASK.md` 완료 조건을 행으로 옮기고, 실행한 검증 명령은 한 행으로 묶는다.
   - 테스트 파일이나 테스트 이름을 나열하지 않는다. 근거는 결과 칸에 링크 하나로 붙인다.
   - 리뷰로 확인할 항목은 리뷰 전에는 `미실행`이다.
5. 실행하지 못한 검증과 이유·후속 방법, 남은 위험과 되돌리는 방법을 쓴다. 단순한 변경이면 한 문단이면 된다.
6. PR 템플릿의 리뷰 확인 체크박스를 둔다. 실제로 한 것만 체크한다.

## 5. 작성 제약

### 간결함

- 단순한 변경은 설명을 1~3문장으로 끝낸다. 목록은 서로 다른 변경을 나눠야 할 때만 쓰고, 항목 하나에 결과 하나만 담는다.
- diff를 보면 바로 아는 내용, 제목과 같은 내용, 다른 곳에 이미 쓴 내용은 빼낸다.
- 핵심이 아니면 개별 클래스·함수·파일을 설명하지 않는다.
- 고정 길이는 두지 않는다. 다만 본문은 링크 주소를 포함해 3,000자를 넘지 않는다.

### 정확함

- 모든 문장은 실제 변경으로 뒷받침되어야 한다. 계획만 한 일을 끝낸 일로 쓰지 않는다.
- 실행하지 않은 테스트를 통과로 쓰지 않는다. 측정하지 않은 성능 수치를 쓰지 않는다.
- 근거 없이 안정성·보안이 좋아졌다고 쓰지 않는다.
- 구현한 동작과 남은 한계를 구분한다.

### 빼는 것

- 단계별 구현 기록, 수정 파일 전체 목록, 함수별 설명
- 겹치는 요약·변경 절, 뻔한 코드 변경 설명
- 템플릿 체크박스 밖의 불필요한 체크리스트
- 이모지, 과한 굵은 글씨, 자기 칭찬
- 작성 도구에 대한 언급, 면책 문구, 서명 줄
- 요청이 없거나 이해에 필요하지 않은 테스트 목록
- 추측성 향후 개선

### 남기는 것

정확성을 짧음과 바꾸지 않는다. 해당할 때 다음은 반드시 남긴다.

- 호환성을 깨는 변경, 필요한 마이그레이션, 배포 시 고려사항
- 드러나지 않는 트레이드오프와 동작 한계
- diff로 알 수 없는 리뷰어 결정 사항

## 6. 참조

- 같은 저장소의 Issue·PR은 `#123`, 다른 저장소는 `owner/repo#123`으로 쓴다. Issue·PR 참조를 전체 URL이나 Markdown 링크로 바꾸지 않는다.
- Jira 이슈 URL, 명세·결정 기록·외부 문서 링크는 쓸 수 있다. 저장소 파일 링크는 지금 커밋에 고정한 주소로 건다.
- 로컬 파일 링크, 에이전트 전용 이동 링크, 내부 인용 표시, 도구 지시, 불필요한 각주는 넣지 않는다.

## 7. 최종 점검

초안을 내기 전에 확인하고, 걸리면 고친다. 점검 과정은 출력하지 않는다.

1. 변경 목적이 첫 문단에서 바로 이해되는가
2. 모든 주장이 최종 diff로 뒷받침되는가
3. 왜 중요한지 설명했는가
4. 지워도 정보가 줄지 않는 문장이 남았는가
5. 겹치는 절이나 반복 설명이 있는가
6. 호환성 위험을 정확히 적었는가
7. 합쇼체이고 `writing-style.md` 4절 금지 표현과 6절 점검을 통과하는가
8. GitHub에 그대로 붙여 넣을 수 있는가

## 8. 출력 형식

```text
# PR 초안

## 브랜치
<현재 브랜치. 바꿔야 하면 제안 이름>

## 제목
<type>: <한국어 요약>

## 본문
<GitHub에 그대로 붙여 넣을 본문>
```

앞뒤 설명을 덧붙이지 않는다. GitHub에 쓸 때는 제목과 본문만 PR 필드에 넣고, 브랜치 줄과 위 제목들은 넣지 않는다.
