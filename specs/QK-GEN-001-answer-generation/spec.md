  빠지는 것을 받아들인다. 뺀 수를 요약에 남기고, 첫 예외가 등록되면 다시 검토한다. QK-RET-001 계약은 바꾸지 않는다(FR-010).
- Q: (독립 검토 M6) FR-015 결정은 AGENTS.md 3.2("답변에는 Source ID를 단다. 근거가 없으면 확인할 수 없다고 답한다")와 부딪힌다. 유지하나? → A: 유지한다. 충돌을 알고 정했다
  (FR-015, Assumptions).

## User Scenarios & Testing *(mandatory)*

이 명세의 사용자는 생성 결과를 Discord에 보여 주는 후속 명세 구현자(QK-BOT-001), 답변을 평가하는 평가 구현자(QK-EVL-002), 생성 사용량과 실패를 확인하는
운영 담당자, PR 리뷰어다. 최종 사용자(Discord에서 질문하는 팀원)는 이 명세가 만든 답변 본문과 출처 목록을 QK-BOT-001을 거쳐 본다.

용어:

- **Context**: QK-RET-001이 돌려준 문맥 묶음 목록. 묶음마다 Source ID(`S1`, `S2` …), 문서 단위 출처 정보(원본 링크·버전·원본 수정 시각·수집 시각), 청크별 제목 경로,
  끊긴 자리 표시가 있다.
- **인용**: 답변 본문 안의 `[S1]` 같은 Source ID 표기.
- **유효 인용**: 이번 Context에 실제로 있는 Source ID를 가리키는 인용.
- **확인 불가 문장**: `제공된 자료만으로 확인할 수 없습니다.` 이 글자 그대로의 문장(constitution C-01 문구).
- **생성 입력**: 시스템 프롬프트, Context를 표시 형식으로 옮긴 자료 블록, 질문으로 이뤄진 생성 모델 입력 전체.
- **프롬프트 버전**: 시스템 프롬프트와 사용자 메시지 템플릿, Context 표시 형식을 함께 가리키는 식별자. 평가에서 수치를 비교할 때 조건으로 쓴다.

### User Story 1 - 근거가 있는 질문에 출처가 붙은 한국어 답을 받는다 (Priority: P1)

질의 경로 구현자가 질문과 검색 결과를 넘기면, 생성은 Context를 정해진 표시 형식으로 옮겨 시스템 프롬프트와 함께 생성 모델에 보내고, 받은 답변을 후처리해
답변 본문, 인용한 출처 목록, 상태, 요약을 돌려준다. 답변의 사실 문장 끝에는 그 문장을 뒷받침하는 Source ID가 있고, 출처 목록에는 인용된 Source ID마다
문서 제목 경로와 원본 링크·버전이 있다.

**Why this priority**: 로드맵 1.G 완료 조건 "출처 링크가 붙은 답변으로 갱신된다"와 constitution C-01(근거와 출처)을 만드는 핵심 경로다. QK-BOT-001이 이 결과 없이는
시작할 수 없다.

**Independent Test**: 외부 호출 없는 가짜 생성 제공자가 미리 정한 답변(유효 인용, 없는 ID 인용, 인용 없음 섞음)을 돌려주게 하고, 고정 샘플 Context로 생성한다.
생성 입력이 표시 형식대로 만들어졌는지, 결과의 본문·출처 목록·상태가 규칙대로인지 본다.

**Acceptance Scenarios**:

1. **Given** Context 묶음 S1·S2와 둘을 인용한 가짜 답변, **When** 생성한다, **Then** 상태는 "답변"이고 출처 목록에 S1·S2가 Source ID 순서로 있으며 각 항목에 제목과
   원본 링크·버전·원본 수정 시각·수집 시각이 있다.
2. **Given** Context 묶음 S1·S2·S3과 S1만 인용한 답변, **When** 생성한다, **Then** 출처 목록에는 S1만 있다. 인용되지 않은 묶음은 목록에 나오지 않는다.
3. **Given** 같은 질문·같은 Context·같은 가짜 답변, **When** 두 번 생성한다, **Then** 생성 입력과 결과가 같다.
4. **Given** 어떤 생성이든, **When** 생성 입력을 본다, **Then** 시스템 프롬프트는 승인된 프롬프트 버전의 글이고, 자료 블록은 Context 묶음 순위 순서이며, 묶음마다
   `[S번호] 제목 | 수정 YYYY-MM-DD`(수정일을 모르면 `수정 미상`) 머리줄과 발췌문, 끊긴 자리의 생략 표시, 절이 바뀌는 자리의 `(절: …)` 줄이 있다(FR-004). 질문은 자료 블록 뒤에 온다.
5. **Given** 결과 하나, **When** 요약을 본다, **Then** 프롬프트 버전, 생성 모델 식별자, 생성 설정(출력 상한, 온도, 추론 끔), 사용한 Source ID 수, 예상 입력 토큰,
   제공자가 알려 준 입력·출력 토큰과 소비 Neurons, 지연 시간이 있다. 질문 원문과 답변 본문은 요약에 없다.

### User Story 2 - 자료에 근거가 없으면 "확인할 수 없습니다"로 답한다 (Priority: P1)

검색 결과가 없거나 Context가 비었으면, 생성은 생성 모델을 부르지 않고 확인 불가 문장을 답으로 돌려준다. 모델이 근거가 없다고 판단해 확인 불가 문장만 돌려준
경우에도 상태를 "확인 불가"로 구분한다. 일부만 확인되는 답은 "답변" 상태로 두고, 확인 불가 부분은 본문에 따로 적힌다.

**Why this priority**: 로드맵 1.G 완료 조건 "자료에 없는 질문에 '확인할 수 없습니다'로 답한다"와 C-01이다. 벡터 검색에 점수 임계값이 없어 색인이 비어 있지 않으면 대개 Context가 생기므로,
실제 확인 불가 답의 대부분은 모델 판단(프롬프트 규칙 3)에서 나온다. 생성 호출 없는 경로는 결과가 없거나 Context가 빈 드문 경우를 위한 것이다(Assumptions).

**Independent Test**: 검색 상태가 "결과 없음"인 결과, Context가 빈 결과, 가짜 제공자가 확인 불가 문장만 돌려주는 경우, 확인 불가 문장과 다른 내용을 함께 돌려주는 경우를
각각 넣고 상태·본문·생성 호출 수를 본다.

**Acceptance Scenarios**:

1. **Given** 검색 상태가 "결과 없음", **When** 생성한다, **Then** 생성 모델 호출은 0회이고 본문은 확인 불가 문장 하나이며 상태는 "확인 불가", 출처 목록은 비어 있다.
2. **Given** 검색 상태는 "답변 가능"이지만 Context 묶음이 0개(예산보다 큰 청크만 있었음), **When** 생성한다, **Then** 1과 같다. 요약에 "Context 없음" 사유가 있다.
3. **Given** 가짜 답변이 앞뒤 공백만 다른 확인 불가 문장, **When** 생성한다, **Then** 상태는 "확인 불가"이고 본문은 확인 불가 문장 그대로다.
4. **Given** 가짜 답변이 유효 인용이 있는 문장과 "`○○`은 제공된 자료만으로 확인할 수 없습니다." 문장을 함께 담음, **When** 생성한다, **Then** 상태는 "답변"이다.
5. **Given** 확인 불가 문장이 아니면서 유효 인용이 하나도 남지 않은 답변, **When** 생성한다, **Then** 상태는 "답변"이고 결과에 "출처 확인 안 됨"이 표시되며 출처 목록은
   비어 있다(FR-015).

### User Story 3 - 답변의 출처 표기를 코드가 검사하고 출처 목록은 코드가 만든다 (Priority: P1)

생성 모델이 단 인용 가운데 이번 Context에 없는 Source ID는 본문에서 지우고 요약에 센다. 출처 목록은 모델 출력에서 가져오지 않고 Context의 출처 정보로 만든다.
모델이 본문에 URL이나 출처 목록을 쓰더라도 그대로 사용자에게 가지 않는다.

**Why this priority**: 스파이크에서 qwen3는 출처 표시 4/4, 문장마다 출처 2/4였다(spike-workers-ai 4절, n=5). 모델 출력만 믿으면 없는 문서를 출처로 보이거나
원본에 없는 링크가 나갈 수 있다(C-01, C-14). ADR-009 Negative 항목이 "프롬프트와 후처리로 보강"을 요구한다.

**Independent Test**: 가짜 답변에 없는 ID(`[S9]`), 여러 ID 표기(`[S1, S2]`), 인식하지 못하는 표기(`[s1]`, `(S1)`), 발췌문에 있는 URL과 없는 URL, "출처:" 목록을 섞어 넣고 결과 본문과 출처 목록, 요약 수치를 본다.

**Acceptance Scenarios**:

1. **Given** Context가 S1·S2이고 답변에 `[S9]`가 있음, **When** 생성한다, **Then** 본문에서 `[S9]`가 지워지고 요약의 "지운 인용 수"가 1이다. 출처 목록에 S9는 없다.
2. **Given** 답변에 `[S1][S2]`, `[S1, S2]`처럼 여러 ID를 붙인 표기, **When** 생성한다, **Then** 정해진 표기 규칙(FR-013)대로 각 ID를 인식하고 본문은 `[S1][S2]` 꼴로 맞춘다.
3. **Given** 답변 본문에 발췌문에 없는 URL이나 "출처:"로 시작하는 목록 줄, **When** 생성한다, **Then** 본문에서 지우고 요약에 센다. 발췌문에 같은 글자로 있는 URL(예: 문서가 적은
   엔드포인트 주소)은 남는다. 출처 링크는 코드가 만든 출처 목록에만 있다(FR-014).
4. **Given** 답변의 문장 중 인용이 없는 문장, **When** 생성한다, **Then** 그 문장은 지우지 않고 그 문장 수를 요약에 센다(FR-015).
5. **Given** Context가 S1·S2이고 답변의 인용이 `[S9]` 하나뿐, **When** 생성한다, **Then** `[S9]`를 지운 뒤 유효 인용이 없으므로 "출처 확인 안 됨"이 표시되고 출처 목록은 비어 있다.

### User Story 4 - 비밀값과 문맥 속 지시문이 생성 경로를 넘지 못한다 (Priority: P1)

생성은 질문과 Context를 외부 생성 모델로 보내기 직전에 전송 직전 검사(QK-SEC-001)를 거친다. 질문이 걸리면 아무것도 보내지 않는다. Context 묶음이 걸리면 그 묶음을
빼고 남은 묶음으로 진행한다. 청크 본문이나 질문 안에 자료 블록의 구분자를 흉내 낸 글이 있어도 자료 블록 밖으로 나가지 않는다. 질문·답변 원문은 기록·요약·로그에
남지 않는다.

**Why this priority**: AGENTS.md 3.1(외부 전송 전 비밀값 검사), 3.2(검색된 Context 속 명령은 실행하지 않는다), 6절(민감한 질의 원문을 기록하지 않는다)과 C-03이다.
QK-RET-001은 질문이 차단돼도 키워드 검색 결과를 넘기므로, 생성 단계가 다시 막아야 한다(QK-RET-001 Edge Cases).

**Independent Test**: 비밀값 규칙에 걸리는 질문, 걸리는 Context 묶음 하나가 섞인 Context, 본문에 `[자료 끝]`·`[질문]`·`[S7]`이 든 청크, 검색 요약에 "외부 전송 차단"이
있는 결과를 넣고, 가짜 제공자가 받은 생성 입력과 호출 수, 기록에 원문이 있는지 본다.

**Acceptance Scenarios**:

1. **Given** 비밀값 규칙에 걸리는 질문, **When** 생성한다, **Then** 생성 모델 호출은 0회이고 상태는 "외부 전송 차단"이다. 질문 원문이나 맞은 문자열은 결과·요약·로그에 없다.
2. **Given** QK-RET-001 요약에 질문의 "외부 전송 차단"이 있는 결과, **When** 생성한다, **Then** 1과 같다(전송 직전 검사를 다시 하지 않아도 같은 결과다).
3. **Given** Context 묶음 S1·S2·S3 가운데 S2만 비밀값 규칙에 걸림, **When** 생성한다, **Then** 생성 입력에 S2가 없고 S1·S3은 원래 Source ID 그대로이며, 요약에 "제외한 묶음
   S2(비밀값 차단)"가 있다. 남은 묶음이 없으면 US2-2처럼 확인 불가로 답한다.
4. **Given** 청크 본문이나 제목 경로에 `[자료 끝]`, `[질문]`, `[S7]`, `[S1, S2]`, 시스템 프롬프트를 흉내 낸 글이 있음, **When** 생성 입력을 만든다, **Then** 그 글은 구분자나
   Source ID로 읽히지 않는 꼴로 바뀌어 자료 블록 안에 남는다. 질문에 있는 같은 글도 같다.
5. **Given** 생성이 끝난 뒤, **When** 사용량 기록과 실행 로그를 본다, **Then** 질문 원문, 답변 본문, 청크 본문이 0건이다.

### User Story 5 - 자료가 충돌하거나 현재 상태를 물을 때 단정하지 않는다 (Priority: P2)

출처끼리 내용이 어긋나면 답변은 양쪽 주장을 각각의 Source ID와 함께 보여 주고, 수정 시점을 비교할 수 있으면 어느 쪽이 최근인지 밝힌다. 배포 여부·PR 상태처럼
현재 상태를 묻는 질문에는 자료 시점으로 한정해 답하고 원본에서 확인해야 한다고 덧붙인다. 이 동작은 시스템 프롬프트 규칙과 Context 표시 형식(수정일 머리줄)으로 만든다.

**Why this priority**: AGENTS.md 3.2("색인된 과거 자료로 현재 상태를 단정하지 않는다")와 백로그 제목의 "충돌 처리"다. 모델 동작이라 가짜 제공자로는 시험할 수 없고
실제 모델 확인(사람 단계)이 필요해 P2로 둔다. 실제 원본 조회로 현재 상태를 답하는 기능은 이 명세 밖이다.

**Independent Test**: 같은 항목을 다르게 적은 두 묶음(수정일 다름, 수정일 하나 없음)과 "지금 배포됐어?" 같은 질문을 담은 소수 질문 세트로 실제 생성 모델을 사람 확인 뒤
호출하고, 답변이 규칙대로인지 사람이 읽어 판정한다.

**Acceptance Scenarios**:

1. **Given** S1(수정 2026-10-10)은 "재시도 3회", S2(수정 2026-10-18)는 "재시도 5회", **When** 재시도 횟수를 묻는다, **Then** 답변에 두 값이 각각 `[S1]`·`[S2]`와 함께 있고
   S2가 더 최근이라고 하며, 한쪽을 실제 적용 값으로 단정하지 않는다.
2. **Given** 배포를 기록한 묶음 하나, **When** "지금 운영에 배포돼 있어?"를 묻는다, **Then** 답변은 "자료 기준(수정 날짜)으로는"으로 한정하고 "현재 상태는 원본에서
   확인해야 합니다."를 덧붙인다.
3. **Given** 수정일이 없는 묶음, **When** Context를 표시한다, **Then** 머리줄에 `수정 미상`이 있고, 2와 같은 질문의 답에 "수정 시점 미상"이 쓰인다.

### User Story 6 - 생성 사용량을 기록하고 실패를 구분해 돌려준다 (Priority: P2)

생성 모델 호출마다 사용량(시각, 용도, 모델, 입력·출력 토큰, 소비 Neurons, 측정·추정 구분, 결과 종류)을 기록하고, 하루 사용량에 임베딩과 함께 합산한다. 질의응답
예비분을 넘어도 질문을 막지 않고 경고를 남긴다. 제공자 실패는 종류별로 구분하고, 일시 실패는 한 번만 다시 시도한다. 출력 상한에 걸려 잘린 답변은 표시해 돌려준다.

**Why this priority**: C-05(일일 예산 안에서 쓰고 질의응답을 색인보다 우선), ADR-009 비용 가정 확인, QK-EMB-001이 남긴 "생성 사용량 기록 방식은 QK-GEN-001이 맞춘다"
(QK-EMB-001 Assumptions)다. 답변 자체가 아니라 운영 장치라 P2다.

**Independent Test**: 가짜 제공자가 호출마다 정해진 토큰·Neurons를 알려 주거나 알려 주지 않게 하고, 일시 실패·할당 소진·인증 오류·잘못된 응답·시간 초과·출력 잘림을
주입한다. 기록 행, 하루 합계, 재시도 횟수, 결과 상태를 본다.

**Acceptance Scenarios**:

1. **Given** 제공자가 소비 Neurons를 알려 준 호출, **When** 생성한다, **Then** 기록에 그 값이 "측정"으로 남고, 그날 질의응답 사용량 합계에 임베딩과 함께 더해진다.
2. **Given** 제공자가 값을 알려 주지 않은 호출, **When** 생성한다, **Then** 설정의 단가와 토큰 수로 추정하고 "추정"으로 표시한다.
3. **Given** 그날 질의응답 사용량이 예비분을 넘은 상태, **When** 생성한다, **Then** 생성은 그대로 하고 경고를 기록한다.
4. **Given** 첫 호출이 일시 실패, **When** 생성한다, **Then** 한 번만 다시 시도하고, 두 번째도 실패하면 "생성 일시 실패"로 돌려준다. 시도마다 기록이 남는다.
5. **Given** 제공자가 할당 소진·인증 오류·잘못된 응답을 알림, **When** 생성한다, **Then** 다시 시도하지 않고 각각의 실패 종류로 돌려준다. 호출자는 제공자 고유 오류를 보지 않는다.
6. **Given** 출력 상한에 걸려 끝난 답변, **When** 생성한다, **Then** 후처리를 거친 본문을 돌려주고 결과에 "출력 잘림"을 표시한다.

### User Story 7 - 운영 담당자가 명령으로 질문부터 답변까지 확인한다 (Priority: P3)

운영 담당자와 개발자는 Discord 없이 명령 하나로 질문을 검색하고 답변을 생성해, 답변 본문·출처 목록·상태·요약(검색 요약 포함)을 본다. 질문은 표준 입력으로 받는다.
외부 생성 모델을 부르는 실행은 명시적으로 고를 때만 하고, 기본은 가짜 제공자다.

**Why this priority**: 실제 모델 확인(US5, SC-008)과 QK-BOT-001 이전의 점검 수단이다. 운영 경로가 아니라 P3다.

**Independent Test**: 로컬 데이터베이스에 샘플을 넣고 가짜 제공자로 명령을 실행해 결과가 나오는지, 질문 원문이 명령행 인자·로그 파일에 남지 않는지, 실제 제공자 실행에
명시적 선택이 필요한지 본다.

**Acceptance Scenarios**:

1. **Given** 색인된 로컬 데이터베이스, **When** 질문을 표준 입력으로 넣어 명령을 실행한다, **Then** 답변 본문, 출처 목록, 상태, 생성 요약과 검색 요약이 나온다.
2. **Given** 실제 제공자를 고르지 않은 실행, **When** 명령을 실행한다, **Then** 외부 생성 호출은 0회이고 출력에 "가짜 제공자"가 표시된다.
3. **Given** 생성 실패, **When** 명령을 실행한다, **Then** 실패 종류를 알리고 0이 아닌 종료 코드로 끝난다.

---

### Edge Cases

- 검색이 실패 상태(빈 질문, 질문 길이 초과, 활성 인덱스 없음, 저장소 사용 불가, 인덱스 버전 바뀜, 두 검색 모두 실패 등)일 때: 생성 모델을 부르지 않고 검색 실패 종류를
  그대로 실어 "검색 실패"로 돌려준다. 확인 불가 문장으로 바꾸지 않는다. 사용자 안내 문구는 QK-BOT-001이 정한다.
- 하이브리드 검색이 한쪽 검색을 생략하고 결과를 낸 때: 남은 결과로 생성하고, 생략 사유는 검색 요약에 그대로 남는다.
- 모델 출력에 추론 블록(`<think>…</think>`)이 있을 때: 블록을 지우고 남은 글로 후처리한다. 블록 안에 글이 있었으면 요약에 "추론 출력 감지"를 남긴다(추론 끔 설정이 지켜지지
  않았다는 신호). 닫히지 않은 `<think>`(출력 잘림 등)는 그 위치부터 끝까지 지운다.
- 모델 출력이 비었거나 추론 블록만 있을 때: "잘못된 응답"으로 돌려준다. 확인 불가 문장으로 바꾸지 않는다.
- 모델이 확인 불가 문장 앞뒤에 따옴표나 출처를 붙였거나, 끝 마침표를 빠뜨렸거나, 같은 문장을 되풀이했을 때: FR-009의 판정 규칙으로 "확인 불가"로 본다.
- 답변의 모든 문장이 "`○○`은 제공된 자료만으로 확인할 수 없습니다." 꼴(프롬프트 규칙 4)이거나 확인 불가 문장과 "현재 상태는 원본에서 확인해야 합니다."뿐일 때: 사실 문장이
  없으므로 "확인 불가"로 보고 본문은 그대로 두되 인용은 지우고 출처 목록은 비운다(FR-009 (나)).
- 인용이 마침표 뒤에 붙었을 때(`…잡는다. [S3]`, 스파이크 부록 B에서 관찰): 인용만으로 된 조각은 앞 문장의 인용으로 본다(FR-015).
- 질문이 영어이거나 코드가 섞였을 때: 같은 규칙으로 처리한다. 답은 한국어다(프롬프트 규칙 8).
- 인사·잡담이나 팀 자료와 무관한 일반 질문일 때: 다른 질문과 똑같이 처리해 대개 확인 불가로 답한다(FR-017).
- 같은 문서가 Context에 두 번 나오는 일은 없다(QK-RET-001 FR-013 문서당 묶음 하나). 서로 다른 문서가 같은 내용을 담으면 각자 별도 출처다.
- 생성 입력 예상 토큰이 한도를 넘을 때: 기본 설정은 설정 검사가 막지만, 검색 요청별 덮어쓰기(QK-RET-001 `overrides`로 Context 예산·질문 길이 상한을 최대 8,000까지)로는 생길 수
  있다. 호출 직전에 실제 생성 입력으로 다시 재고(FR-019), 넘으면 호출하지 않고 "입력 한도 초과"로 돌려준다.
- 사용량 기록 쓰기가 실패할 때: 답변은 그대로 돌려주고 결과와 요약에 "사용량 기록 실패"를 표시하며 경고를 남긴다(FR-020). 기록 실패 때문에 답변을 버리지 않는다.
- 생성 중 활성 인덱스 버전이 바뀌거나 문서가 내려졌을 때: 생성은 받은 Context만 쓰고 저장소를 다시 읽지 않는다. 출처 링크는 Context에 실린 원본 링크·버전 그대로다.

## Requirements *(mandatory)*

### Functional Requirements

**생성 경계와 입력 (US1)**

- **FR-001**: 질문과 QK-RET-001 검색 결과(상태, Context, 요약)를 받아 생성 결과(상태, 답변 본문, 출처 목록, 생성 요약)를 돌려주는 생성 경계를 제공한다.
  생성 경계는 생성 모델 제공자와 사용량 기록 저장소를 경계(인터페이스) 뒤에서만 쓴다. 로컬 서버, Workers, 확인 명령이 같은 생성 함수를 부른다(C-06).
- **FR-002**: 생성 결과 상태는 답변, 확인 불가, 검색 실패, 외부 전송 차단, 생성 실패로 구분한다. 생성 실패는 일시 실패, 제공자 할당 소진, 인증·설정 오류, 잘못된 응답,
  시간 초과, 입력 한도 초과로 나눈다. 호출자는 제공자 고유의 오류를 보지 않는다.
- **FR-003**: 생성 입력은 시스템 프롬프트, 자료 블록, 질문 순서다. 시스템 프롬프트와 사용자 메시지 템플릿의 기본값은 2026-10-23 승인된 후보 1(`TASK.md` "승인된 입력"의
  "시스템 프롬프트 후보 1"과 "사용자 메시지 템플릿")이다. 템플릿은 자료 블록을 `[자료 시작]`과 `[자료 끝]` 사이에, 질문을 `[질문]` 아래에 두고, 시스템 프롬프트의 "[자료]"는
  이 두 표시 사이의 글을 가리킨다. 표기를 맞추려고 프롬프트나 템플릿 글을 바꾸면 새 프롬프트 버전이 되고 사람 승인을 받는다.
- **FR-004**: 자료 블록은 Context 묶음을 순위 순서로 옮긴다. 묶음마다 머리줄 `[S번호] 제목 | 수정 YYYY-MM-DD` 뒤에 발췌문이 온다.
  - 제목은 묶음 첫 청크의 제목 경로를 ` > `로 이은 것이다. 제목 경로가 비면(첫 제목 앞 머리말 청크) 청크 위치의 경로를, 그것도 없으면 `제목 없음`을 쓴다. 문서 제목은
    Context에 따로 없으므로 제목 경로를 그대로 쓴다(승인 프롬프트의 "문서 제목 > 절 제목"은 이 값을 가리킨다).
  - 수정일은 원본 수정 시각을 한국 시간(UTC+9) 날짜로 쓰고, 없으면 `수정 미상`이다. 팀이 한국 시간으로 일하므로 UTC 날짜로 하루 이르게 보이지 않게 한다.
  - 묶음 안 끊긴 자리에는 `…(중간 생략)…` 줄을 둔다. QK-RET-001 묶음 텍스트의 생략 표시(`(…)`)는 쓰지 않고 이 규칙으로 다시 만든다.
  - 묶음 안에서 제목 경로가 바뀌는 청크 앞에는 `(절: 제목 경로)` 줄을 둔다. 이 줄은 `[`로 시작하지 않아 머리줄과 헷갈리지 않는다(QK-RET-001 FR-014가 넘긴 표시 형식).
- **FR-005**: 프롬프트 버전 식별자는 시스템 프롬프트, 사용자 메시지 템플릿, 자료 블록 표시 규칙에서 결정적으로 정해진다. 셋 중 하나라도 바뀌면 식별자가 바뀐다.
  기준 프롬프트(spike-workers-ai 부록 B)도 비교용 프롬프트 버전으로 고를 수 있다. 기본값은 후보 1이다.
- **FR-006**: 같은 질문·같은 검색 결과·같은 프롬프트 버전이면 생성 입력이 바이트 단위로 같다.

**확인 불가 (US2)**

- **FR-007**: 검색 상태가 "결과 없음"이거나 Context 묶음이 0개면(FR-010으로 모두 빠진 경우 포함) 생성 모델을 부르지 않고, 본문이 확인 불가 문장 하나인 "확인 불가" 결과를
  돌려준다. 요약에 사유(결과 없음, Context 없음, 모든 묶음 차단)를 남긴다.
- **FR-008**: 검색 상태가 실패 종류면 생성 모델을 부르지 않고 "검색 실패"와 검색 실패 종류를 돌려준다. 단, 검색 실패 종류가 외부 전송 차단(벡터 전용 요청에서 질문이 막힌 경우)이면
  FR-010의 "외부 전송 차단"이 앞선다. 판정 순서는 외부 전송 차단 → 검색 실패 → 결과 없음·빈 Context(FR-007)다.
- **FR-009**: 확인 불가 판정은 FR-014의 후처리 순서 가운데 인용 정리 뒤에 한다. 본문에서 인용 표기(인식하지 못한 꼴 포함), 따옴표, 앞뒤 공백을 걷어 내고 FR-014의 문장 경계로
  나눈 뒤,
  (가) 모든 문장이 확인 불가 문장(끝 마침표가 없어도 같다고 본다)이면 상태는 "확인 불가", 본문은 확인 불가 문장 하나다.
  (나) 모든 문장이 "제공된 자료만으로 확인할 수 없습니다."로 끝나는 문장(끝 마침표가 없어도 같다)이거나 "현재 상태는 원본에서 확인해야 합니다."이면 상태는 "확인 불가"다. 본문은
  그 문장들 그대로 두되 인용 표기는 지우고, 출처 목록은 비운다(US2-1과 같다).
  (다) 그 밖에 사실 문장이 하나라도 있으면 상태는 "답변"이다.
  Phase 1은 검색 점수 임계값으로 확인 불가를 판단하지 않는다(Assumptions).

**보안과 기록 (US4)**

- **FR-010**: 생성 모델로 보내기 직전에 질문과 Context 묶음을 QK-SEC-001 전송 직전 검사에 각각 따로 넣는다. 검사하는 글은 실제로 보낼 꼴이다: 질문은 FR-011로 바꾼 뒤의 질문,
  묶음은 FR-004·FR-011로 만든 묶음 글(머리줄, `(절: …)` 줄, 발췌문 포함)이다. 질문은 출처 없이 예외 없이 검사한다. Context 묶음도 출처 없이(오탐 예외를 적용하지 않고)
  검사한다. Context에 묶음의 자료원 이름이 없기 때문이다. 그래서 오탐 예외로 색인된 문서도 생성 단계에서는 걸려 빠질 수 있다. 걸린 묶음이 예외 대상 문서인지 색인 뒤 규칙이
  늘어나 걸린 것인지는 출처 없이 가를 수 없으므로, 요약에는 "출처 없이 검사해 뺀 묶음 수"를 규칙 이름별로 남기고 어느 쪽인지는 사람이 기록을 보고 판단한다
  (2026-10-23 사용자 결정. 등록된 예외가 생기면 다시 검토한다, Assumptions).
  질문이 걸리거나 검색 결과에 질문의 외부 전송 차단이 있으면 아무것도 보내지 않고 "외부 전송 차단"을 돌려준다. 묶음이 걸리면 그 묶음을 빼고, 통과한 묶음만으로 생성 입력을
  새로 만들어 다시 검사하지 않고 보낸다. 다른 묶음의 Source ID는 바꾸지 않으며, 뺀 묶음과 사유(규칙 이름)를 요약에 남긴다. 결과·요약·로그에 걸린 본문이나 맞은 문자열을 담지 않는다.
  QK-SEC-001 계약("걸린 조각이 하나라도 있으면 그 요청 전체를 보내지 않는다")은 묶음 하나를 검사 요청 하나로 보고 지킨다. 걸린 묶음은 어떤 요청에도 실리지 않는다(Assumptions).
- **FR-011**: 생성 입력을 만들 때 청크 본문, 제목 경로, 청크 위치, 질문 안의 자료 블록 구분자(`[자료 시작]`, `[자료 끝]`, `[질문]`)와 인용으로 읽힐 수 있는 꼴(대괄호 안에
  `S숫자`가 있는 모든 글, 예: `[S7]`, `[S1, S2]`)을 구분자·인용으로 읽히지 않는 꼴로 바꾼다. 머리줄 구분 글자(` | `)가 제목에 있으면 함께 바꾼다. 바꾼 횟수는 요약에 남긴다.
  사용자에게 돌려주는 출처 목록과 Context 원문은 바꾸지 않는다.
- **FR-012**: 질문 원문, 답변 본문, 청크 본문, 생성 입력 전체를 사용량 기록, 요약, 실행 로그, 오류 메시지에 남기지 않는다(ADR-016, AGENTS.md 6절). 질의 로그와 원문 저장은
  QK-OBS-001 몫이다.

**출처 표시 후처리 (US3)**

- **FR-013**: 인용 표기 규칙: 대괄호 안에 `S` + 0으로 시작하지 않는 숫자가 하나 이상, 쉼표(반각·전각)나 공백으로 나뉘어 있으면 인용이다. `[S1]`, `[ S1 ]`, `[S1, S2]`,
  `[S1，S2]`, `[S1][S2]`를 인식하고 본문은 `[S1][S2]` 꼴로 맞추며, 같은 문장 안 같은 ID가 겹치면 하나로 줄인다. 범위 표기(`[S1-S3]`, `[S1~S3]`), 0으로 시작하는 번호(`[S01]`),
  소문자·다른 괄호(`[s1]`, `(S1)`, `【S1】`)는 인용으로 인식하지 않고 그대로 두며 요약에 "인식하지 못한 인용 꼴" 수를 센다. 코드 표기(`` ` `` 또는 코드 블록) 안의 글은 인용으로
  보지 않고 바꾸지 않는다.
- **FR-014**: 문장 경계: 마침표·물음표·느낌표 뒤에 공백이나 줄 끝이 올 때와 줄바꿈에서 나눈다. 숫자·파일 이름 안의 점(`5.5`, `a.py`)과 코드 표기 안은 경계로 보지 않는다.
  인용만으로 된 조각(`…잡는다. [S3]`)은 앞 문장의 인용으로 보고, 인용을 걷어 낸 뒤 빈 조각은 버린다. FR-009·FR-013·FR-015가 모두 이 경계를 쓴다.
  후처리 순서는 (1) 추론 블록 제거 → (2) 출처 목록 줄 제거 → (3) URL 정리 → (4) 인용 인식·정규화(FR-013) → (5) 생성 입력에 없는 ID 제거 → (6) 확인 불가 판정(FR-009) →
  (7) 유효 인용 확인과 인용 없는 문장 세기(FR-015) → (8) 출처 목록 작성(FR-016)이다.
  - 출처 목록 줄: 줄 머리가 `출처`, `참고`, `Sources`, `Source`, `References` 다음에 콜론(`:`, `：`)이 오는 줄과 그 바로 아래 목록 줄(`-`, `*`, 숫자 + 마침표로 시작)을 지운다.
    "참고로 …"처럼 콜론이 없는 문장은 지우지 않는다.
  - URL: 코드 표기 밖의 URL은 이번 생성 입력의 발췌문에 같은 글자로 있으면 남기고, 없으면 지운다. 코드 표기 안의 URL은 건드리지 않는다. 지운 URL 수를 센다.
  - 없는 ID: 이번 생성 입력에 없는 Source ID(FR-010으로 빠진 묶음 포함)는 지우고 "지운 인용 수"를 센다. `[S1, S9]`는 정규화 뒤 S9만 지운다.
- **FR-015**: 확인 불가가 아닌 답변에서 FR-014를 거친 뒤 유효 인용이 하나도 남지 않으면, 본문을 그대로 내보내되 상태는 "답변"으로 두고 결과에 "출처 확인 안 됨"을 표시하며
  출처 목록은 비운다(2026-10-23 사용자 결정. AGENTS.md 3.2와의 충돌을 알고 유지했다, Assumptions). 확인 불가 문장으로 바꾸거나 실패로 돌리지 않는다. 사용자에게 어떻게 알릴지는 QK-BOT-001이 정한다.
  인용이 없는 문장이 일부 섞인 답변은 그대로 두고 요약에 "인용 없는 문장 수"를 센다. 문장은 FR-014의 경계로 나누고, FR-009 (나)에 해당하는 문장은 사실 문장으로 세지 않는다.
- **FR-016**: 출처 목록은 본문에 남은 유효 인용의 Source ID를 번호 순서로, 한 번씩 담는다. 항목은 Source ID, 묶음 제목(FR-004), 원본 링크, 원본 버전, 원본 수정 시각,
  수집 시각이다(constitution C-02: 색인을 근거로 쓸 때는 수집 시각을 함께 보여 준다).
  출처 목록은 Context에서 만들고 모델 출력에서 가져오지 않는다. 화면 표시 형식(링크 꼴, 분할)은 QK-BOT-001이 정한다.

**질문 범위 (Edge Cases)**

- **FR-017**: 인사·잡담이나 팀 자료와 무관한 일반 질문(예: 일반 프로그래밍 방법)을 가려내는 판별을 두지 않는다. 다른 질문과 같은 경로로 처리하며, 검색 결과가 없으면 FR-007,
  있으면 프롬프트 규칙 1·3에 따라 확인 불가로 답하게 된다. 일반 지식 답이나 별도 안내 문구는 두지 않는다(2026-10-23 사용자 결정, C-01). 질문 분류는 QK-TRK-001 몫이다.

**생성 Provider와 설정 (US6)**

- **FR-018**: 생성 모델 기본값은 Workers AI `@cf/qwen/qwen3-30b-a3b-fp8`이다(ADR-009). 추론 끔(`/no_think`를 사용자 메시지 끝에 붙임)은 qwen3 계열 모델의 규칙이고, 코드가
  고정으로 적용하며 설정으로 끄지 않는다. 다른 계열 모델로 바꾸는 것은 이 명세의 설정 변경이 아니라 ADR-009 개정(결정 기록)과 그 모델의 추론 끔 규칙 정의가 필요하다.
  온도 초기값 0.2, 출력 상한 초기값 800토큰이다.
- **FR-019**: 입력 한도 검사는 두 번 한다. (1) 설정 검사: 기본 설정으로 (시스템 프롬프트 + 템플릿 고정 문구 + 질문 길이 상한 + Context 토큰 예산)의 예상 토큰에 과소 추정 배율을
  곱한 값과(질문 길이 상한은 글자 수이므로 한 글자를 UTF-8 최대 4바이트로 보고 바이트로 바꾼다) 출력 상한의 합이 모델 컨텍스트 창(32,768)을 넘으면 실패한다. (2) 호출 직전 검사: 실제로 만든 생성 입력의 예상 토큰에 배율을 곱한 값과 출력 상한의 합이 창을 넘으면
  호출하지 않고 "입력 한도 초과"로 돌려준다(검색 요청별 덮어쓰기 대비). 예상 토큰은 QK-RET-001과 같은 방식(UTF-8 바이트 ÷ 설정값)이고, 과소 추정 배율 초기값은 2.0이다
  (QK-RET-001 research R-08 실측 최대 1.875). 배율은 입력에만 곱하고 출력 상한은 그대로 더한다.
- **FR-020**: 생성 모델 호출 시도마다 시각, 용도("생성"), 실행 식별자, 모델 식별자, 프롬프트 버전, 입력·출력 토큰, 소비 Neurons, 측정·추정 구분, 결과 종류를 기록한다.
  소비 Neurons는 제공자가 알려 준 값을 쓴다. 없으면 제공자가 알려 준 입력·출력 토큰과 설정 단가로 계산하고, 토큰도 없으면(시간 초과 등) 예상 입력 토큰과 출력 상한으로 추정한다.
  뒤의 둘은 추정임을 표시한다(QK-EMB-001 FR-013·FR-014와 같은 규칙). 결과를 받지 못한 시도도 과금됐을 수 있으므로 추정값으로 기록한다. 기록 보관과 하루 합계는 QK-EMB-001
  FR-025와 같다. 기록 쓰기가 실패하면 답변은 그대로 돌려주고 "사용량 기록 실패"를 결과와 요약에 표시하며 경고를 남긴다.
- **FR-021**: 생성 사용량은 질의용 임베딩과 함께 그날의 질의응답 사용량으로 합산한다. 합계가 질의응답 예비분(초기값 3,000)을 넘어도 생성을 막지 않고 경고를 기록한다(C-05,
  QK-EMB-001 FR-019). 생성 사용량은 색인 예산 판정(QK-EMB-001 FR-018, 그날 색인 사용량만 센다)에 들어가지 않는다. 색인 판정에 생성을 넣으려면 QK-EMB-001 변경으로 따로 승인받는다.
- **FR-022**: 일시 실패(제공자 일시 오류, 시간 초과)는 1회까지 다시 시도한다. 할당 소진, 인증·설정 오류, 잘못된 응답, 입력 한도 초과는 다시 시도하지 않는다. 호출 시간 제한
  초기값은 20초이고, 다시 시도까지 포함한 생성 전체 시간 상한은 계획 단계에서 QK-BOT-001 응답 시간에 맞춰 정한다.
- **FR-023**: 제공자가 출력 상한에 걸려 끝났다고 알리거나, 종료 사유를 알려 주지 않을 때 출력 토큰이 출력 상한과 같으면 후처리한 본문과 함께 "출력 잘림"을 결과에 표시한다.
- **FR-024**: 생성 단계의 외부 호출(생성 모델 호출, 사용량 기록 쓰기)은 질의 하나에 상한(초기값 4: 생성 2(재시도 1회 포함) + 사용량 기록 2) 안이다. 검색 단계(QK-RET-001 FR-026,
  상한 7)와 합친 질의 하나의 외부 호출 상한은 11이다(ADR-008 Workers subrequest 한도). 요약에는 생성 단계와 질의 전체의 실제 호출 수를 각각 남긴다.
- **FR-025**: 생성 모델 식별자, 온도, 출력 상한, 시간 제한, 프롬프트 버전, 과소 추정 배율, 입력·출력 단가는 설정으로 바꿀 수 있고 설정 검사가 범위를 벗어난 값을 거부한다.
  가짜 제공자를 둬 기본 검증은 외부 호출 0건으로 돈다.

**요약과 확인 명령 (US1, US7)**

- **FR-026**: 생성 요약은 상태, 프롬프트 버전, 모델 식별자, 생성 설정, 자료 블록에 넣은 Source ID 수와 뺀 묶음·사유, 예상 입력 토큰, 제공자 입력·출력 토큰, 소비 Neurons와
  측정·추정 구분, 시도 횟수, 지연 시간, 지운 인용 수, 인식하지 못한 인용 꼴 수, 인용 없는 문장 수, 지운 URL·출처 줄 수, 구분자 바꾼 횟수, 추론 출력 감지, 출력 잘림,
  출처 확인 안 됨, 사용량 기록 실패, 생성 단계와 질의 전체의 실제 외부 호출 수를 담는다. 질문 원문·답변 본문·청크 본문은 담지 않는다.
- **FR-027**: 질문을 표준 입력으로 받아 검색(QK-RET-001)과 생성을 이어 실행하고 답변 본문·출처 목록·상태·생성 요약·검색 요약을 보여 주는 확인 명령을 제공한다. 기본은 가짜
  제공자이고, 실제 생성 모델은 명시적 선택이 있을 때만 부른다. 실패하면 0이 아닌 종료 코드로 끝난다. 질문 원문을 명령행 인자나 파일로 남기지 않는다.

### Key Entities

- **생성 요청(Generation Request)**: 질문, QK-RET-001 검색 결과, 프롬프트 버전(기본 후보 1).
- **생성 입력(Generation Input)**: 시스템 프롬프트, 자료 블록, 질문(추론 끔 표기 포함). 예상 입력 토큰. 원문은 저장하지 않는다.
- **자료 블록 항목(Rendered Block)**: Source ID, 머리줄(제목 경로·수정일), 구분자를 바꾼 발췌문, 생략 표시.
- **생성 결과(Generation Result)**: 상태, 답변 본문(후처리 뒤), 출처 목록, 표시(출처 확인 안 됨, 출력 잘림, 사용량 기록 실패), 생성 요약, 검색 요약(QK-RET-001 그대로).
- **출처 항목(Citation)**: Source ID, 제목, 원본 링크, 원본 버전, 원본 수정 시각, 수집 시각.
- **생성 요약(Generation Summary)**: FR-026의 항목.
- **생성 사용량 기록(Generation Usage)**: FR-020의 항목. 질의응답 사용량 하루 합계에 들어간다.
- **프롬프트 버전(Prompt Version)**: 시스템 프롬프트·템플릿·표시 규칙에서 정해지는 식별자. 후보 1(기본), 기준(비교용).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 가짜 제공자로 유효 인용·없는 ID·여러 ID 표기·인식 못 하는 표기·URL·출처 줄을 섞은 고정 시험 전부에서, 결과 본문과 출처 목록에 남은 Source ID가 모두 이번 생성
  입력에 있고(위반 0건), 출처 목록의 링크가 모두 Context의 원본 링크와 같으며, 요약 수치가 기대값과 같다. 유효 인용이 남지 않은 답변 시험은 모두 "출처 확인 안 됨" 표시와
  빈 출처 목록이다. 발췌문에 없는 URL은 모두 지워지고, 발췌문에 같은 글자로 있는 URL은 모두 남는다.
- **SC-002**: 검색 "결과 없음", 빈 Context, 모든 묶음 차단, 검색 실패 상태 시험 전부에서 생성 모델 호출이 0회이고, 앞의 셋은 본문이 확인 불가 문장과 글자 그대로 같으며, 검색 실패는
  "검색 실패"와 원래 실패 종류로 나온다.
- **SC-003**: 비밀값 규칙에 걸리는 질문·Context 묶음 시험 전부에서 걸린 질문이나 묶음이 생성 제공자로 나간 사례가 0건이고, 걸린 묶음을 뺀 뒤 남은 Source ID가 바뀐 사례가 0건이다.
- **SC-004**: 구분자·인용 꼴 글(`[S7]`, `[S1, S2]` 포함)과 머리줄 구분 글자를 청크 본문·제목 경로·청크 위치·질문에 심은 시험 전부에서, 생성 입력 안의 구분자가 템플릿 위치 말고는
  0개이고, FR-013이 인용으로 인식하는 꼴이 각 머리줄의 `[S번호]` 말고는 0개다.
- **SC-005**: 모든 생성 호출 시험에서 사용자 메시지가 추론 끔 표기로 끝나고(100%), 추론 블록이 든 가짜 응답의 본문에 추론 블록이 남은 사례가 0건이다.
- **SC-006**: 생성 경로 시험 전부(실패 주입 포함)에서 사용량 기록·요약·로그·오류 메시지에 질문 원문, 답변 본문, 청크 본문이 든 사례가 0건이다.
- **SC-007**: 일시 실패 뒤 재시도 성공·재시도 실패, 할당 소진, 인증 오류, 잘못된 응답, 시간 초과, 출력 잘림을 주입한 시험 전부에서 재시도는 일시 실패에만 1회 이하이고, 생성 단계 외부
  호출 수가 상한(초기값 4) 이하이며, 시도마다 사용량 기록이 하나씩 남고, 하루 질의응답 합계가 임베딩과 생성을 함께 센다.
- **SC-008**: 사람 확인 뒤 실제 생성 모델로 질문 세트(spike-ko-v0 생성 질문 5개 + 충돌·현재 상태·일부만 답 가능·지시문 주입·무관 질문을 더한 10~12개)를 후보 1과 기준
  프롬프트로 각 1회 실행해 기록한다. 자료는 색인하지 않은 고정 합성 Context를 생성 경계에 직접 넣으므로 임베딩 호출은 0건이다. 후보 1에서 근거 없는 질문(무관 질문 포함)의
  확인 불가 판정 100%, 문맥 속 지시문을 따른 답 0건이다. 모델 자체의 인용 품질은 후처리 전 값(지운 인용 수, 인식하지 못한 인용 꼴 수, 인용 없는 문장 수)으로 보고, 문장마다
  인용 비율·충돌 처리·현재 상태 한정 문구 준수와 지연(p50·p95)·소비 Neurons를 두 프롬프트로 함께 기록한다. 질문 수, 모델, 프롬프트 버전, 날짜를 붙인다(C-13). 판정은 사람 검토로
  확정한다. 전체 답변 평가는 QK-EVL-002 몫이다.
- **SC-009**: 설정 검사 시험에서 FR-019 (1) 합계가 모델 컨텍스트 창을 넘는 설정은 모두 거부되고 기본 설정은 통과한다. 검색 요청별 덮어쓰기로 Context 예산과 질문 길이를 최대로 올린
  시험에서 창을 넘는 생성 입력은 모두 호출 없이 "입력 한도 초과"로 끝난다(FR-019 (2)).
- **SC-010**: 같은 입력으로 두 번 생성한 시험 전부에서 생성 입력과 결과(가짜 제공자) 차이가 0건이고, 프롬프트·템플릿·표시 규칙 중 하나만 바꾼 시험에서 프롬프트 버전 식별자가 모두 바뀐다.

- Context 생략·제목 경로 표시 형식: FR-004.
- 프롬프트 몫: 시스템 프롬프트 후보 1은 약 640토큰, 템플릿 고정 문구 약 20토큰이다(2026-10-23, Qwen2.5 토크나이저 근사. qwen3 토크나이저로는 재지 않았다). 질문이 수백 자 안이면

- "확인할 수 없습니다" 판단에 쓸 검색별 원래 점수: Phase 1은 점수 임계값을 두지 않는다. RRF 점수는 절대 관련도가 아니고(QK-RET-001 Assumptions), 검색 점수만으로 정한 임계값을
  검증할 라벨이 아직 없다. 확인 불가는 Context 유무와 모델 판단(프롬프트 규칙 3)으로 정하고, 임계값은 QK-EVL-001·002 결과를 보고 다시 정한다.
- 질문이 전송 차단됐을 때: FR-010. 키워드 결과가 있어도 질문을 보내지 않으므로 생성은 하지 않는다.
- 생성 호출 없는 확인 불가 경로(FR-007)는 드물다. 벡터 검색에 점수 임계값이 없어 색인이 비어 있지 않으면 하이브리드 검색은 대개 결과를 내고, Context는 대개 비지 않는다.
  그래서 인사·무관 질문(FR-017)을 포함한 대부분의 질문이 생성 호출을 하고, 로드맵 1.G의 "확인할 수 없습니다"는 주로 모델 판단(프롬프트 규칙 3)에서 나온다. 이 비용은 아래
  "비용"에 질문 수 그대로 넣었다. 무관 질문 비율이 높으면 QK-TRK-001(질문 분류)에서 생성 전에 거르는 것을 검토한다.

**QK-SEC-001 계약의 해석**

- QK-SEC-001은 "걸린 조각이 하나라도 있으면 그 요청 전체를 보내지 않는다"고 정한다. 이 명세는 질문과 Context 묶음을 각각 별도 검사 요청으로 보고, 걸린 묶음은 어떤 생성 요청에도
  싣지 않으며 통과한 조각만으로 생성 요청을 새로 만든다(FR-010). 걸린 조각이 외부로 나가지 않는다는 계약의 목적은 그대로 지킨다. 질문이 걸리면 질문 없이는 생성할 수 없으므로
  요청 전체를 보내지 않는다.
- 2026-10-23 기준 `config/security_exceptions.toml`에 등록된 오탐 예외는 0건이다. 색인 단계(QK-SEC-001 FR-011)에서 비밀값이 걸린 문서는 색인되지 않으므로, 생성 단계에서 걸리는
  묶음은 예외로 색인된 문서이거나 색인 뒤 비밀값 규칙이 늘어난 경우다. Context 묶음을 출처 없이 검사하므로(FR-010, 2026-10-23 사용자 결정) 예외로 색인된 문서는 생성 단계에서
  늘 빠진다. 지금은 해당 문서가 0건이다. 첫 예외를 등록할 때 이 결정을 다시 보고, 필요하면 QK-RET-001 Context에 자료원 이름·경로를 더하는 변경을 따로 올린다.

**FR-015와 AGENTS.md 3.2**

- AGENTS.md 3.2는 "팀의 정책, 구현, 상태에 대한 답변에는 Source ID를 단다. 근거가 없으면 확인할 수 없다고 답한다"이고 도구별 문서보다 우선한다. FR-015는 유효 인용이 없는 답변도
  내보내므로 이 규칙과 부딪힌다. 사용자가 이 충돌을 알고 유지하기로 했다(2026-10-23, 독립 검토 M6).
- 보완: 그런 답변은 "출처 확인 안 됨" 표시와 빈 출처 목록으로 나가 사용자가 근거 없는 답임을 알 수 있다(QK-BOT-001이 표시). 프롬프트 규칙 1·3은 그대로라 모델은 근거가 없으면
  확인 불가로 답하도록 지시받는다. 표시가 붙은 답의 비율은 SC-008과 QK-EVL-002에서 재고, 높으면 FR-015를 확인 불가로 바꾸는 결정을 다시 한다.
- AGENTS.md를 고치는 것은 이 작업 범위가 아니다(TASK.md 제외 범위).

**프롬프트와 모델 동작**

- 충돌 처리, 현재 상태 한정, 일부만 답하기, 문맥 속 지시문 무시는 모델 동작이라 가짜 제공자 시험으로 확인할 수 없다. 코드가 보장하는 것은 프롬프트에 규칙이 있고, Context
  머리줄에 수정일이 있으며, 구분자를 흉내 낸 글이 자료 블록 밖으로 나가지 않는다는 데까지다. 모델이 규칙을 지키는지는 SC-008(사람 단계)과 QK-EVL-002로 본다.
- 후보 1과 기준 프롬프트의 실측 비교는 SC-008에서 한다. 후보 1이 기준보다 나쁘면 기본값을 기준으로 돌리는 결정을 사람이 한다.
- 현재 상태를 원본 API로 조회해 답하는 기능(AGENTS.md 3.2)은 이 명세 밖이다. 이 명세는 과거 기록으로 단정하지 않게 하는 데까지 한다.
- 스파이크에서 qwen3는 `/no_think`를 붙이면 추론 블록이 없었다(5/5). 빈 추론 블록이 출력 앞에 붙는 경우를 대비해 지우는 규칙만 둔다.

**비용**

- qwen3 단가(입력 1M 토큰당 4,625, 출력 30,475 Neurons, spike-workers-ai 3.2절)로 입력 3,000·출력 800이면 생성 1회 약 38 Neurons다. 하루 50건이면 약 1,900이고 질의 임베딩을
  합쳐도 질의응답 예비분(3,000) 안이다.
- 출력 상한을 800으로 두어, 출력 1,200을 가정한 ADR-009·QK-RET-001 spec·TASK.md의 질의당 약 51 Neurons보다 낮다. 그 문서들의 값은 상한 쪽 가정으로 둔다.
- 나쁜 경우(p95 기준): 실제 Context가 예상의 1.3배(QK-RET-001 R-08 p95 1.286)이고 질문이 상한 길이면 입력 약 4,800토큰, 생성 1회 약 47 Neurons다. 모든 질문이 일시 실패로
  재시도까지 하면 하루 50건에 약 4,700으로 예비분을 넘는다. 예비분은 막지 않고 경고만 남기므로(FR-021) 초과분 약 1,700은 하루 무료 할당 여유분(2,000)에서 쓴다.
- 최악(R-08 최대 1.875배): 입력 약 5,950토큰, 생성 1회 약 52 Neurons, 재시도 포함 하루 50건 약 5,200으로 예비분 + 여유분(5,000)을 조금 넘는다. 이때는 색인 예산 몫까지 쓰게
  되고, 제공자 할당이 소진되면 그날 남은 생성은 "제공자 할당 소진"으로 실패한다. 모든 질문이 최대 길이·최대 배율·재시도인 경우라 드물다고 보고, 실측(SC-008)과 운영 사용량으로 다시 본다.
- 이 명세의 기본 검증은 가짜 제공자로 0 Neurons다. SC-008 실측은 질문 최대 12개 × 프롬프트 2개 × 1회 × 약 38로 약 920 Neurons이고, 고정 Context를 쓰므로 임베딩은 0이다. 실행 전
  예상량을 보고하고 사람 확인을 받는다(AGENTS.md 3.5).

**범위**

- Discord 명령·지연 응답·답변 분할·표시 형식(QK-BOT-001), 질문 분류·필터 추론(QK-TRK-001), 질의 재작성·스레드 문맥(QK-BOT-002), 답변 평가·판정 모델(QK-EVL-002),
  질의 로그·피드백·원문 저장(QK-OBS-001), 검색 동작 변경(QK-RET-001), Workers 배포는 이 명세 밖이다.
- 스트리밍 응답은 두지 않는다. QK-BOT-001은 처리 중 응답 뒤 완성된 답변으로 한 번 갱신한다(로드맵 1.G).
- 생성 사용량을 기존 임베딩 사용량 기록과 같은 저장 구조에 둘지(이름 일반화 포함), 별도 구조에 두고 합계만 함께 볼지는 계획 단계에서 정한다(QK-EMB-001 plan "다른 명세에 넘기는 것").
  어느 쪽이든 기존 기록 행과 하루 합계 값은 바뀌지 않아야 한다.
- 질의 하나의 전체 시간과 Workers 한도(요청당 CPU, subrequest) 측정은 QK-BOT-001에서 한다.

**환경**

- 질의응답은 Cloudflare Workers에서 실행한다(ADR-008). 생성 모델 호출은 Workers AI 바인딩이나 HTTP API로 할 수 있고, 어느 방식을 쓸지는 계획 단계에서 정한다.
  소비 Neurons는 HTTP API 응답 헤더로 받는 것이 스파이크에서 확인됐다(spike-workers-ai 3.2). 바인딩 경로에서 Neurons·토큰·종료 사유를 받을 수 있는지는 확인하지 않았다.
  받지 못하면 FR-020·FR-023의 대체 규칙(토큰 × 단가, 출력 토큰 = 상한이면 잘림)을 쓴다.
- ADR-009는 Proposed 상태다. 이 명세는 ADR-009의 결정을 따르고, 승인은 이 작업의 PR 리뷰에서 받는다.
- Cloudflare는 Workers AI 입력·출력을 학습에 쓰지 않는다고 밝힌다(ADR-009 Data and cost). 새 외부 모델이나 자료원은 더하지 않는다.
