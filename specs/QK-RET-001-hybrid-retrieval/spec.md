## Clarifications

### Session 2026-10-22

- Q: ADR-010 후보 중 어떤 규칙을 이 명세에서 운영 색인 기본값으로 적용하나? → A: 색인 쪽 후보(기준선, 식별자 분해)를 모두 구현하되 운영 기본값은
  기준선으로 둔다. 질의 쪽 규칙(문장 → 낱말 하나만 맞아도 후보가 되는 검색어)은 바로 적용한다. 운영 색인 규칙 변경은 QK-EVL-001 비교와 ADR-010 확정 뒤에
  한다(FR-018, FR-020).
- Q: (독립 검토 H1) 기준선이 활성인 DB에는 다른 인덱스 버전을 활성화할 수 없다. 식별자 분해 후보의 평가용 색인은 어디에 만드나? → A: 후보 규칙마다 별도 로컬
  데이터베이스를 만들고 원본 데이터베이스의 임베딩 캐시를 복사해 시작한다. 재임베딩 0 Neurons, 운영 변경 없음. 이 명세가 준비 절차를, QK-EVL-001이 비교를 맡는다(FR-029).
- Q: (H2) 질의당 외부 호출 상한과 재시도는? → A: 사용량 기록 쓰기까지 세어 상한 6. 인덱스 버전이 바뀌면 다시 검색하지 않고 실패로 돌려준다. 질의용 임베딩 재시도는
  1회까지다(FR-006, FR-026). 재검토(N1)에서 사용량 기록이 시도마다 쓰인다는 것이 확인돼 상한을 7로 고쳤다(2026-10-22 사용자 결정).
- Q: (재검토 N3) 규칙 차이와 자료 차이가 섞이지 않게 하려면? → A: 기준선을 포함한 모든 후보를 같은 원본 리비전으로 새 평가용 데이터베이스에 만들고, 그 리비전을
  결과 조건으로 기록한다(FR-029).
- Q: (M1) 문맥 확장에서 상위 절을 어떻게 붙이나? → A: 가장 가까운 상위 절, 곧 중심 청크가 속한 절의 첫 청크 하나만 붙인다. 순서 번호와 제목 경로를 돌려주는
  주변 청크 일괄 조회를 새로 둔다(FR-012, FR-014).
- Q: (M5) 토큰 예산은? → A: Context 몫으로 두고 초기값을 2,000(예상 토큰)으로 낮춘다. 프롬프트 몫 약 1,000과 합쳐 ADR-009의 입력 3,000에 맞춘다(FR-016).

## User Scenarios & Testing *(mandatory)*

이 명세의 사용자는 검색 결과로 답변을 만드는 후속 명세 구현자(QK-GEN-001 생성, QK-BOT-001 Discord), 검색 방식을 비교하는 평가 구현자
(QK-EVL-001), 색인 결과를 확인하는 운영 담당자, PR 리뷰어다. 최종 사용자(Discord에서 질문하는 팀원)는 이 명세의 결과를 직접 보지 않지만,
답변의 근거가 되는 자료가 무엇이고 어디서 왔는지는 여기서 정해진다.

용어:

- **후보**: 벡터 검색이나 키워드 검색이 돌려준 청크 하나.
- **통합 순위**: 두 검색의 후보를 RRF(Reciprocal Rank Fusion)로 합친 순위. 후보마다 각 검색에서의 순위를 바탕으로 점수를 매긴다.
- **문맥 묶음**: Context에 담긴 청크 중 같은 문서의 청크를 원문 순서로 모은 텍스트 한 덩어리. 문서 하나에 묶음 하나다. 통합 상위 청크(중심 청크)와 그 앞뒤 청크,
  상위 절 첫 청크로 이뤄진다.
- **상위 절 첫 청크**: 중심 청크와 제목 경로가 같고 원문 순서가 중심 청크까지 끊기지 않고 이어지는 청크들 가운데 첫 청크. 중심 청크가 절의 첫 청크면 없다.
- **Context**: 이번 질의에서 생성(QK-GEN-001)에 넘기는 문맥 묶음 목록. 토큰 예산 안에 든다.
- **키워드 검색 텍스트 규칙**: 청크의 키워드 검색용 텍스트를 만드는 색인 쪽 규칙과, 질문을 키워드 검색어로 바꾸는 질의 쪽 규칙(ADR-010).

### User Story 1 - 질문 하나로 벡터 검색과 키워드 검색을 합친 결과를 받는다 (Priority: P1)

생성 구현자가 질문 문장과 선택 필터(자료원 종류, 자료 종류)를 넘기면, 검색은 질문을 질의용으로 임베딩해 벡터 검색을 하고, 같은 질문으로
키워드 검색을 한 뒤, 두 결과를 통합 순위로 합쳐 돌려준다. 두 검색 중 한쪽에만 나온 청크도 통합 결과에 남는다. 같은 질문과 같은 색인이면
결과 순서가 항상 같다.

**Why this priority**: 질의 트랙(QK-GEN-001, QK-BOT-001)과 평가(QK-EVL-001)가 모두 이 결과 없이는 시작할 수 없다. 의미 검색은 표현이 다른
질문에 강하고, 키워드 검색은 함수명·경로 같은 식별자에 강하다(ADR-007 관찰). 둘을 합쳐야 두 유형의 질문을 함께 다룬다.

**Independent Test**: 외부 호출 없는 가짜 임베딩 제공자와 고정 샘플 청크를 넣은 로컬 데이터베이스로, 벡터 쪽에만 걸리는 청크·키워드 쪽에만
걸리는 청크·양쪽에 걸리는 청크가 있는 질문을 실행한다. 통합 순위가 RRF 계산과 같은지, 세 종류 청크가 모두 결과에 있는지, 같은 질문을 두 번
실행한 결과가 같은지 본다.

**Acceptance Scenarios**:

1. **Given** 벡터 검색 순위 1위인 청크 A와 키워드 검색 순위 1위인 청크 B가 서로 다른 상태, **When** 검색한다, **Then** A와 B가 모두 결과에 있고
   통합 점수는 각 검색 순위로 계산한 RRF 값과 같다.
2. **Given** 두 검색 모두에 나온 청크 C, **When** 검색한다, **Then** C는 결과에 한 번만 나오고 두 검색의 순위가 함께 기록된다.
3. **Given** 통합 점수가 같은 두 청크, **When** 같은 질문으로 두 번 검색한다, **Then** 두 번 모두 같은 순서다(동점 처리 규칙이 정해져 있다).
4. **Given** 자료원 필터(예: 저장소 문서만), **When** 검색한다, **Then** 두 검색 모두 같은 필터를 쓰고 다른 자료원 청크는 결과에 없다.
5. **Given** 결과 한 건, **When** 내용을 본다, **Then** 청크 식별자, 통합 순위와 점수, 각 검색의 순위와 원래 점수(없으면 없음), 출처 정보(원본 링크·
   버전·위치·제목 경로·원본 수정 시각·수집 시각)가 함께 온다.

### User Story 2 - 노출하면 안 되는 청크는 결과에도 문맥에도 들어가지 않는다 (Priority: P1)

접근 범위를 확인할 수 없는 청크, 비활성 인덱스 버전의 청크, 삭제되거나 내린 문서의 청크는 통합 결과에도, 문맥 확장으로 붙는 앞뒤 청크와
상위 절에도 들어가지 않는다. 검색 도중 활성 인덱스 버전이 바뀌어도 한 질의의 결과는 한 인덱스 버전의 청크로만 이뤄진다.

**Why this priority**: 1.G 완료 조건 "접근 범위를 확인할 수 없는 샘플 문서가 검색되지 않는다"와 C-14를 질의 경로 끝까지 지킨다. QK-STO-001은
검색 질의 안에서 거르지만, 이 명세가 더하는 통합·문맥 확장 단계에서 새로 섞여 들어오는 길이 없어야 한다.

**Independent Test**: 접근 범위 미확인·제한, 비활성 인덱스 버전, 삭제·내림 상태의 청크를 질문과 가깝게 섞어 넣고, 그 청크의 앞뒤에 노출 가능한
청크를 둔다. 검색 결과와 Context에 노출하면 안 되는 청크가 0건인지 본다.

**Acceptance Scenarios**:

1. **Given** 질문과 가장 가까운 청크가 접근 범위 "미확인"인 상태, **When** 검색한다, **Then** 그 청크는 통합 결과와 Context 어디에도 없다.
2. **Given** 노출 가능한 청크 바로 앞뒤에 같은 문서의 비활성 인덱스 버전 청크가 있는 상태, **When** 문맥을 확장한다, **Then** 활성 버전 청크만 붙는다.
3. **Given** 통합 결과를 받은 직후 그 문서가 내려진 상태, **When** 문맥을 확장한다, **Then** 그 문서의 청크는 Context에 들어가지 않는다.
4. **Given** 벡터 검색과 키워드 검색(또는 주변 청크 조회) 사이에 활성 인덱스 버전이 바뀐 상태, **When** 결과를 합친다, **Then** 합치지 않고 다시 검색하지도 않으며
   "인덱스 버전 바뀜" 실패로 돌려준다. 서로 다른 버전의 청크가 한 결과에 섞이지 않는다.

### User Story 3 - 상위 결과에 앞뒤 문맥을 붙여 생성용 문맥 묶음을 만든다 (Priority: P1)

검색은 통합 순위 상위 청크마다 같은 문서의 앞뒤 청크와 상위 절 첫 청크를 붙인다. Context에 담긴 청크는 문서별로 원문 순서대로 모아 문맥 묶음 하나로 만들고,
같은 청크는 Context에 한 번만 들어간다. 문맥 묶음마다 답변이 출처로 쓸 식별자(Source ID)와 출처 정보가 붙는다.

**Why this priority**: QK-CHK-002는 청크가 겹치지 않게 나누고 앞뒤 문맥을 검색 단계에 맡겼다(FR-009). 청크 하나만 넘기면 절 제목이나 표 머리글,
앞 문단의 조건을 잃는다. 출처 식별자는 C-01과 AGENTS.md 3.2(답변에 Source ID를 단다)를 지키는 바탕이다.

**Independent Test**: 한 문서에 연속된 청크 1~9가 있고 통합 상위에 청크 2·3과 8이 있는 샘플로 검색한다. 그 문서의 청크가 묶음 하나에 원문 순서로 모이는지,
끊긴 자리(4~6)가 표시되는지, 중복 청크가 없는지, 묶음마다 Source ID와 출처 정보가 있는지 본다.

**Acceptance Scenarios**:

1. **Given** 통합 상위 청크 하나, **When** 문맥을 확장한다, **Then** 같은 문서·같은 인덱스 버전의 앞 청크와 뒤 청크(기본 각 1개)와 상위 절 첫 청크가
   원문 순서대로 붙는다.
2. **Given** 같은 문서의 청크 2·3과 8이 통합 상위에 있는 상태, **When** 문맥을 확장한다, **Then** 그 문서의 묶음은 하나이고 청크는 원문 순서이며 각 청크는 한 번만
   들어간다. 순서가 끊긴 자리에는 생략 표시가 있다.
3. **Given** 문서의 첫 청크나 마지막 청크, **When** 문맥을 확장한다, **Then** 없는 쪽은 비워 두고 오류를 내지 않는다.
4. **Given** 같은 제목 경로가 문서 안에 두 번 나오는 경우(QK-CHK-002 알려진 한계), **When** 상위 절을 찾는다, **Then** 중심 청크 쪽 절의 첫 청크만 붙고
   앞쪽의 같은 이름 절 청크는 붙지 않는다(상위 절 첫 청크 정의: 순서가 끊기지 않는 범위).
5. **Given** Context의 문맥 묶음 하나, **When** 내용을 본다, **Then** Source ID, 문서 단위 출처 정보(원본 링크·버전·원본 수정 시각·수집 시각), 청크마다
   위치·제목 경로, 묶음의 중심 청크들과 그 순위, 묶음에 든 청크 식별자 목록이 있다.

### User Story 4 - Context를 정해진 토큰 예산 안에 담는다 (Priority: P1)

검색은 청크를 정해진 순서로 Context에 담되, 전체 예상 토큰이 Context 토큰 예산(초기값 2,000)을 넘지 않게 한다. 청크는 중간에서 자르지 않는다.
중심 청크를 통합 순위 순서로 먼저 담고, 남은 예산으로 앞뒤 문맥을 붙인다. 들어가지 않는 청크는 건너뛰고, 무엇을 건너뛰었는지 결과 요약에 남는다.

**Why this priority**: 생성 모델(ADR-009 qwen3-30b-a3b)의 컨텍스트는 32,768토큰이고, ADR-009의 비용 계산은 프롬프트를 포함한 질의당 입력 3,000토큰을 가정한다.
하루 질의응답 예비분(QK-EMB-001: 3,000 Neurons)을 지키려면 Context 크기에 상한이 있어야 한다(C-05). 청크 상한은 예상 2,800토큰이라(QK-CHK-002)
청크 하나가 예산보다 클 수 있어 담는 규칙이 필요하다.

**Independent Test**: 예상 토큰을 아는 샘플 청크로 예산을 작게 둔 검색을 실행한다. Context 합계가 예산 이하인지, 잘린 청크가 없는지, 빼는 순서가
규칙대로인지, 요약의 사용 토큰과 건너뛴 항목이 맞는지 본다.

**Acceptance Scenarios**:

1. **Given** 문맥 묶음 합계가 예산 이하, **When** Context를 만든다, **Then** 모든 묶음이 통합 순위 순서로 들어가고 요약에 사용 토큰과 예산이 나온다.
2. **Given** 합계가 예산을 넘는 상태, **When** Context를 만든다, **Then** FR-016의 순서대로 담는다. 중심 청크가 모두 담긴 뒤에야 앞뒤 문맥이 붙고, 들어가지 않는
   청크는 그 청크만 건너뛰고 다음 항목을 계속 본다. 잘린 청크는 없다.
3. **Given** 통합 1위 청크 하나만으로 예산을 넘는 상태, **When** Context를 만든다, **Then** 그 청크는 건너뛰고 "예산보다 큰 청크"로 요약에 남기며,
   다음 순위부터 예산 안에서 담는다.
4. **Given** 같은 질문·같은 색인·같은 예산, **When** 두 번 실행한다, **Then** Context가 같다.

### User Story 5 - 자연어 질문과 코드 식별자로도 키워드 검색이 맞는다 (Priority: P2)

팀원은 "결제 취소 API 경로가 뭐야?"처럼 문장으로 묻거나 `retry`처럼 식별자 일부로 묻는다. 검색은 질문을 키워드 검색어로 바꾸는 질의 쪽 규칙과,
청크의 키워드 검색용 텍스트를 만드는 색인 쪽 규칙(ADR-010 후보)을 둔다. 질문의 모든 낱말이 한 청크에 있어야만 찾는 방식이 아니어야 하고,
`retryPayment`, `payment_status`, `/payments/{id}/cancel` 같은 식별자는 원형으로도 구성 낱말로도 찾을 수 있어야 한다.

**Why this priority**: QK-STO-001의 키워드 검색은 검색어를 그대로 받으므로 문장 전체를 넣으면 거의 맞지 않는다. ADR-007 스파이크에서 `retry`가
`retryPayment`를 찾지 못했고, QK-SYN-001 첫 색인에서 `에러 코드`가 `docs/error-codes.md`를 찾지 못했다(RISK-05). 1.G는 ADR-010 확정을 요구한다.
다만 US1~4만으로도 의미 검색으로 답할 수 있어 P2로 둔다.

**Independent Test**: 식별자(camelCase, snake_case, kebab-case, URL 경로 각 5개 이상)와 한국어 낱말이 든 샘플 청크를 규칙 후보마다 별도로 색인한 로컬
데이터베이스(FR-029)에서, 원형 식별자·식별자 일부·문장형 질문으로 키워드 검색만 실행해 해당 청크가 상위 20건 안에 드는지 본다.

**Acceptance Scenarios**:

1. **Given** 본문에 `retryPayment`가 있는 청크, **When** `retry`로 키워드 검색한다, **Then** 식별자 분해 후보 규칙에서는 그 청크가 결과에 나온다.
2. **Given** 같은 청크, **When** `retryPayment` 원형으로 검색한다, **Then** 모든 후보 규칙에서 그 청크가 결과에 나온다(QK-STO-001 SC-007 유지).
3. **Given** 본문에 "결제 취소"가 있는 청크, **When** "결제 취소 API 경로가 뭐야?"로 검색한다, **Then** 질의 쪽 규칙이 문장을 검색어로 바꿔 그 청크가 결과에 나온다.
4. **Given** 키워드 검색 문법 특수 문자(따옴표, 괄호, 연산자)가 든 질문, **When** 검색한다, **Then** 문법 오류 없이 처리된다.
5. **Given** 후보 규칙마다 별도 로컬 데이터베이스에 만든 색인, **When** 같은 질문 세트로 검색한다, **Then** 결과에 그 색인의 색인 쪽 규칙 식별자와 인덱스 버전이 붙어
   규칙별로 비교할 수 있다.
6. **Given** 이 명세가 병합된 운영 색인, **When** 색인 쪽 규칙을 본다, **Then** 기준선 규칙이고 인덱스 버전은 바뀌지 않았다. 질의 쪽 규칙은 바로 적용돼 있다.
   식별자 분해 후보는 평가용 색인에서만 쓰이고, 운영 기본값 변경은 ADR-010 확정 뒤에 한다. 기준선 설정의 청킹 규칙 버전 값도 이 명세 전과 같다.
7. **Given** 운영 데이터베이스에서 기준선 규칙으로 색인한 상태, **When** 식별자 분해 후보의 평가용 데이터베이스를 준비한다, **Then** 새 로컬 데이터베이스에 임베딩 캐시가
   복사되고, 그 후보로 색인하는 동안 임베딩 외부 호출이 0건이며, 운영 데이터베이스에는 쓰기가 없다.

### User Story 6 - 평가를 위해 검색 방식별 결과를 따로 받는다 (Priority: P2)

평가 구현자(QK-EVL-001)는 같은 질문으로 벡터 검색만, 키워드 검색만, 하이브리드 결과를 각각 받아 Recall@5와 MRR을 비교한다. 검색 방식, 후보 수,
RRF 상수, 질의 쪽 키워드 규칙은 요청마다 바꿀 수 있다. 색인 쪽 규칙은 검색하는 데이터베이스의 활성 인덱스 버전이 정한다. 결과에 이 조건과 인덱스 버전이 함께 남는다.
단일 방식 요청은 실패해도 다른 방식으로 바꾸지 않는다.

**Why this priority**: 1.G 완료 조건 "첫 검색 평가 리포트(Recall@5, MRR, 벡터·키워드·하이브리드 비교)"와 C-13(수치에는 조건을 붙인다)을 위한 장치다.
평가 실행기 자체는 QK-EVL-001 몫이라 P2로 둔다.

**Independent Test**: 같은 질문을 세 방식으로 실행해, 벡터 전용 결과가 벡터 검색 순위와 같고 키워드 전용 결과가 키워드 검색 순위와 같으며 하이브리드
결과가 US1과 같은지 본다. 각 결과에 조건이 기록되는지 본다.

**Acceptance Scenarios**:

1. **Given** 같은 질문, **When** 벡터 전용으로 검색한다, **Then** 키워드 검색은 실행되지 않고 결과는 벡터 검색 순위와 같다. 질의용 임베딩이 실패하거나 전송 차단되면
   키워드 결과로 바꾸지 않고 실패로 돌려준다.
2. **Given** 같은 질문, **When** 키워드 전용으로 검색한다, **Then** 질의 임베딩을 부르지 않고(사용량 0) 결과는 키워드 검색 순위와 같다.
3. **Given** 어떤 방식의 결과든, **When** 내용을 본다, **Then** 검색 방식, 후보 수, RRF 상수, 질의 쪽 규칙, 색인 쪽 규칙, 인덱스 버전, 토큰 예산이 함께 있다.
4. **Given** 평가가 Context 없이 순위만 필요한 경우, **When** 요청한다, **Then** 문맥 확장과 Context 만들기를 건너뛰고 통합 순위만 받을 수 있다.

### User Story 7 - 운영 담당자가 명령으로 검색 결과를 확인한다 (Priority: P3)

운영 담당자와 개발자는 생성이나 Discord 없이 명령 하나로 질문을 검색해, 통합 순위·출처·Context 요약(묶음 수, 사용 토큰, 건너뛴 항목)을 본다.
질문은 표준 입력으로 받아 셸 기록이나 CI 로그의 명령행에 남지 않게 한다.

**Why this priority**: 첫 색인 뒤 "왜 이 문서가 안 나오나"를 확인할 수단이 지금은 없다(QK-SYN-001 관찰을 손으로 확인했다). Discord 경로(QK-BOT-001)가
생기기 전에도 검색을 점검할 수 있게 한다. 운영 경로가 아니라 P3다.

**Independent Test**: 로컬 데이터베이스에 샘플을 넣고 명령을 실행해 순위·출처·요약이 나오는지, 질문 원문이 명령행 인자·사용량 기록·로그 파일에 남지 않는지 본다.

**Acceptance Scenarios**:

1. **Given** 색인된 로컬 데이터베이스, **When** 질문으로 명령을 실행한다, **Then** 통합 순위, 각 검색 순위, 출처 링크, Context 요약이 나온다.
2. **Given** 활성 인덱스가 없는 데이터베이스, **When** 명령을 실행한다, **Then** "활성 인덱스 없음"을 알리고 0이 아닌 종료 코드로 끝난다.
3. **Given** 명령 실행 뒤, **When** 사용량 기록을 본다, **Then** 질의용 임베딩 1건이 기록되고 질문 원문은 없다(QK-EMB-001 FR-013).

---

### Edge Cases

- 질문이 비었거나 공백뿐일 때: 외부 호출과 저장소 질의 없이 "빈 질문"으로 거부한다.
- 질문이 질문 길이 상한(초기값 2,000자)을 넘을 때: 외부 호출 없이 "질문 길이 초과"로 거부한다. 자르지 않는다.
- 질의용 임베딩이 실패할 때(일시 실패, 제공자 할당 소진, 입력 한도 초과): 하이브리드 요청이면 키워드 검색만으로 결과를 만들고 "벡터 검색 생략"과 사유를 결과에 남긴다.
  벡터 전용 요청이면 실패로 돌려준다. 일시 실패 재시도는 1회까지다. 질의용 임베딩은 색인 예산 소진과 관계없이 처리된다(QK-EMB-001 FR-019).
- 전송 직전 검사(QK-SEC-001 `check_outgoing`)가 질문을 비밀값으로 막을 때: 질문을 외부로 보내지 않는다. 키워드 검색만으로 결과를 만들고 "외부 전송 차단"을
  결과에 남긴다(하이브리드 요청만. 벡터 전용이면 실패). 생성 단계에서 질문을 어떻게 다룰지는 QK-GEN-001이 정한다.
- 키워드 검색이 실패할 때(저장소 오류): 하이브리드 요청이면 벡터 결과만으로 만들고 "키워드 검색 생략"을 남긴다. 키워드 전용 요청이면 실패로 돌려준다.
  두 검색이 모두 실패하면 결과 없이 실패 종류를 돌려준다.
- 저장소를 쓸 수 없을 때: "저장소 사용 불가"로 구분해 돌려준다. 사용자 안내는 QK-BOT-001이 정한다.
- 활성 인덱스 버전이 없을 때: 빈 결과와 "활성 인덱스 없음"을 함께 돌려준다. 빈 목록만 주지 않는다.
- 두 검색 결과가 모두 비었을 때: 빈 Context와 "결과 없음"을 돌려준다. "확인할 수 없습니다" 답변은 QK-GEN-001이 만든다.
- 질문이 영어·한국어·코드가 섞였을 때: 같은 규칙으로 처리한다. 언어 판별로 검색 방식을 바꾸지 않는다.
- 같은 내용의 청크가 서로 다른 문서에 있을 때: 각자 별도 결과다. 출처를 합치지 않는다.
- 상위 결과가 모두 한 문서에서 나올 때: 이 명세는 문서당 개수를 제한하지 않는다. 문서별 묶음(US3)으로 중복만 없앤다. 다양성 제한은 평가 결과를 보고 정한다.
- 문맥 확장 대상 청크가 결과를 받은 뒤 바뀌었을 때(동기화와 동시 실행): 확장 시점의 활성·노출 가능 청크만 쓴다. 교체 중인 문서는 QK-STO-001 FR-012에 따라 이전 묶음만 보인다.

## Requirements *(mandatory)*

### Functional Requirements

**하이브리드 검색과 통합 순위 (US1, US2)**

- **FR-001**: 질문 문장, 선택 필터(자료원 종류, 자료 종류), 검색 조건(검색 방식, 후보 수, RRF 상수, 질의 쪽 키워드 규칙, 토큰 예산, Context 필요 여부)을 받아
  통합 결과와 Context를 돌려주는 검색 경계를 제공한다. 검색 조건을 주지 않으면 설정의 기본값을 쓴다. 색인 쪽 규칙은 검색 조건이 아니다. 검색하는 데이터베이스의
  활성 인덱스 버전이 정한다(FR-020).
- **FR-002**: 하이브리드 방식은 질문을 QK-EMB-001 경계로 질의용 임베딩해 벡터 검색(QK-STO-001 FR-006)을 하고, 질의 쪽 키워드 규칙(FR-017)으로 만든
  검색어로 키워드 검색(QK-STO-001 FR-007)을 한다. 두 검색의 후보 수 기본값은 각각 20이다.
- **FR-003**: 통합 점수는 RRF로 계산한다. 청크의 통합 점수는 그 청크가 나온 각 검색에서 `1 / (k + 순위)`를 더한 값이고, RRF 상수 `k`의 기본값은 60이다.
  한쪽 검색에만 나온 청크는 그 검색 몫만 더한다.
- **FR-004**: 통합 순위의 동점은 (벡터 검색 순위, 키워드 검색 순위, 청크 식별자) 순서로 가른다. 없는 순위는 가장 뒤로 본다. 같은 입력이면 순서가 항상 같다.
- **FR-005**: 결과 한 건은 청크 식별자, 통합 순위와 점수, 검색별 순위와 원래 점수(나오지 않았으면 없음), 출처 정보(QK-STO-001 FR-009)를 담는다.
- **FR-006**: 두 검색 결과와 주변 청크 조회의 활성 인덱스 버전이 하나라도 다르면 합치지 않는다. 다시 검색하지 않고 "인덱스 버전 바뀜" 실패로 돌려준다.
- **FR-007**: 노출 조건(활성 인덱스 버전, 팀 공용으로 확인된 접근 범위, 활성 상태 자료)은 QK-STO-001 검색 질의와 주변 청크 조회가 판정한다. 이 명세는 그
  조건을 거치지 않은 청크를 결과나 Context에 넣는 경로를 두지 않는다(C-14). 저장소 질의 결과를 다른 조건으로 넓히는 캐시나 별도 조회를 두지 않는다.
- **FR-008**: 질문 원문을 저장하지 않는다. 사용량 기록과 실행 로그에도 남기지 않는다(ADR-016, QK-EMB-001 FR-013). 질의 로그는 QK-OBS-001 몫이다.

**실패와 축소 동작 (Edge Cases)**

- **FR-009**: 빈 질문과 질문 길이 상한(초기값 2,000자)을 넘는 질문은 외부 호출과 저장소 질의 없이 거부한다.
- **FR-010**: 축소 동작은 하이브리드 방식에만 적용한다. 질의용 임베딩이 실패하거나 전송 직전 검사에 막히면 키워드 검색만으로 결과를 만들고, 생략한 검색과 사유
  (일시 실패, 제공자 할당 소진, 입력 한도 초과, 외부 전송 차단)를 결과에 남긴다. 키워드 검색이 실패하면 벡터 결과만으로 만들고 같은 방식으로 남긴다. 벡터 전용·
  키워드 전용 방식에서는 다른 방식으로 바꾸지 않고 실패로 돌려준다. 질의용 임베딩의 일시 실패 재시도는 1회까지다.
- **FR-011**: 실패 종류는 빈 질문, 질문 길이 초과, 활성 인덱스 없음, 저장소 사용 불가, 인덱스 버전 바뀜, 질의 임베딩 실패, 외부 전송 차단, 키워드 검색 실패,
  두 검색 모두 실패로 구분한다. 호출한 쪽은 저장소 제품이나 임베딩 제공자 고유의 오류를 보지 않는다(C-06).

**문맥 확장 (US3)**

- **FR-012**: 통합 순위 상위 청크(기본 상위 8개, 중심 청크)마다 같은 문서·같은 인덱스 버전의 앞 청크와 뒤 청크(기본 각 1개)와 상위 절 첫 청크를 붙일 후보로 가져온다.
  주변 청크는 중심 청크 전체에 대해 저장소 질의 한 번으로 가져오고(FR-026), 결과에는 청크마다 같은 자료 안 순서 번호와 제목 경로가 있다. 이 일괄 조회는
  QK-STO-001 FR-008·FR-011과 같은 노출 조건을 질의 안에서 적용하는 새 저장소 질의다. 이 조회는 중심 청크도 다시 확인해 돌려준다. Context에 담는 중심 청크는
  이 조회가 돌려준 청크만이다. 빠진 중심 청크(결과를 받은 뒤 내려진 문서 등)는 확장하지도 담지도 않고, 요약에 사유(노출 조건 불통과)를 남긴다.
- **FR-013**: Context에 담긴 청크는 문서별로 모아 문서 하나에 문맥 묶음 하나를 만든다. 묶음 안 청크는 원문 순서(순서 번호)이고, 순서가 끊긴 자리에는 생략 표시를 둔다.
  각 청크는 Context 전체에서 한 번만 들어간다. 묶음의 순위는 그 안 중심 청크의 가장 높은 통합 순위이고, Context는 묶음을 이 순위 순서로 놓는다.
- **FR-014**: 상위 절 첫 청크는 중심 청크와 제목 경로가 같고 순서 번호가 중심 청크까지 끊기지 않고 이어지는 청크들 가운데 첫 청크다. 중심 청크가 그 범위의 첫 청크면
  붙이지 않는다. 같은 제목 경로가 문서 안 다른 곳에 또 나와도 그 청크는 붙지 않는다. 바깥 수준의 상위 절 청크는 붙이지 않는다. 바깥 절 이름은 FR-015의 청크별
  제목 경로로 전달되고, 생성 입력에 어떻게 보일지는 QK-GEN-001이 정한다(검색 헤더는 청크 본문에 들어가지 않는다, QK-CHK-002 FR-019).
- **FR-015**: 문맥 묶음마다 Source ID를 붙인다. Source ID는 한 질의 결과 안에서 묶음을 가리키는 짧은 식별자이고, 같은 질의·같은 색인이면 같다. 묶음은 Source ID,
  문서 단위 출처 정보(원본 링크·원본 버전·원본 수정 시각·수집 시각), 청크마다 위치·제목 경로·순서 번호, 중심 청크들과 그 통합 순위, 청크 식별자 목록을 담는다.
  답변에서의 출처 표시 형식은 QK-GEN-001이 정한다.

**토큰 예산 (US4)**

- **FR-016**: Context의 예상 토큰 합계는 Context 토큰 예산(초기값 2,000)을 넘지 않는다. 예산은 Context 몫이고 프롬프트와 출력 몫은 들어 있지 않다. 예상 토큰 계산은
  QK-EMB-001 미리 보기와 같은 방식(UTF-8 바이트 ÷ 설정값)을 쓴다. 청크는 자르지 않는다. 담는 알고리즘은 다음과 같다.
  (1) 주변 청크 일괄 조회가 다시 확인해 돌려준 중심 청크(FR-012)를 통합 순위 순서로 하나씩 본다. 청크 하나가 예산보다 크면 "예산보다 큰 청크", 남은 예산보다 크면 "예산 부족"으로 건너뛰고 다음 청크를 계속 본다.
  (2) (1)에서 담은 중심 청크를 다시 통합 순위 순서로 하나씩 보며, 각 중심 청크에 대해 상위 절 첫 청크 → 앞 청크(가까운 것부터) → 뒤 청크(가까운 것부터) 순서로
  후보를 본다. 이미 Context에 있는 청크는 건너뛰고, 남은 예산보다 큰 청크는 "예산 부족"으로 건너뛰고 다음 후보를 계속 본다.
  (3) 담은 청크로 FR-013의 문맥 묶음을 만든다. 담지 못한 청크는 청크 식별자와 사유를 요약에 남긴다. 같은 입력이면 같은 Context다.
  설정 검사는 예산을 1 이상 8,000 이하로 제한한다. 8,000은 생성 모델 컨텍스트(ADR-009: 32,768)에서 출력·프롬프트 몫과 예상 토큰 과소 추정(최대 2.3배, QK-CHK-002
  research R-03)을 감안한 임시 상한이고, QK-GEN-001이 프롬프트 몫을 정하면 다시 정한다.

**키워드 검색 텍스트 규칙 (US5, ADR-010)**

- **FR-017**: 질의 쪽 규칙은 질문 문장을 키워드 검색어로 바꾼다. 질의 쪽 규칙은 요청마다 고를 수 있고 운영 기본값은 이 명세의 규칙이다. 낱말 하나만 맞아도 후보가 되게 하고(모든 낱말이 맞아야 하는 방식이 아니다), 문장 부호와
  검색 문법 특수 문자는 글자 그대로 다루며, 식별자는 원형을 남긴다. 낱말이 많이 맞을수록 순위가 높아야 한다.
- **FR-018**: 색인 쪽 규칙 후보는 최소 두 가지다. 기준선은 QK-CHK-002 FR-020의 청커 기본값(검색 헤더 + 청크 본문)이다. 식별자 분해 후보는 기준선에 더해
  camelCase·PascalCase, snake_case, kebab-case 식별자와 URL·파일 경로의 구성 낱말을 덧붙인다. 원형은 지우지 않는다. 후보마다 규칙 식별자와 버전이 있다.
  운영 색인의 기본값은 기준선이다. 식별자 분해 후보는 평가용 색인(FR-029)에서 고를 수 있게만 둔다(2026-10-22 사용자 결정). 기준선 설정으로 계산한 청킹 규칙 버전
  값(`chk-md-20d966f730bb`)과 운영 인덱스 버전 식별자는 이 명세 전후로 같다. 규칙 선택 기능을 넣어도 기준선의 값이 바뀌지 않아야 한다(QK-SYN-001 FR-020에 따라
  값이 바뀌면 운영 동기화가 멈춘다).
- **FR-019**: 색인 쪽 규칙은 임베딩 입력 텍스트를 바꾸지 않는다. 같은 임베딩 캐시를 가진 데이터베이스에서 규칙만 바꿔 색인하면 다시 임베딩하는 외부 호출이 0건이다.
- **FR-020**: 이 명세는 운영 색인의 인덱스 버전을 바꾸지 않는다. 색인 쪽 규칙이 다른 색인(평가용 포함)은 다른 청킹 규칙 버전과 인덱스 버전을 갖는다(AGENTS.md 3.3).
  검색 결과의 인덱스 버전에서 그 색인의 색인 쪽 규칙 식별자를 알 수 있어야 한다. 청킹 규칙 버전은 해시라 거기서 되찾을 수 없으므로, 기록 방법(인덱스 버전 열 추가
  마이그레이션 또는 코드의 대응표)은 계획 단계에서 정한다. 어느 방법이든 메타데이터 스키마 버전을 올리지 않는다. 올리면 운영 인덱스 버전 식별자가 바뀌어 SC-010이 깨진다.
- **FR-021**: ADR-010 결정에 쓸 후보, 비교 기준(식별자 원형·일부·문장형 질문의 상위 20건 포함 비율, 골든셋 Recall@5·MRR), 비교 방법(QK-EVL-001)을
  이 명세의 설계 문서에 남긴다. ADR-010 문서 작성과 결정(Status)은 QK-EVL-001 비교 결과로 사람이 승인한다.
- **FR-029**: 평가용 색인 준비 절차를 제공한다. 기준선을 포함한 후보 규칙마다 새 로컬 데이터베이스를 만들어 마이그레이션을 적용하고, 원본 데이터베이스(로컬 개발 DB 또는 운영 저장소)의
  임베딩 캐시(입력 해시·모델 버전·벡터. 텍스트 원문은 없다)를 복사한 뒤, 그 후보 규칙으로 QK-SYN-001 동기화를 실행하고 첫 인덱스 버전 활성화 명령으로 활성화한다. 한 번의 비교에 쓰는 평가용 데이터베이스는 모두 같은 원본 리비전
  (저장소 커밋)을 읽는다. 리비전을 고정하지 못하면 준비를 멈춘다. 리비전은 그 데이터베이스의 색인 쪽 규칙 식별자와 함께 검색 결과 조건(FR-024)으로 남는다.
  원본 데이터베이스에는 쓰지 않는다. 복사한 캐시로 처리되지 않는 임베딩이 있으면(원본 색인 뒤 문서가 바뀐 경우) 실행 전 미리 보기로 예상 Neurons를 보이고, 0이 아니면
  사람 확인 없이 실행하지 않는다(AGENTS.md 3.5). 대상 데이터베이스가 로컬이 아니면 거부한다. 비교 실행과 리포트는 QK-EVL-001이 한다.
  평가용 데이터베이스의 사용량 기록은 그 데이터베이스에만 남아 그날의 운영 사용량과 합쳐지지 않는다. 예상 0 Neurons이고 0이 아니면 사람 확인을 거치므로 이 차이를 받아들인다.

**평가 지원과 확인 명령 (US6, US7)**

- **FR-022**: 검색 방식은 하이브리드, 벡터 전용, 키워드 전용 중에서 고른다. 벡터 전용은 키워드 검색을, 키워드 전용은 질의용 임베딩을 부르지 않는다.
- **FR-023**: 순위만 필요한 요청은 문맥 확장과 Context 만들기를 건너뛸 수 있다.
- **FR-024**: 결과 요약은 검색 방식, 후보 수, RRF 상수, 질의 쪽 규칙, 색인 쪽 규칙, 인덱스 버전, 생략한 검색과 사유, 검색별 후보 수, 묶음 수, 사용 토큰과 예산,
  담지 못한 청크와 사유, 질의용 임베딩 사용량을 담는다. 질문 원문과 청크 본문은 요약에 넣지 않는다.
- **FR-025**: 질문 하나를 검색해 통합 순위·검색별 순위·출처 링크·Context 요약을 보여 주는 확인 명령을 제공한다. 명령은 운영 담당자 PC나 CI에서 로컬 또는 운영 저장소를
  대상으로 실행하며, 대상(로컬·원격)을 출력에 표시한다. 질문은 표준 입력으로 받고 명령행 인자로 받지 않는다. 질문 원문을 파일로 남기지 않는다.

**실행 환경 (ADR-008)**

- **FR-026**: 질의 하나의 외부 호출 수는 문맥 확장 대상 청크 수와 관계없이 상한(초기값 7) 안이다. 세는 호출은 질의용 임베딩 제공자 호출(재시도 포함), 사용량 기록
  쓰기, 저장소 질의 전부다. 하이브리드 기본 경로의 최대치는 임베딩 2(재시도 1회 포함) + 사용량 기록 2(시도마다, QK-EMB-001 FR-013) + 벡터 검색 1 + 키워드 검색 1 + 주변 청크 일괄 조회 1 = 7이다.
  질의응답은 Workers에서 돌아 요청당 subrequest와 CPU 시간 한도를 받기 때문이다(ADR-008). 질의 경로의 재시도 대기 시간은 계획 단계에서 Discord 응답 시간에 맞춰 정한다.
- **FR-027**: 검색 경계는 저장소와 임베딩 제공자를 경계(인터페이스) 뒤에서만 쓴다. 로컬 서버와 Workers가 같은 검색 함수를 부른다(C-06, QK-FND-001).
- **FR-028**: 후보 수(상한 50, QK-STO-001 FR-010), RRF 상수, 문맥 확장 범위, 확장 대상 상위 개수, 토큰 예산, 질문 길이 상한은 설정으로 바꿀 수 있고, 설정 검사가
  범위를 벗어난 값을 거부한다.

### Key Entities

- **검색 요청(Retrieval Request)**: 질문 문장, 필터, 검색 조건(방식, 후보 수, RRF 상수, 질의 쪽 규칙, 토큰 예산, Context 필요 여부).
- **통합 결과 항목(Fused Hit)**: 청크 식별자, 통합 순위·점수, 검색별 순위·원래 점수, 출처 정보.
- **문맥 묶음(Context Block)**: 문서 하나. Source ID, 문서 단위 출처 정보, 청크별 위치·제목 경로·순서 번호, 중심 청크들과 통합 순위, 청크 식별자 목록(원문 순서),
  생략 표시가 든 본문, 예상 토큰.
- **Context**: 문맥 묶음 목록(순위 순서), 사용 토큰, 예산.
- **검색 요약(Retrieval Summary)**: FR-024의 항목. 질문 원문과 본문은 없다.
- **키워드 검색 텍스트 규칙(Keyword Text Rule)**: 규칙 식별자·버전. 색인 쪽 규칙(기준선·식별자 분해)은 인덱스 버전에 딸리고, 질의 쪽 규칙은 요청마다 고른다.
- **평가용 색인(Evaluation Index)**: 후보 규칙 하나(기준선 포함)로 만든 별도 로컬 데이터베이스. 복사한 임베딩 캐시, 고정한 원본 리비전, 그 규칙의 활성 인덱스 버전을 가진다.
- **검색 실패(Retrieval Failure)**: FR-011의 실패 종류와, 축소 동작에서 생략한 검색과 사유.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 벡터 쪽에만, 키워드 쪽에만, 양쪽에 걸리는 청크를 섞은 고정 샘플 시험 전부에서 통합 순위가 RRF 기대값과 같고, 같은 질문을 두 번 실행한 결과 차이가 0건이다.
- **SC-002**: 접근 범위 미확인·제한, 비활성 인덱스 버전, 삭제·내림 상태의 청크를 질문과 가깝게, 또 노출 가능 청크의 앞뒤에 섞은 검증 세트에서 통합 결과와 Context에
  그런 청크가 들어간 사례가 0건이다.
- **SC-003**: 토큰 예산을 바꿔 가며 실행한 시험 전부에서 Context 예상 토큰 합계가 예산 이하이고, 잘린 청크가 0건이며, Context 안 중복 청크가 0건이고,
  담긴 청크와 건너뛴 청크가 FR-016 알고리즘의 기대 결과와 같다.
- **SC-004**: 식별자 검색 시험(camelCase·snake_case·kebab-case·URL 경로 각 5개 이상)에서 원형 질의는 모든 후보 규칙에서, 식별자 일부 질의는 식별자 분해 후보에서
  해당 청크가 키워드 검색 상위 20건 안에 드는 비율이 100%다.
- **SC-005**: 본문 낱말 하나 이상을 담은 문장형 질문 10개 이상에서 해당 청크가 키워드 검색 상위 20건 안에 드는 비율이 90% 이상이다(질의 쪽 규칙 적용 전 비율과 함께 기록).
- **SC-006**: Phase 1 대상 규모(원문 약 1.1 MB) 로컬 데이터베이스에서 하이브리드 검색과 Context 만들기(질의용 임베딩 제외)가 p95 1.5초 안에 끝난다. 데이터 규모,
  반복 횟수, 실행 환경, 질문 수를 함께 기록한다(C-13).
- **SC-007**: 문맥 확장 대상 상위 개수를 1, 8, 20으로 바꾸고 질의용 임베딩 일시 실패 뒤 재시도 성공 경로를 넣은 시험에서 질의 하나의 외부 호출 수(FR-026 기준)가 모두
  상한(초기값 7) 이하다. 인덱스 버전 바뀜 경로에서 다시 검색한 호출은 0건이다.
- **SC-008**: 하이브리드 요청에 질의용 임베딩 실패·전송 차단·키워드 검색 실패를 주입한 시험 전부에서 남은 검색으로 결과가 나오고 생략 사유가 기록된다. 사용량 기록과 요약에 질문 원문이
  든 사례가 0건이다.
- **SC-009**: 키워드 전용 검색 시험에서 질의용 임베딩 외부 호출이 0건이다. 임베딩 캐시를 복사한 평가용 데이터베이스에서 식별자 분해 후보로 색인한 시험에서 임베딩
  외부 호출이 0건이고 원본 데이터베이스 쓰기가 0건이다.
- **SC-010**: 이 명세를 구현한 뒤 기준선 설정의 청킹 규칙 버전 값과 운영 인덱스 버전 식별자가 구현 전과 같다(`chk-md-20d966f730bb`와 비교하는 시험).
- **SC-011**: 벡터 전용·키워드 전용 요청에 실패를 주입한 시험 전부에서 다른 방식의 결과가 나온 사례가 0건이다.

## Assumptions

**요구사항 원문 부재**

- FR-RET-01~03, 07, 08과 FR-CHK-07은 저장소(git 이력 포함)에 원문이 없다(2026-10-22 확인). QK-STO-001·QK-EMB-001·QK-SYN-001과 같은 방식으로
  뜻을 추측해 대응시키지 않았다. 원문이 나오면 이 명세와 대조해 고친다.
- ADR-010은 로드맵 3절과 RISK-05에 "키워드 검색 텍스트" 결정으로만 나오고 문서가 없다. 이 명세가 후보와 비교 기준을 정하고(FR-021), 확정은 1.G 전에
  QK-EVL-001 비교 결과로 사람이 한다.
- 백로그 제목 요소와 이 명세의 대응은 아래와 같다.

| 백로그 제목 요소 | 이 명세 | 근거 |
| --- | --- | --- |
| 하이브리드 검색 | FR-001~002, FR-005~011, FR-022, FR-026, US1·US2·US6 | QK-STO-001 US2, Confluence `설계` Step04(벡터 20 + 키워드 20 → RRF) |
| RRF | FR-003~004 | QK-STO-001 Assumptions(순위 통합은 QK-RET-001) |
| 문맥 확장 | FR-012~015, US3 | QK-STO-001 FR-011(지금 함수는 중심 청크 하나씩·상위 절 목록·순서 번호 없음), QK-CHK-002 FR-009 |
| 토큰 예산 | FR-016, US4 | ADR-009(컨텍스트 32,768, 프롬프트 포함 입력 3,000·출력 1,200토큰 가정), QK-EMB-001 FR-017(질의응답 예비분) |
| 키워드 검색 텍스트 | FR-017~021, FR-029, US5 | QK-CHK-002 FR-020, ADR-007 관찰, QK-SYN-001 관찰·FR-020·FR-021, RISK-05 |

**초기값**

- 후보 수 20, RRF 상수 60, 확장 대상 상위 8개, 앞뒤 각 1개, Context 토큰 예산 2,000, 질문 길이 상한 2,000자, 질의당 외부 호출 상한 7은 초기값이다.
  QK-EVL-001 평가 결과로 조정하고, 조정은 결정 기록과 평가 보고서로 남긴다(AGENTS.md 3.4).
- RRF 상수 60은 RRF 원 논문(Cormack 외, 2009)의 값이다. 순위만 쓰므로 벡터 거리와 키워드 점수의 척도 차이를 맞출 필요가 없다.
- Context 예산 2,000은 프롬프트 몫 약 1,000(QK-GEN-001이 확정)과 합쳐 ADR-009의 질의당 입력 3,000에 맞춘 값이다. qwen3 단가(입력 1M 토큰당 4,625, 출력 30,475 Neurons,
  spike-workers-ai 3.2절)로 질의당 입력 3,000 ≈ 13.9, 출력 1,200 ≈ 36.6, 질의 임베딩은 1 미만이라 약 51 Neurons다. 하루 50건이면 약 2,550으로 질의응답 예비분
  3,000 안이다. 생성 몫의 배분은 QK-GEN-001이 정한다.
- 예상 토큰(UTF-8 바이트 ÷ 3.5)은 실제보다 적게 나온다는 측정이 이미 있다. bge-m3 토크나이저 기준으로 표는 중앙값 1.32배·최대 2.30배, 코드는 중앙값 1.18배다
  (QK-CHK-002 research R-03). QK-SYN-001 첫 실제 색인에서는 실측 Neurons가 미리 보기의 2.42배였다(H02, 원인 미확인). Context가 예산 2,000 그대로 2.3배로 늘면
  질의당 약 63 Neurons, 하루 50건에 약 3,150으로 예비분을 넘는다. 그래서 생성 모델 토크나이저로 Phase 1 대상 문서의 실제/예상 비율을 재는 것을 계획 단계 게이트로 두고,
  그 결과로 예산 초기값이나 바이트당 토큰 설정값을 정한다.
- Context 예산 2,000은 청크 상한(예상 2,800, QK-CHK-002)보다 작아, 예상 2,000을 넘는 청크는 Context에 들어갈 수 없다. 대상 문서에서 그런 청크는 소수로 보인다
  (QK-CHK-002 research R-02의 블록 분포에서 추정). 같은 계획 단계 게이트에서 예산을 넘는 청크 수를 재 기록하고, 많으면 예산이나 청크 목표 크기를 다시 정한다.

**범위**

- 질문 분류·필터 추론(QK-TRK-001), 질의 재작성·스레드 문맥(QK-BOT-002), 관계 기반 후보 확장(QK-RET-002), 리랭커(QK-RET-003), 문서당 결과 개수 제한은 이 명세 밖이다.
- 관련도 임계값(이 점수보다 낮으면 결과 없음)은 두지 않는다. RRF 점수는 순위만 반영해 절대 관련도를 뜻하지 않는다. "확인할 수 없습니다" 판단은 QK-GEN-001이
  Context와 검색별 원래 점수로 한다.
- 검색 평가 실행기, 골든셋 라벨, 비교 리포트는 QK-EVL-001이다. 이 명세는 평가가 부를 검색 방식과 조건 기록(FR-022~024)만 제공한다.
- 인덱스 버전 평가 게이트와 활성화 절차는 QK-STO-002(Phase 2)다. 이 명세는 운영 색인 규칙을 바꾸지 않으므로 활성화 절차가 필요 없다. ADR-010 확정 뒤 운영 규칙을
  바꾸는 작업은 별도 작업으로 하고, 그때 활성화 방식(QK-SYN-001 첫 인덱스 버전 방식 또는 QK-STO-002)을 정한다.
- 저장소 질의 함수의 노출 조건과 키워드 검색 문법 처리(QK-STO-001)는 바꾸지 않는다. 주변 청크 일괄 조회(FR-012)는 같은 노출 조건으로 새 마이그레이션을 더한다.
- 지금 키워드 검색 함수는 검색어를 함수 안에서 이스케이프한다. 이 상태로 FR-017(낱말 하나만 맞아도 후보)을 만들 수 있는지, `OR`가 이스케이프되는지는 확인하지 않았다.
  계획 단계에서 확인하고, 안 되면 같은 노출 조건의 새 키워드 검색 질의를 더한다. 그때 질문 속 낱말 "OR"가 연산자로 해석되지 않게 한다.
- 로드맵 2.2 QK-CHK-001(코드 청커)에도 식별자 분해가 있다. 이 명세의 색인 쪽 식별자 분해 규칙(FR-018)은 Markdown 청크의 키워드 검색 텍스트에 대한 것이다.
  QK-CHK-001은 코드 메타데이터를 다루며, 키워드 검색 텍스트에 식별자를 분해해 넣을 때는 ADR-010에서 확정한 규칙을 다시 쓴다고 가정한다.

**환경**

- 질의응답은 Cloudflare Workers에서 실행한다(ADR-008). 운영 저장소 연결 방식(HTTP RPC 계층 등, ADR-008 변경 제안)과 Workers 안에서 이 명세의 코드가 도는
  방식은 계획 단계에서 정한다. 확인 명령(FR-025)과 평가는 Workers 밖에서 돈다.
- Workers의 요청당 CPU 10 ms와 동시 외부 연결 6(ADR-008)은 이 명세의 SC가 직접 재지 않는다. SC-006은 로컬 실행 시간이다. 검색 결과 최대 40건이 본문을 담아 오는
  응답 크기와 CPU 시간은 계획 단계에서 확인하고, 한도에 걸리면 ADR-008 Revisit conditions로 넘긴다.
- 평가용 색인(FR-029)은 GitHub 원본을 다시 읽어 색인한다. GitHub API 읽기 호출이 생기지만 Neurons는 캐시로 0이다.
- 질의용 임베딩 사용량은 QK-EMB-001 규칙대로 기록·집계된다. 이 명세는 별도 사용량 기록을 두지 않는다.
- 확인 명령과 평가로 원격 저장소를 질의하는 것은 읽기만 한다. 원본 자료원에는 쓰지 않는다(C-09).
