# H01 Confluence 동의 문서 초안: 질의 기록과 질문 원문 저장

작성일: 2026-11-04. **미게시 초안**. 문서 위치 `<Confluence 문서 링크>`, 공지 `<Discord 공지 링크>`, 공지일 `<공지 날짜>`, 운영 배포일·시작일은 2026-11-04로 확정했다. 게시 링크·날짜는 미확인이다.

## 목적과 보는 사람

팀 봇의 지연·사용량·실패 유형을 확인하고, 파일럿에서 👎 사례를 분석하며 개선용 질문 후보를 모읍니다. 파일럿 분석을 위해 질문 원문을 열람하는 사람과 운영 담당자는 GitHub 계정 byuntil, tkv00 두 명으로 같습니다. 삭제 작업의 관리 연결 접근은 이 열람 범위를 넓히지 않습니다. 이는 분석 목적의 열람 범위이며, 운영 서버 관리 권한이 있는 사람은 기술적으로 원문을 읽을 수 있습니다. 그 권한을 가진 사람의 명단은 미확인입니다. 평가 세트로 옮기는 사본은 개인 정보를 지운 별도 사본입니다.

## 기록하는 범위

기록 기능이 켜지면 대상 질의의 메타데이터(질의 시각·상태·지연·사용량·모델·인덱스 버전·근거 청크 식별자 등)와 피드백을 기록합니다. 질문자와 평가자의 원본 Discord 식별자가 포함됩니다. 이 메타데이터 기록은 팀 공지와 동의 문서를 근거로 하며, 질문 원문의 질의별 동의와 구분됩니다. 원문 저장을 거절해도 “나만 보기”와 실패·시간 초과·비밀값 차단·대기열 가득 결과는 기록 대상입니다. 답변·확인 불가·검색/생성 실패·시작 확인 없음·전달 실패·예상하지 못한 실패도 포함합니다. 서명 오류·허용 범위 밖·지원하지 않는 요청·같은 상호작용 재전송은 제외합니다. Worker가 질의 서비스에 닿지 못해 대체 응답한 요청은 질의 기록에 없고 중계 운영 로그의 건수로 따로 셉니다(FR-002). 메타데이터에는 질문 원문·답변 본문·청크 본문·출처 제목과 링크를 넣지 않습니다. 메타데이터 식별자는 원문과 달리 보존 기간이 정해져 있지 않으며 삭제 요청으로 지웁니다.

**원문 기록은 동의한 질문 하나만 저장합니다. 답변 본문은 저장하지 않습니다.** 출처 목록·청크 본문도 원문 기록에 저장하지 않습니다. 답변은 메타데이터의 근거 청크 식별자와 인덱스 버전으로 따라갑니다. 질문 원문과 함께 동의 시각·동의 방식이 남습니다. 저장 직전 비밀값 검사에 걸리면 원문을 저장하지 않고 생략 표시만 남깁니다.

## 답변 생성을 위한 외부 전송

답변을 만들기 위한 질문은 Cloudflare Workers AI로 전송됩니다. 이 전송은 질문 원문 저장 동의와 별개이며, [저장 안 함]을 골라도 이미 일어난 전송은 달라지지 않습니다. 이 기록 기능으로 새 외부 전송은 추가되지 않습니다(ADR-016 Data and cost; `query/pipeline.py:167`, `:180`).

[Cloudflare의 Workers AI 데이터 사용 문서](https://developers.cloudflare.com/workers-ai/platform/data-usage/)(2026-10-16 갱신, 2026-11-04 조회)는 프롬프트·출력·임베딩 등 처리한 고객 콘텐츠를 모델 학습에 쓰지 않는다고 밝힙니다. 상태 저장 기능을 쓰지 않는 일반 추론 요청의 입력·출력은 요청 처리와 응답 전달에 필요한 동안 처리하고, 더 이상 필요하지 않으면 보관하지 않는다고 설명합니다. **이는 제공자의 공개 문서 기준이며, 제공자 내부 동작을 독립 검증한 사실이 아닙니다.** 게시 직전에 페이지를 다시 확인합니다(Source ID CF-DATA).

사용자가 켠 저장 기능은 예외입니다. AI Gateway 로깅·캐싱, 애플리케이션 로그, R2·KV·Durable Objects·Vectorize 같은 저장 서비스, 비동기·batch 등 상태 저장 기능은 각 기능의 설정과 보존 주기를 따릅니다. 법적 의무 이행에 필요한 콘텐츠 분석·보존도 예외이며, 문서는 그 콘텐츠를 학습이나 제품 개선에 쓰지 않는다고 밝힙니다. 고객 콘텐츠를 제외한 모델 식별자·시각·요청 크기·토큰/뉴런 수·지연·상태 등 운영 메타데이터는 남을 수 있습니다.

저장소의 임베딩·생성 어댑터는 REST `POST /client/v4/accounts/{account}/ai/run/{model}`를 직접 호출합니다(`adapters/workers_ai/rest.py:23`, `:142`, `adapters/workers_ai/generation.py:190`). 확인한 프로젝트 사용 경로는 AI Gateway, batch, Vectorize·R2·KV·Durable Objects를 쓰지 않습니다. 이 코드 확인이 제공자의 실제 처리·보존을 독립 검증했다는 뜻은 아닙니다. [ADR-009](../../../docs/sdd/decisions/ADR-009-generation-model.md)의 과거 기록과 구분합니다.

## 질문마다 동의하는 방법

질문자 본인이 자기 질문에 대한 답변의 👎 버튼을 눌렀을 때만 “질문을 개선용으로 저장할까요?”를 묻습니다. [저장 동의]를 선택하면 이 질문 하나를 저장합니다. 기본값은 [저장 안 함]이며, 아직 저장되지 않은 질문은 이를 선택하면 저장하지 않습니다. 👍나 다른 사람이 누른 👎에는 동의를 묻지 않습니다. 질문마다 따로 선택하며 상시 동의로 취급하지 않습니다.

동의 처리 결과를 확인하지 못했다는 안내를 받으면 저장되지 않았다고 단정할 수 없습니다. 대기 시간 안에 다시 누를 수 있고, 이후 안내는 실제 저장 여부에 따라 정해집니다. 결과 불명 뒤 [저장 안 함]을 눌러도 이미 저장된 질문은 취소되지 않습니다. 이미 저장됐다면 운영 담당자에게 삭제를 요청해야 합니다(`contracts/discord-components.md` 13행, `query/app.py:263`).

## 동의 전 메모리 대기

결과가 “답변”·“확인 불가”인 질의의 질문과 질문자 식별자를 서비스 메모리에만 최대 1시간·500건 둡니다. DB·파일·운영 로그에 쓰지 않습니다. 상한을 넘으면 오래된 것부터 버리며, 만료·재시작 후에는 동의를 묻지 못합니다. 선택 결과가 확정되면 대기 질문을 바로 지우고 선택 사실만 만료까지 남깁니다. 처리 결과가 불명이면 재시도를 위해 대기 시간 안에서 질문을 유지합니다.

이 대기를 C-10의 “저장”으로 보지 않는 해석을 사용자가 2026-11-04 수용했고 ADR-016도 승인했습니다. core dump 금지·스왑 등 메모리가 파일로 나가지 않는 운영 조건은 확인한 뒤 켭니다. 이 정책 승인이 운영 명령별 승인을 대신하지 않습니다.

## 보존 기간과 종료

질문 원문은 **Phase 2 완료 리뷰까지, 늦어도 시작일로부터 약 1개월인 `2026-12-04(UTC)`까지** 보존합니다. 2.G에서 사람이 연장 또는 삭제를 결정하여 ADR-016에 기록합니다. 연장하면 새 날짜를 팀에 알립니다. 날짜가 지나면 새 동의를 묻지 않고 삭제 필요 경고가 나옵니다. 자동 삭제 기능은 없으므로 운영 담당자가 전체 원문 삭제 명령 `qk-index queries erase-texts`의 건수를 확인하고 승인 후 삭제합니다. 이 전체 원문 삭제는 메타데이터·피드백을 남깁니다. 이 명령은 현재 운영 DB 원문만 지우며 서비스 메모리 대기는 지우지 못합니다. 보존 날짜 전이면 대기 질문이 삭제 뒤 동의로 다시 저장될 수 있습니다. 기록 기능을 끄고 서비스를 재시작해 대기를 비운 뒤 삭제하거나, 대기가 끝난 뒤 다시 삭제해야 합니다. 기능을 계속 켜거나 다시 켤지는 `<사람이 정할 기능 유지·재개 여부>`입니다. 내보낸 파일·백업은 이 명령의 삭제 범위에 포함되지 않습니다(`indexer/queries_cli.py:120`, `adapters/postgres/query_log_admin.py:55`, `query/pending.py:31`).

## 본인 기록 삭제 요청

운영 담당자 `<운영 담당자 멘션>`에게 Discord DM으로 삭제를 요청하세요. 담당자가 관리 연결의 `qk-index queries erase-user`로 대상 건수를 미리 확인하고 승인 후 실행합니다. 이 명령은 현재 운영 DB에 있는 대상 사용자의 질문 원문을 지우고, 질의 기록의 질문자 식별자와 피드백의 평가자 식별자를 비웁니다. 수치·상태·평가 값은 남습니다. 삭제 이력에는 시각·종류·건수만 남고 대상 식별자는 남기지 않습니다.

이 명령은 서비스 메모리 대기를 지우지 못합니다. 담당자는 서비스 재시작 또는 최대 1시간 대기가 끝난 뒤 재실행하는 절차를 함께 수행합니다. 내보낸 파일은 DB 삭제와 별개로 사람이 찾아 삭제합니다. 요청 식별자는 안전한 경로와 표준 입력으로만 전달하며 공개 문서·저장소·명령 인자·명령 이력에 남기지 않습니다. DB 삭제가 모든 사본 삭제를 뜻하지 않습니다.

## 원문 열람·백업의 범위: 게시 전 사람 결정

분석 목적의 원문 열람자와 운영 담당자는 GitHub 계정 byuntil, tkv00 두 명으로 같고, 삭제 작업의 관리 연결 접근은 이 열람 범위를 넓히지 않습니다. 운영 서버 소유자는 tkv00입니다(사용자 확인). 2026-11-04 전달받은 읽기 전용 확인에 따르면 운영 DB는 공유 인스턴스의 컨테이너에 있고, 서버 sudo 또는 docker 그룹 권한이 있으면 기술적으로 원문을 읽을 수 있습니다. sudo 경로를 통한 DB 조회가 동작했으며 인스턴스는 팀원 테넌시 소유입니다. 서버 관리 권한 전체 명단은 확인하지 못했으므로 게시 전 사람 확인이 필요합니다(Source ID OPS-ACCESS-20261104).

원문은 애플리케이션 저장 시 별도로 암호화하지 않습니다. `0008_query_log.sql:35`의 질문 열은 text이고, `:133`의 저장 함수는 입력 본문을 그대로 넣으며, 어댑터도 질문을 그대로 전달합니다(`adapters/postgres/query_log.py:113`). 이는 저장 코드 확인이며 디스크·볼륨 암호화 여부를 확인했다는 뜻은 아닙니다.

 ADR-016 Negative / risks에는 원문과 식별자가 WBS 5.2의 백업 대상에 들어간다고 적혀 있습니다. 그러나 저장소 기준으로 DB 백업·복구 절차 전체는 아직 정해지지 않았으며 QK-SYN-003(WBS 5.2)에서 정합니다([운영 문서 5절](../../../docs/ops/oci-production-store.md#5-복구재색인), [로드맵 5.2](../../../docs/sdd/roadmap.md)). **2026-11-04 확인 범위에서 운영 DB 백업은 발견되지 않았다**는 읽기 전용 확인 결과를 전달받았습니다(Source ID OPS-BACKUP-20261104). 부트 볼륨 백업 0건·백업 정책 미할당, 추가 블록 볼륨 없음, 해당 컴파트먼트의 블록 볼륨 백업 0건이었습니다. 서버에서 pg_dump·restic·borg·rclone·wal-g·pgbackrest 등 백업 도구와 DB 백업 타이머·크론·컨테이너를 발견하지 못했고, 흔한 경로의 덤프 파일은 0개, PostgreSQL archive_mode는 off, 복제 슬롯은 0개였습니다.

다른 컴파트먼트의 수동 백업, 이름이 다른 스크립트, 서버 밖 복사는 확인하지 못했습니다. 2026-11-04에 확인한 도구·설정·경로에서는 운영 DB 백업이나 다른 DB 사본을 발견하지 못했습니다. 삭제 명령은 현재 운영 DB만 처리하며, 내보낸 파일과 확인하지 못한 사본은 별도입니다. 확인한 복구 수단 기준으로 DB를 잃으면 저장된 질문과 기록은 복구되지 않습니다. 조사 한계를 넘어 모든 사본이 없다고 보장하지 않습니다.

향후 백업이 생기면(QK-SYN-003, WBS 5.2) 삭제 범위가 달라지므로 동의 문서를 고치고 다시 공지한다는 방침은 사람 확인 대상입니다. 백업 도입 시 `<백업 보존 기간>`, `<백업 접근 범위>`, `<복원 뒤 원문·식별자 재삭제 방법>`을 확정해야 합니다. 현재 DB의 원문·식별자 삭제와 내보낸 파일의 별도 삭제는 다르며, 향후 DB 삭제 명령이 백업까지 지운다고 약속하지 않습니다.

문의·범위에 대한 이견은 운영 담당자 `<운영 담당자 멘션>`에게 Discord DM으로 보내 주세요.

## 편집자용 게시 전 확인·승인 확인란

- 운영 배포일·시작일 2026-11-04와 보존 상한 2026-12-04(UTC)는 확정값이다. 공지·이 문서·설정에 같은 값을 쓴다. 배포가 2026-11-04를 넘기면 시작일, 상한 날짜, 설정 값을 함께 고치고 게시 전이면 문구를, 게시 후면 정정 공지를 낸다.
