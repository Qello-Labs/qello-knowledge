## User Scenarios & Testing *(mandatory)*

이 명세의 사용자는 Qello Knowledge 저장소에 기여하는 팀 개발자, PR 리뷰어, 운영 환경에 값을 넣는 운영 담당자다.
Phase 1의 다른 명세(QK-STO-001, QK-ING-001 등)는 모두 이 골격 위에서 구현한다.

### User Story 1 - 외부 계정 없이 로컬에서 개발·테스트를 시작한다 (Priority: P1)

새로 합류한 개발자가 저장소를 받은 뒤, 문서에 적힌 절차대로 로컬 개발 환경(로컬 데이터베이스 포함)을 띄우고
기본 테스트를 통과시킨다. 이 과정에 Cloudflare·Supabase·GitHub·Discord 계정이나 토큰이 필요하지 않다.

**Why this priority**: 다른 모든 Phase 1 명세가 이 환경에서 개발되고 테스트된다. 로컬 환경이 없으면 QK-STO-001의
스키마·검색 SQL을 실제 DB 없이 검증해야 하고, 팀원마다 환경이 달라 결과를 재현할 수 없다.

**Independent Test**: 토큰이 없는 깨끗한 환경에서 저장소를 받아 문서의 절차만 따라 기본 테스트를 실행한다.
모든 테스트가 통과하고 외부 서비스로 나간 요청이 0건이면 통과다.

**Acceptance Scenarios**:

1. **Given** 저장소를 막 받았고 토큰·`.env`가 없는 상태, **When** 개발자가 문서의 로컬 시작 절차를 따른다,
   **Then** 로컬 데이터베이스가 뜨고 기본 테스트가 모두 통과한다.
2. **Given** 로컬 환경이 이미 떠 있는 상태, **When** 같은 시작 절차를 다시 실행한다, **Then** 오류 없이 끝나고
   기존 로컬 데이터는 유지된다.
3. **Given** 로컬 데이터베이스가 떠 있는 상태, **When** 개발자가 벡터 유사도 질의와 한국어 키워드 질의를 각각 한 번 실행한다,
   **Then** 두 질의가 모두 성공한다. 운영 저장소(ADR-008)에서 쓸 검색 기능을 로컬에서도 쓸 수 있다는 뜻이다.
4. **Given** 로컬 환경을 지우고 처음부터 다시 만들고 싶은 상태, **When** 개발자가 로컬 재설정 절차를 실행한다,
   **Then** 로컬 데이터베이스만 초기화되고 원격 저장소에는 아무 요청도 가지 않는다.

### User Story 2 - 실행 주체마다 필요한 설정만 검증하고, 잘못되면 시작 전에 멈춘다 (Priority: P1)

질의응답 서비스와 색인 실행기(ADR-008: 색인은 질의응답 런타임 밖에서 실행)는 같은 설정 규칙으로 값을 읽는다.
각 실행 주체는 자기에게 필요한 항목만 요구하고, 필수 값이 빠졌거나 형식이 틀리면 실제 작업을 시작하기 전에
멈춘다. 오류 메시지에는 설정 **이름**만 나오고 값은 나오지 않는다.

**Why this priority**: 설정 오류가 작업 중간에 드러나면 부분 반영이 남는다(AGENTS.md 4절). 비밀값이 로그에
찍히면 AGENTS.md 6절 위반이다. 실행 주체별로 필요한 토큰만 받아야 C-09(필요한 범위만)를 지킨다.

**Independent Test**: 필수 설정을 일부러 빼거나 형식을 틀리게 넣고 각 실행 주체의 설정 점검을 실행한다.
누락·오류 항목이 이름으로 모두 보고되고, 출력 어디에도 넣은 값이 나오지 않으면 통과다.

**Acceptance Scenarios**:

1. **Given** 색인 실행기에 필요한 필수 설정 두 개가 빠진 상태, **When** 색인 실행기의 설정 점검을 실행한다,
   **Then** 빠진 두 이름을 한 번에 보고하고 0이 아닌 종료 코드로 끝난다. 외부 서비스 호출은 없다.
2. **Given** 비밀 항목에 형식이 틀린 값을 넣은 상태, **When** 설정 점검을 실행한다, **Then** 항목 이름과
   "형식 오류"만 보고하고 넣은 값은 일부도 출력하지 않는다.
3. **Given** 질의응답 서비스에 필요한 설정만 채운 상태, **When** 질의응답 서비스의 설정 점검을 실행한다,
   **Then** 통과한다. 색인 전용 항목(예: 저장소 읽기 토큰)이 비어 있어도 실패하지 않는다.
4. **Given** 같은 설정 이름이 로컬 설정 파일과 실행 환경 변수에 모두 있는 상태, **When** 설정을 읽는다,
   **Then** 실행 환경 쪽 값이 쓰인다.
5. **Given** 모든 설정이 올바른 상태, **When** 설정 점검을 실행한다, **Then** 항목별 통과 여부를 이름으로 보여 주고
   0으로 끝난다.

### User Story 3 - PR마다 테스트·린트·비밀값 검사가 자동으로 돈다 (Priority: P2)

개발자가 PR을 열거나 갱신하면 테스트, 린트(코드 형식 포함), 비밀값 검사가 자동으로 실행되고 결과가 PR에 표시된다.
리뷰어는 세 검사 결과를 보고 병합 여부를 판단한다.

**Why this priority**: AGENTS.md 7절의 기본 검증(`python scripts/preflight.py`, `git diff --check`)을 지금은 사람이
손으로 돌린다. Phase 1에서 코드가 늘면 빠뜨리기 쉽다. 다만 로컬 환경(US1)과 설정(US2)이 먼저 있어야 CI가 돌릴 테스트가 생긴다.

**Independent Test**: 테스트 실패, 린트 위반, 비밀값 샘플을 각각 하나씩 넣은 PR 세 개를 연다. 각 PR에서 해당
검사만 실패로 표시되고, 아무 문제 없는 PR에서는 세 검사가 모두 통과하면 통과다.

**Acceptance Scenarios**:

1. **Given** 실패하는 테스트가 들어간 PR, **When** CI가 돈다, **Then** 테스트 검사가 실패로 표시되고 실패한 테스트 이름이 보인다.
2. **Given** 비밀값 패턴(예: 토큰 형식 문자열)이 들어간 파일이 있는 PR, **When** CI가 돈다, **Then** 비밀값 검사가
   실패하고, 결과에는 파일 경로와 규칙 이름만 나오고 값은 나오지 않는다.
3. **Given** 저장소의 CI 비밀값(토큰)에 접근할 수 없는 PR(예: 포크에서 연 PR), **When** CI가 돈다, **Then** 세 검사가
   토큰 없이 끝까지 돈다.
4. **Given** 실제 외부 API를 호출하는 테스트가 있는 상태, **When** 기본 테스트를 실행한다(CI 포함), **Then** 그 테스트는
   건너뛴 것으로 표시되고 외부 호출은 0건이다.
5. **Given** 같은 커밋, **When** 개발자가 로컬에서 세 검사를 돌린 결과와 CI 결과를 비교한다, **Then** 통과·실패가 같다.

---

### User Story 4 - 교체 경계와 두 실행 진입점이 처음부터 나뉘어 있다 (Priority: P3)

후속 명세 담당자가 자료원 어댑터(QK-ING-001), 저장소(QK-STO-001), 임베딩(QK-EMB-001), 생성(QK-GEN-001),
채팅 창구(QK-BOT-001)를 구현할 때, 각각을 넣을 자리와 경계 규칙이 이미 정해져 있다. 질의응답 진입점과 색인 진입점은
따로 있고, 색인 쪽 의존성이 질의응답 쪽에 딸려 들어가지 않는다.

**Why this priority**: C-06(교체 가능한 경계)을 골격 단계에서 정하지 않으면 각 명세가 제각각 구조를 만든다.
다만 실제 기능은 후속 명세가 채우므로 이 명세에서는 자리와 규칙만 만든다.

**Independent Test**: 두 진입점을 각각 실행해 "설정 점검 통과, 아직 기능 없음" 수준의 응답이 나오는지 본다.
경계 규칙을 어기는 의존(예: 도메인 코드가 외부 SDK 타입을 직접 참조)을 하나 넣었을 때 자동 검사가 실패하는지 본다.

**Acceptance Scenarios**:

1. **Given** 골격만 있는 상태, **When** 질의응답 진입점을 로컬에서 실행하고 상태 확인 요청을 보낸다, **Then** 정상 응답이 온다.
2. **Given** 골격만 있는 상태, **When** 색인 진입점을 실행한다, **Then** 설정 점검 결과를 보여 주고 아무 자료도 수집하지 않은 채
   0으로 끝난다.
3. **Given** 도메인 영역 코드가 외부 서비스 SDK를 직접 가져오는 변경, **When** 린트나 테스트를 돌린다, **Then** 경계 위반으로 실패한다.

---

### Edge Cases

- `.env`가 아예 없을 때: 로컬 기본 테스트는 통과해야 한다(US1). 설정 점검은 "필수 항목 누락"을 이름으로 보고한다.
- 설정 값이 빈 문자열이거나 공백뿐일 때: 누락으로 취급한다.
- 로컬 데이터베이스에 한국어 키워드 검색 확장 기능이 없을 때: 시작 절차가 "어떤 확장이 없는지"를 이름으로 보고하고 실패한다.
  조용히 벡터 검색만 되는 상태로 넘어가지 않는다.
- 로컬 데이터베이스가 쓰는 포트를 다른 프로그램이 이미 쓰고 있을 때: 충돌한 포트를 알리고 포트를 바꾸는 방법을 문서에 둔다.
- 로컬 재설정 절차를 원격 저장소를 가리키는 설정으로 실행했을 때: 실행을 거부한다(AGENTS.md 4절 공유 DB 초기화 금지).
- 저장해 둔 외부 API 응답 샘플에 토큰·계정 식별자가 섞여 있을 때: 비밀값 검사가 실패해야 한다. 샘플도 검사 대상이다.
- 비밀값 검사 규칙에 걸리지만 실제로는 비밀값이 아닌 문자열(오탐)일 때: 경고를 끄는 대신 규칙의 예외 목록에 사유와 함께 올린다.
  예외 목록 변경은 리뷰 대상이다.
- 실제 외부 API 테스트를 명시적으로 켰는데 토큰이 없을 때: 건너뛰지 않고 "토큰 없음"으로 실패한다. 켠 사람이 결과를 오해하지 않게 한다.
- CI가 외부 원인(러너 장애, 네트워크)으로 끝나지 못했을 때: 통과로 표시하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**골격 (US4)**

- **FR-001**: 저장소는 질의응답 진입점과 색인 진입점을 따로 가진다. 색인 진입점은 질의응답 런타임 밖(로컬 CLI 또는
  CI 작업)에서 실행할 수 있어야 한다(ADR-008).
- **FR-002**: 자료원, 임베딩, 생성, 저장소, 채팅 창구는 각각 경계(인터페이스) 뒤에 두고, 외부 SDK의 타입이 경계 밖
  도메인 코드로 나가지 않는다(C-06). 위반은 자동 검사(FR-019 린트 또는 테스트)로 잡는다.
- **FR-003**: 질의응답 진입점은 로컬에서 실행해 상태 확인 요청에 응답할 수 있다. 색인 진입점은 설정 점검만 하고
  0으로 끝나는 동작을 가진다. 실제 기능은 후속 명세가 채운다.

**설정 로딩 (US2)**

- **FR-004**: 두 진입점은 같은 설정 로딩 규칙을 쓴다. 설정 원천은 실행 환경 변수와 로컬 설정 파일(`.env`, git 추적 제외)이고,
  같은 이름이 둘 다 있으면 실행 환경 변수가 우선한다.
- **FR-005**: 설정 항목마다 이름, 설명, 필수 여부, 비밀 여부, 사용하는 진입점, 기본값(비밀 항목은 기본값 없음)을 한 곳에 정의한다.
  저장소에는 이 정의에서 만든 예시 파일(이름과 placeholder만, 실제 값 없음)과 문서를 둔다.
- **FR-006**: 각 진입점은 자기가 쓰는 항목만 필수로 검사한다. 예: 색인 진입점은 Discord 항목을 요구하지 않고,
  질의응답 진입점은 저장소 읽기 토큰을 요구하지 않는다(C-09).
- **FR-007**: 필수 항목 누락, 빈 값, 형식 오류는 실제 작업(외부 호출, DB 쓰기) 전에 모두 모아 한 번에 보고하고,
  0이 아닌 종료 코드로 끝난다.
- **FR-008**: 비밀 항목의 값은 설정 점검 결과, 오류 메시지, 로그, 예외 출력 어디에도 일부라도 나오지 않는다.
  보고에는 항목 이름과 상태(통과, 누락, 형식 오류)만 쓴다.
- **FR-009**: 각 진입점에 외부 호출 없이 설정만 확인하는 점검 모드를 둔다. 결과는 항목별 이름과 상태를 보여 준다.

**로컬 개발 환경 (US1)**

- **FR-010**: 로컬 의존 서비스(최소한 데이터베이스)를 문서화된 명령 하나로 띄우고 내릴 수 있다. 이 환경은 로컬 개발·테스트 전용이며
  운영 실행 환경이 아니다(ADR-008 Follow-ups).
- **FR-011**: 로컬 데이터베이스는 운영 저장소(ADR-008: 관리형 PostgreSQL, pgvector·PGroonga)에서 쓸 벡터 유사도 검색과
  한국어 키워드 검색 기능을 제공한다. 필요한 확장 기능이 없으면 시작 절차가 확장 이름을 보고하고 실패한다.
- **FR-012**: 시작 절차는 재실행해도 안전하다. 이미 떠 있으면 그대로 두고 로컬 데이터를 지우지 않는다(AGENTS.md 4절).
- **FR-013**: 로컬 재설정(데이터 초기화) 절차는 로컬 데이터베이스만 대상으로 한다. 설정이 로컬이 아닌 데이터베이스를 가리키면
  실행을 거부한다.
- **FR-014**: 로컬 시작부터 기본 테스트 통과까지의 절차를 저장소 문서에 둔다. 이 절차는 외부 계정과 토큰 없이 끝난다.

**테스트 (US1, US3)**

- **FR-015**: 기본 테스트 명령을 프로젝트 정의 파일에 등록하고 AGENTS.md 7절 기본 검증에 추가한다.
- **FR-016**: 실제 외부 API를 호출하는 테스트는 별도 표시를 붙이고 기본 실행에서 제외한다. 명시적으로 켰을 때만 실행하고,
  켰는데 필요한 토큰이 없으면 실패한다(C-12).
- **FR-017**: 외부 API를 쓰는 기능의 기본 테스트는 저장해 둔 응답 샘플로 돈다. 응답 샘플은 비밀값 검사 대상이다(C-12, AGENTS.md 6절).

**CI (US3)**

- **FR-018**: PR을 열거나 갱신할 때 테스트, 린트, 비밀값 검사 세 가지를 자동으로 실행하고 각각의 결과를 PR에 따로 표시한다.
  `main` 반영 후에도 같은 검사를 실행한다.
- **FR-019**: 린트는 코드 규칙 위반과 형식 위반을 모두 검사하고, 로컬에서 같은 명령으로 같은 결과를 낸다.
- **FR-020**: 비밀값 검사는 저장소의 기존 검사 규칙(`scripts/preflight.py`와 같은 규칙)과 `git diff --check`를 실행한다.
  결과에는 파일 경로와 규칙 이름만 나오고 값은 나오지 않는다.
- **FR-021**: CI의 세 검사는 저장소 CI 비밀값 없이 돈다. 포크 PR에서도 같은 결과가 나와야 한다.
- **FR-022**: 비밀값 검사의 오탐 예외는 사유를 함께 적은 예외 목록으로만 추가하고, 검사를 끄는 설정은 두지 않는다.
  예외 목록 변경은 PR diff에 드러나 리뷰 대상이 된다(AGENTS.md 9절).

### Key Entities

- **설정 항목**: 이름, 설명, 필수 여부, 비밀 여부, 사용하는 진입점(질의응답·색인·둘 다), 기본값, 형식 규칙.
  비밀 항목은 기본값을 갖지 않는다.
- **진입점**: 질의응답 진입점과 색인 진입점. 진입점마다 필요한 설정 항목 목록과 점검 모드를 가진다.
- **설정 점검 결과**: 진입점, 항목 이름, 상태(통과·누락·형식 오류), 전체 결과. 값은 담지 않는다.
- **검사 결과(CI)**: 검사 종류(테스트·린트·비밀값), 결과(통과·실패·미완료), 실패 위치(테스트 이름 또는 파일 경로와 규칙 이름).
- **응답 샘플**: 외부 API 응답을 저장한 테스트 자료. 출처 API, 저장 일자를 함께 기록하고 비밀값 검사를 통과해야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 저장소를 처음 받은 팀원이 토큰 없이 문서 절차만으로 기본 테스트 통과까지 30분 안에 끝낸다.
  팀원 1명 이상이 실제로 따라 해 걸린 시간을 기록한다.
- **SC-002**: 기본 테스트 실행(로컬·CI)에서 외부 서비스로 나가는 요청이 0건이다.
- **SC-003**: 필수 설정을 빼거나 틀리게 넣은 점검 사례 전부에서 문제 항목이 이름으로 한 번에 보고되고, 넣은 비밀 값이 출력에 나온 사례는 0건이다.
- **SC-004**: 테스트 실패, 린트 위반, 비밀값 샘플을 각각 넣은 PR 세 개에서 해당 검사만 실패하고, 문제 없는 PR에서는 세 검사가 모두 통과한다.
- **SC-005**: PR을 연 뒤 세 검사 결과가 모두 표시될 때까지 10분을 넘지 않는다(골격 단계 기준).
- **SC-006**: 같은 커밋에서 로컬 검사 결과와 CI 검사 결과가 다르게 나온 사례가 0건이다.
- **SC-007**: 로컬 시작 절차를 연속 두 번 실행해도 오류가 없고 로컬 데이터가 남아 있다.

- 질의응답 진입점은 Cloudflare Workers에서, 색인 진입점은 GitHub Actions 또는 로컬 CLI에서 돈다(ADR-008). 두 진입점이 같은 언어를
