## User Scenarios & Testing *(mandatory)*

이 명세의 사용자는 청크를 쓰는 구현자(QK-SYN-001 동기화, QK-EMB-001 임베딩, QK-RET-001 검색·문맥 확장, QK-GEN-001 출처 표시),
코드 청크 위에 교차 관계를 올릴 구현자(QK-CHK-004), 코드 자료원을 등록하고 켜는 운영 담당자, PR 리뷰어다. 최종 수혜자는 Discord에서 "이 API는 어느 서비스 메서드가 처리해?",
"로그인 실패 테스트 있어?", "이 화면의 ViewModel은?" 같은 코드 질문에 출처가 붙은 답을 받는 팀원이다. Phase 2 목표(로드맵 Phase 2 "질문의 대부분을 차지하는 코드")의 색인 쪽 산출물이다.

청커는 보안 필터(QK-SEC-001)를 통과한 Java·Kotlin 소스 파일 하나를 받아, 형식 선언(클래스·인터페이스·열거형·레코드·Kotlin `object` 등)과 멤버(메서드·생성자·필드 등)
단위의 청크 목록으로 바꾼다. 원문 청크는 원본 줄 범위로 되돌아갈 수 있고, 본문 있는 멤버를 가진 형식 선언마다 그 선언의 생김새를 보여 주는 요약 청크를 하나 더 만든다.
청크마다 언어, 패키지, 심볼 경로, 시그니처, 종류, Android 컴포넌트 종류, 테스트 여부 같은 코드 메타데이터를 붙인다. 외부 호출과 저장은 하지 않는다.
코드 청킹은 설정으로 켜기 전까지 운영 색인에 아무 영향을 주지 않고(US6), 코드를 수집할 자료원 두 개는 비활성으로 등록한 뒤 결정 기록과 사람 확인을 거쳐 켠다(US7).

### User Story 1 - 메서드 하나를 물으면 그 메서드 청크가 출처로 나온다 (Priority: P1)

코드 파일은 형식 선언과 멤버 경계로 나뉜다. 메서드 청크에는 그 메서드의 문서 주석, 어노테이션, 시그니처, 본문이 함께 들어가고, 원본 경로와 줄 범위가 있어서
답변의 출처를 눌렀을 때 그 메서드로 갈 수 있다. 메서드 청크의 임베딩 입력에는 감싼 형식 선언의 선언 줄(클래스 어노테이션 포함)이 붙어서,
클래스 수준 `@RequestMapping("/orders")` 같은 맥락도 검색에 쓰인다. 같은 원본과 같은 설정이면 언제 몇 번을 나눠도 같은 청크가 나오고,
메서드 하나의 본문만 고치면 다른 멤버의 청크는 그대로라서 다음 동기화에서 다시 임베딩하지 않는다.

**Why this priority**: C-07(같은 원본·같은 설정이면 같은 청크, 원본 위치로 되돌아갈 수 있음)과 로드맵 1.G·2.G의 증분 동기화 조건을 코드에도 지키는 핵심이다.
Markdown 청커처럼 줄 수로만 자르면 메서드 한가운데서 나뉘어 시그니처 없는 본문 조각이 생긴다 `(추론)`. 검색 문맥 확장은 같은 심볼 경로가 이어지는 첫 청크만 붙이고
바깥 수준 청크는 붙이지 않으므로(QK-RET-001 FR-014, `retrieval/service.py:216`, `0005_retrieval.sql:96-104`), 클래스 맥락은 청크 자체가 가져야 한다.

**Independent Test**: 사람이 기대 청크(줄 범위, 심볼 경로, 종류)를 미리 적어 둔 합성 Java·Kotlin 파일 묶음을 청킹해 기대값과 비교하고, 두 번 청킹해 결과를 비교한다.
원문 청크마다 위치의 줄 범위를 원문에서 잘라 본문과 대조한다. 메서드 하나의 본문만 고친 판, 시그니처를 고친 판, 클래스 어노테이션을 고친 판을 다시 청킹해 바뀐 청크를 센다.

**Acceptance Scenarios**:

1. **Given** 문서 주석과 어노테이션이 붙은 메서드 세 개를 가진 Java 클래스, **When** 청킹한다, **Then** 메서드마다 원문 청크가 하나씩 있고, 각 청크 본문은
   그 메서드의 문서 주석 첫 줄부터 메서드 닫는 줄까지의 원문 그대로다(마지막 메서드 청크에는 클래스의 닫는 줄도 붙는다, FR-010). 심볼 경로는 (`클래스명`, `메서드명(매개변수 형식)`)이다.
2. **Given** 같은 본문과 같은 설정, **When** 두 번 청킹한다, **Then** 청크 수, 순서, 본문, 위치, 심볼 경로, 코드 메타데이터, 검색 헤더, 임베딩 입력 텍스트,
   키워드 검색용 텍스트, 청킹 규칙 버전이 모두 같다.
3. **Given** 청킹한 결과, **When** 원문 청크를 모두 모아 공백 아닌 원문 줄을 센다, **Then** 모든 줄이 정확히 한 원문 청크에 들어 있다(빠짐 0, 겹침 0).
   요약 청크(US2)는 이 셈에서 뺀다.
4. **Given** 메서드 세 개 중 가운데 메서드 본문 한 줄만 고친 판(그 줄은 시그니처 줄이 아니고, 시그니처·문서 주석·어노테이션은 그대로), **When** 다시 청킹한다,
   **Then** 바뀐 청크는 그 메서드의 원문 청크뿐이다. 다른 메서드 청크와 클래스 요약 청크의 본문·심볼 경로·임베딩 입력 텍스트는 바뀌지 않는다(순서 번호와 줄 번호는 바뀔 수 있다).
5. **Given** 가운데 메서드의 매개변수 하나를 바꾼 판, **When** 다시 청킹한다, **Then** 그 메서드의 원문 청크와 클래스 요약 청크만 바뀐다.
6. **Given** 클래스 어노테이션 `@RequestMapping("/orders")`가 붙은 컨트롤러의 메서드, **When** 청킹한다, **Then** 그 메서드 청크의 임베딩 입력 텍스트와 키워드 검색용 텍스트에
   클래스 어노테이션과 선언 줄이 들어 있고, 청크 본문에는 없다. 클래스 어노테이션을 고친 판에서는 그 클래스의 모든 멤버 청크와 요약 청크의 임베딩 입력 텍스트가 바뀐다.
7. **Given** 중첩 클래스 안의 메서드, **When** 청킹한다, **Then** 심볼 경로는 (`바깥 클래스`, `중첩 클래스`, `메서드(…)`)이고, 임베딩 입력 텍스트에는 바깥 클래스와 중첩 클래스의
   선언 줄이 바깥부터 차례로 붙는다.
8. **Given** 줄 바꿈 문자만 다른(CRLF·LF) 두 본문, 그리고 앞에 BOM이 붙은 본문, **When** 청킹한다, **Then** 위치 줄 번호와 청크 내용이 같다.

### User Story 2 - 클래스 요약으로 "이 클래스에 뭐가 있어?"에 답한다 (Priority: P1)

본문 있는 멤버(메서드·생성자·초기화 블록·중첩 형식 선언, FR-013)를 가진 형식 선언마다 요약 청크를 만든다. 요약 청크는 그 선언의 문서 주석, 어노테이션, 선언 줄, 필드 선언, 멤버 시그니처를 원문 줄 순서대로 모은 것이다.
메서드 본문은 넣지 않는다. 요약 청크는 독립 검색 대상이다. "OrderService에는 어떤 메서드가 있어?", "이 컨트롤러가 받는 경로는?" 같은 질문은 요약 청크 하나로 근거를 얻는다.

**Why this priority**: 로드맵 2.2가 "클래스 요약"을 명시한다. 메서드 청크만 있으면 클래스 전체의 모양을 묻는 질문에 청크 수십 개가 필요하고,
Context 예산(QK-RET-001, 2,000토큰)에 다 들어가지 않는다 `(추론)`. 검색 문맥 확장은 요약 청크를 메서드 청크의 상위로 붙이지 않는다(US1 근거). 요약은 질문이
클래스 모양을 물을 때 직접 검색되는 것으로만 쓰인다.

**Independent Test**: 필드·생성자·메서드·중첩 클래스를 섞은 합성 클래스, 멤버가 매우 많아 요약이 상한을 넘는 클래스, Kotlin 파일 최상위 함수만 있는 파일을 청킹해
요약 청크의 본문, 위치, 순서를 확인한다.

**Acceptance Scenarios**:

1. **Given** 필드 2개, 생성자 1개, 메서드 3개를 가진 클래스, **When** 청킹한다, **Then** 요약 청크 하나가 그 클래스의 원문 청크들보다 순서가 앞서고,
   본문은 클래스 문서 주석·어노테이션·선언 줄, 필드 선언 줄, 생성자·메서드 시그니처 줄을 원문 순서대로 담으며, 시그니처 줄이 아닌 메서드 본문 줄은 없다.
2. **Given** 요약 청크, **When** 본문의 각 줄을 원문과 대조한다, **Then** 모든 줄이 그 클래스 줄 범위 안의 원문 줄과 같다. 요약 청크의 위치는 클래스 전체 줄 범위이고
   요약 청크 표시가 있다.
3. **Given** 멤버 시그니처만으로 상한을 넘는 클래스(멤버 하나의 시그니처 줄은 헤더·선언 줄과 합쳐 상한 이하), **When** 청킹한다, **Then** 요약 청크가 멤버 경계에서
   여럿으로 나뉘고, 뒤 조각의 임베딩 입력 텍스트에는 선언 줄이 반복해 붙는다. 상한을 넘는 요약 청크는 없다.
4. **Given** 블록 본문(`{ … }`, 여러 줄)을 가진 최상위 함수 두 개와 최상위 프로퍼티 하나만 있는 Kotlin 파일 `Slugs.kt`, **When** 청킹한다, **Then** 심볼이 `Slugs.kt`인 파일 요약 청크 하나와
   함수마다 원문 청크, 프로퍼티 묶음 원문 청크가 있다.
5. **Given** 메서드를 가진 중첩 클래스가 있는 클래스, **When** 청킹한다, **Then** 바깥 클래스 요약에는 중첩 클래스의 선언 줄만 들어가고, 중첩 클래스는 자기 요약 청크를 따로 갖는다.
6. **Given** 필드와 한 줄 접근자만 있는 DTO 클래스, 구성 요소만 있는 레코드, 추상 메서드만 있는 인터페이스, **When** 청킹한다, **Then** 요약 청크가 없고,
   DTO는 형식 선언 머리와 첫 필드 묶음이 한 원문 청크다.

### User Story 3 - 코드 메타데이터로 청크가 무엇인지 안다 (Priority: P1)

청크마다 언어, 패키지, 심볼 이름과 심볼 경로, 시그니처, 청크 종류, 형식 선언 종류, 어노테이션 이름 목록, 테스트 여부, Android 컴포넌트 종류를 붙인다.
이 값은 청크와 함께 저장되고, 검색 결과의 출처 정보로 돌아와 답변 출처 표시와 이후 필터(QK-TRK-001), 교차 관계(QK-CHK-004)에 쓰인다.

**Why this priority**: QK-STO-001이 "코드 전용 메타데이터(심볼, 시그니처 등)는 Phase 2 QK-CHK-001에서 추가한다"고 넘겼다(그 명세 Assumptions).
메타데이터가 없으면 QK-CHK-004가 "컨트롤러 메서드 ↔ API 경로"를 다시 소스에서 파싱해야 한다 `(추론)`.

**Independent Test**: 어노테이션·제네릭·기본값 매개변수·확장 함수·`suspend` 함수·Kotlin 백틱 이름 메서드·오버로드를 담은 합성 파일을 청킹해, 청크별 메타데이터를
기대값과 비교한다. 저장 후 검색 결과의 출처 정보에서 같은 값을 다시 읽는다.

**Acceptance Scenarios**:

1. **Given** `@GetMapping("/orders/{id}") public ResponseEntity<OrderResponse> getOrder(@PathVariable Long id)` 메서드, **When** 청킹한다, **Then** 그 청크의
   종류는 메서드, 심볼 이름은 `getOrder(Long)`, 시그니처는 `public ResponseEntity<OrderResponse> getOrder(@PathVariable Long id)`, 어노테이션 이름 목록은 (`GetMapping`)이다.
   선언에 붙은 어노테이션 인자 원문은 본문에 그대로 있다.
2. **Given** Kotlin 확장 함수 `fun String.toSlug(): String`, **When** 청킹한다, **Then** 심볼 이름은 `String.toSlug()`이고 시그니처에 수신 형식 `String.`이 남는다.
3. **Given** 백틱 이름 테스트 함수 `` fun `로그인에 실패하면 오류를 보여 준다`() ``, **When** 청킹한다, **Then** 심볼 이름은 백틱을 뺀 한국어 문장에 `()`를 붙인 값이다.
4. **Given** 같은 이름의 오버로드 메서드 `find(Long)`과 `find(String)`이 이어져 있는 클래스, **When** 청킹한다, **Then** 두 청크의 심볼 경로가 서로 다르다.
5. **Given** 저장된 코드 청크, **When** 검색 결과로 다시 읽는다, **Then** 출처 정보에 언어, 심볼 경로, 시그니처, 종류가 있고 Markdown 청크의 출처 정보는 바뀌지 않는다.

### User Story 4 - Android 컴포넌트와 테스트를 구분한다 (Priority: P2)

Android 저장소의 화면·상태 관리 코드와 두 저장소의 테스트 코드를 구분해 표시한다. "로그인 화면 ViewModel은?", "주문 취소 테스트 있어?" 같은 질문에서
청크의 종류가 검색 헤더와 메타데이터에 드러난다. 테스트 메서드의 표시 이름(`@DisplayName` 값, Kotlin 백틱 이름)은 한국어 질문과 이어지는 단서라 검색 헤더에 넣는다.

**Why this priority**: 로드맵 2.2와 백로그 제목이 Android 컴포넌트와 테스트를 명시한다. 인벤토리 기준 테스트 코드가 Java 테스트 308개 파일·2,841 KB로
본문 코드(738개·1,756 KB)보다 크고, Android 저장소에는 설계 문서가 거의 없어 질문은 코드에서 답을 찾아야 한다(인벤토리 1.3절).
다만 판정이 틀려도 청크 자체는 검색되므로 P2로 둔다.

**Independent Test**: `AppCompatActivity`·`Fragment`·`ViewModel`을 직접 상속한 클래스, 프로젝트 기반 클래스(`BaseFragment`)를 상속한 클래스, `@Composable` 함수,
Android import가 없는 Spring `OrderServiceImpl extends BaseService`, 다중 모듈 경로의 `src/test`·`src/integrationTest`·`src/androidTest` 테스트,
테스트 경로에 있지만 테스트 어노테이션이 없는 도우미 클래스, 테스트 경로 밖의 `ABTest` 클래스를 넣은 합성 묶음을 청킹한다.

**Acceptance Scenarios**:

1. **Given** `androidx.lifecycle.ViewModel`을 import한 `class LoginViewModel : ViewModel()`, **When** 청킹한다, **Then** 그 형식 선언과 멤버 청크의 Android 컴포넌트 종류는 ViewModel이다.
2. **Given** `androidx.` import가 있는 파일의 `class HomeFragment : BaseFragment<...>()`(기반 클래스는 다른 파일), **When** 청킹한다, **Then** 이름 규칙(FR-024)으로 Fragment로 판정한다.
   이름 규칙에도 맞지 않는 간접 상속은 컴포넌트 종류 없음이고 실패가 아니다.
3. **Given** Android import가 없는 Java 파일의 `class OrderServiceImpl extends BaseService implements OrderService`, **When** 청킹한다, **Then** Android 컴포넌트 종류는 없음이다.
4. **Given** `@Composable fun LoginScreen(...)`, **When** 청킹한다, **Then** 그 함수 청크의 Android 컴포넌트 종류는 Composable이다.
5. **Given** `order/src/test/java/.../OrderServiceTest.java`의 `@Test @DisplayName("재고가 없으면 주문을 거절한다") void rejectsWhenOutOfStock()`, **When** 청킹한다,
   **Then** 그 청크의 종류는 메서드이고, 테스트 코드 여부와 테스트 메서드 여부가 참이며, 검색 헤더에 표시 이름 `재고가 없으면 주문을 거절한다`가 들어간다.
6. **Given** 테스트 경로에 있는 고정값 도우미 클래스(테스트 어노테이션 없음)와 테스트 경로 밖의 `ABTest` 클래스, **When** 청킹한다, **Then** 도우미 클래스 청크는 테스트 코드이지만
   테스트 메서드가 아니고, `ABTest` 청크는 테스트 코드가 아니다.

### User Story 5 - 코드 청크도 상한 안으로 나뉘고, 한 파일의 실패가 동기화를 멈추지 않는다 (Priority: P2)

상한을 넘는 원문 청크(긴 메서드, 열거형 상수가 많은 선언 머리, `import`가 많은 파일 머리, 대체 청크)는 줄 경계에서 나뉘고, 뒤 조각에는 그 청크의 선언 줄이 반복해 붙는다.
구문을 해석할 수 없는 파일은 줄 단위 대체 청킹으로 검색에서 빠지지 않게 하고 경고를 남긴다. 원문은 잘라 버리지 않는다.

**Why this priority**: QK-EMB-001은 한도 초과 입력을 자르지 않고 알리기만 하고(그 명세 FR-003), C-08은 한 문서의 실패가 전체 동기화를 멈추지 않을 것을 요구한다.
코드에는 Markdown보다 긴 줄(인코딩된 상수, 긴 문자열)과 처리기가 모르는 문법이 나올 수 있다 `(추론)`.

**Independent Test**: 상한의 몇 배인 메서드, 상수가 아주 많은 열거형, `import`가 아주 많은 파일, 상한보다 긴 한 줄이 든 파일, 괄호가 맞지 않는 파일, 처리기가 모르는 문법을 쓴 파일을 담은 묶음을
작은 시험용 상한으로 청킹한다.

**Acceptance Scenarios**:

1. **Given** 예상 토큰이 상한의 3배이고 어느 한 줄도 헤더·반복 줄과 합쳐 상한을 넘지 않는 메서드, **When** 청킹한다, **Then** 줄 경계에서 나뉜 조각 여럿이 같은 심볼 경로를 갖고,
   첫 조각에 시그니처가 있으며, 뒤 조각의 임베딩 입력 텍스트는 검색 헤더·형식 선언 맥락 줄 다음에 반복 시그니처 줄이 오고, 모든 조각이 상한 이하다. 메서드 닫는 줄은 마지막 조각에 있다.
2. **Given** 상수 줄만으로 상한을 넘는 열거형 선언 머리(각 줄은 헤더·선언 줄과 합쳐 상한 이하), **When** 청킹한다, **Then** 줄 경계에서 나뉘고 뒤 조각의 임베딩 입력 텍스트에 선언 줄이 붙는다.
3. **Given** 검색 헤더와 따로는 상한 이하지만 헤더를 붙이면 상한을 넘는 한 줄이 든 파일, **When** 청킹한다, **Then** 그 파일은 청크 0개와
   "청킹 실패(줄 길이 초과)"이고 같은 실행의 다른 파일은 정상 처리된다.
4. **Given** 괄호가 맞지 않아 구조를 해석할 수 없는 파일, **When** 청킹한다, **Then** 파일 전체가 줄 단위 대체 청크로 나오고(심볼 경로는 비어 있고 종류는 대체 청크)
   "구문 해석 실패" 경고가 붙는다. 원문 줄 빠짐은 0이다.
5. **Given** 처리 중 예상하지 못한 오류가 나는 파일, **When** 청킹한다, **Then** 그 파일은 청크 0개와 "청킹 실패(처리 오류)"이고 다른 파일은 처리된다.
6. **Given** 중첩 클래스 안 메서드에서 바깥 클래스의 긴 어노테이션 묶음 때문에 검색 헤더·맥락 줄·한 줄 합이 상한을 넘는 파일(자기 형식의 맥락 줄만 붙이면 상한 이하),
   **When** 청킹한다, **Then** 파일은 실패하지 않고, 그 청크의 임베딩 입력 텍스트에서 바깥 형식의 맥락 줄이 빠지며 "맥락 줄 생략" 경고가 붙는다.

### User Story 6 - 코드 청킹은 켜기 전까지 운영 색인을 바꾸지 않는다 (Priority: P1)

코드 청킹은 설정으로 켜고 끈다. 기본값은 꺼짐이다. 꺼져 있으면 코드 자료는 지금처럼 "대상 아님"이고, 인덱스 버전과 Markdown 청킹 결과가 지금과 한 글자도 다르지 않아
운영 동기화가 그대로 돈다. 켜면 코드 청킹 규칙 버전이 인덱스 버전에 들어가 새 인덱스 버전이 생기며, 그 버전의 생성·평가·활성화는 QK-STO-002 절차를 거친다.

**Why this priority**: QK-SYN-001은 활성 인덱스 버전과 현재 설정의 인덱스 버전이 다르면 바뀐 문서 처리를 멈추고 "인덱스 버전 불일치"로 보고한다(그 명세 FR-020).
인덱스 버전 계산(`sync/keys.py:18-26`, `sync/run.py:43-45`)에 코드 청킹 규칙 버전을 무조건 넣으면, 코드 자료원을 켜지 않아도 배포하는 순간 Markdown 자료원까지 모든 운영 동기화가 멈춘다.
새 버전을 만들고 활성화할 QK-STO-002(WBS 2.1)는 아직 명세가 없다(2026-10-26 사용자 결정, TASK.md).

**Independent Test**: 코드 청킹을 끈 설정과 켠 설정으로 같은 Markdown·코드 혼합 묶음을 청킹하고 인덱스 버전을 계산해, 끈 설정의 값이 지금 값과 같은지와 켠 설정의 값이 다른지 본다.

**Acceptance Scenarios**:

1. **Given** 코드 청킹이 꺼진 기본 설정, **When** 지금 운영 설정으로 인덱스 버전을 계산한다, **Then** 값은 지금과 같은 `iv-4c0bc4fcc642`이고, Markdown 청킹 규칙 버전과
   메타데이터 스키마 버전(`meta-v1`)도 지금과 같으며, 저장 스키마에 적용되는 마이그레이션이 늘지 않는다.
2. **Given** 코드 청킹이 꺼진 설정, **When** `.java`·`.kt` 자료를 청킹한다, **Then** 결과는 청크 0개와 "대상 아님"이다.
3. **Given** 코드 청킹을 켠 설정, **When** 인덱스 버전을 계산한다, **Then** 꺼진 설정의 값과 다르다. Markdown 청킹 규칙 버전이나 코드 청킹 규칙 버전 중 하나만 바꿔도 값이 바뀐다.
4. **Given** 코드 청킹을 켠 설정에서 코드 문서와 Markdown 문서가 섞인 자료원, **When** 변경 없이 두 번 동기화를 계획한다, **Then** 두 번째 계획에서 다시 처리로 판정된 문서 수는 0이다.
5. **Given** 코드 청킹을 켰지만 그 인덱스 버전이 키워드 규칙 대응표에 없는 설정, **When** 설정 검사와 동기화 실행을 한다, **Then** 둘 다 오류로 멈추고 원본 호출·청킹·저장은 0건이다.

### User Story 7 - 코드 자료원을 등록하고, 결정 기록과 사람 확인을 거쳐 켠다 (Priority: P2)

백엔드 저장소 코드와 Android 저장소 코드를 수집할 자료원을 각각 하나씩 비활성으로 등록한다. 포함·제외 패턴, 테스트 코드 포함 여부, 예상 비용, 데이터 처리 정책을
결정 기록에 남기고, 사람이 개인 정보를 확인한 기록을 쓴 뒤에만 켠다. 기존 Markdown 자료원 `dnd-backend-docs`의 범위와 확인 기록은 바꾸지 않는다.

**Why this priority**: AGENTS.md 3.1은 새 자료원을 더할 때 데이터 처리 정책을 확인하고 결정 기록을 남기게 한다. QK-ING-002 research R-13·R-16은 활성화를
결정 기록 → 사람의 개인 정보 확인 → 확인 기록 → `enabled = true` → `sources check` → 측정의 여섯 단계로 정했다(`config/source_reviews/README.md`).
청커가 있어도 자료원이 없으면 코드 질문에 답할 수 없다. 켜는 일은 US6의 인덱스 버전 활성화와 함께 사람이 정하므로 P2로 둔다.

**Independent Test**: 비활성 자료원 두 개를 등록한 설정으로 설정 검사(`qk-index sources check` 동등)를 돌리고, 포함 패턴 확장자 검사, 다른 자료원과의 범위 겹침, 기존 자료원 범위 불변을 확인한다.

**Acceptance Scenarios**:

1. **Given** 비활성으로 등록한 두 코드 자료원, **When** 설정 검사를 한다, **Then** 확장자 오류(`UNKNOWN_EXTENSION`)와 설정 오류가 0건이고, 비활성이라 확인 기록이 없어도 통과한다.
2. **Given** 백엔드 코드 자료원과 `dnd-backend-docs`, **When** 두 자료원의 포함 패턴으로 같은 저장소 트리(고정 커밋 목록)를 고른다, **Then** 두 자료원이 함께 고르는 파일 수는 0이다.
   지금 설정 검사에는 범위 겹침 검사가 없으므로(`sources/config.py`) 확인 방법은 `plan.md`에서 정한다.
3. **Given** 등록 뒤의 `config/sources.toml`과 `config/source_reviews/dnd-backend-docs.toml`, **When** 등록 전과 비교한다, **Then** `dnd-backend-docs`의 범위와 확인 기록은 바뀌지 않았다.
4. **Given** 코드 자료원 결정 기록, **When** 리뷰한다, **Then** 자료원·범위, 테스트 코드 포함 여부와 근거, 읽기 전용 토큰 권한, 외부로 나가는 데이터와 데이터 처리 정책(ADR-002 공급자),
   예상 첫 색인 Neurons와 하루 예산 대비, 활성화 순서(자료원별 식별 선행 명세, QK-STO-002 인덱스 버전 활성화, 한 번에 자료원 하나씩)가 있다.

---

### Edge Cases

- 빈 파일, 공백만 있는 파일: 청크 0개이고 실패가 아니다. "빈 문서"로 센다(QK-CHK-002와 같다).
- 패키지 선언·`import`·파일 머리 주석만 있는 파일: 파일 머리 청크 하나만 나온다. 요약 청크는 없다.
- 한 파일에 최상위 형식 선언이 여러 개(Java의 비공개 형식, Kotlin 파일 여러 클래스): 각각 독립 형식 선언으로 원문 청크와 (FR-013 조건을 만족하면) 요약 청크를 만든다.
- 익명 클래스, 람다, 지역 함수·지역 클래스: 감싼 메서드 본문의 일부로 다룬다. 따로 청크나 심볼을 만들지 않는다.
- 열거형 상수, 레코드 구성 요소, Kotlin 주 생성자 프로퍼티: 형식 선언 머리 원문 청크에 들어가고, 그 형식에 요약 청크가 있으면(FR-013) 요약에도 들어간다. `companion object`는 중첩 형식 선언(심볼 이름 `Companion` 또는 붙인 이름)이다.
- 형식 선언의 닫는 줄(`}`)과 멤버 사이의 빈 줄·단독 주석: 원문 줄이 빠짐 없이 한 원문 청크에 들어가도록 바로 앞 원문 청크에 붙인다(FR-010).
  멤버에 붙지 않은 단독 주석 묶음은 다음 멤버의 문서 주석이 아니면 앞 청크에 붙는다.
- 형식 선언 문서 주석만 고친 판: 형식 선언 머리 원문 청크가 바뀌고, 그 형식에 요약 청크가 있으면(FR-013) 요약 청크도 바뀐다. 멤버 문서 주석만 고친 판: 그 멤버 원문 청크만 바뀐다(요약에는 멤버 문서 주석이 없다).
- 한 줄 본문 선언(`void f() { return x; }`, Kotlin `fun f() = g()`): 시그니처 줄과 본문이 같은 줄이라 본문 수정이 요약 청크도 바꾼다. 원문 줄을 그대로 담는 원칙(FR-013)을 지키려고 받아들인다.
- 생성 코드(`@Generated`, "자동 생성" 머리 주석): 특별 처리하지 않고 같은 규칙으로 청킹한다. 색인에서 뺄지는 자료원 제외 패턴으로 정한다(FR-033).
- 대상 확장자가 아닌 코드 파일(`.py`, `.ts`, `.kts`, `.gradle` 등): 처리하지 않고 "대상 아님"이다. 지금 GitHub 수집기는 `.kts`·`.gradle`을 코드로 분류하지 않는다(`adapters/github.py:178-203`).
- 비밀값: 청커는 QK-SEC-001을 통과한 자료만 받는다. 비밀값 규칙에 걸린 파일은 파일 전체가 빠진다(QK-SEC-001 FR-011). 요약 청크의 임베딩 입력 텍스트도 다른 청크처럼
  임베딩 직전 검사(QK-SEC-001 FR-013)를 받는다. 테스트 코드의 가짜 토큰이 파일 전체를 빼는 사례가 많을 수 있어 plan에서 대상 저장소로 센다.
- 코드 주석·문자열 안의 지시문("이 코드를 무시하고…"): 청커는 원문 그대로 담고 해석하지 않는다. 지시문을 데이터로만 다루는 일은 QK-GEN-001이 한다(C-03).
- 파일 이름이나 경로가 바뀐 파일: 검색 헤더에 위치가 들어가므로 모든 청크의 임베딩 입력 텍스트가 바뀐다. 다시 임베딩하는 것이 맞다.
- 매우 큰 파일(수천 줄): 멤버 경계 규칙은 그대로이고, 성능 기준(SC-012)은 파일 수가 아니라 전체 대상 규모로 잰다.

## Requirements *(mandatory)*

### Functional Requirements

**공통**

- **FR-001**: 입력은 QK-SEC-001 필터를 통과한 자료다. 코드 청킹이 켜져 있고(FR-030) 본문 형식이 코드이며 위치의 확장자가 `java` 또는 `kt`인 자료만 이 청커가 청킹한다.
  나머지 코드 자료와 코드 청킹이 꺼져 있을 때의 코드 자료는 청크 0개와 "대상 아님"이다. Markdown 자료는 지금처럼 QK-CHK-002 청커가 맡는다.
- **FR-002**: 자료를 청커에 나눠 주는 규칙을 바꿔도 Markdown 자료의 청킹 결과(청크, 검색 헤더, 임베딩 입력 텍스트, 키워드 검색용 텍스트, Markdown 청킹 규칙 버전)는
  한 글자도 바뀌지 않는다.
- **FR-003**: 청킹 결과는 입력 본문, 원본 위치, 청킹 설정으로만 정해진다. 자료원 종류·자료원 이름에 따라 규칙이 갈리지 않고(C-06), 실행 시각·처리 순서·실행 환경에
  따라 달라지지 않는다. 다른 파일의 내용(상위 형식 선언 등)을 읽지 않고 파일 하나만으로 정한다.
- **FR-004**: 청커는 외부 API를 호출하지 않고, 원본에 쓰지 않고, 저장하지 않는다(C-09). 저장은 QK-SYN-001이 한다.
- **FR-005**: 파일 하나의 결과는 청크 목록(1개 이상), 빈 문서, 대상 아님, 청킹 실패 중 하나다. 청킹 실패에는 정해진 실패 유형(줄 길이 초과, 헤더 길이 초과,
  처리 오류)만 붙는다. 실패한 파일은 일부 청크만 내지 않는다. 청크 목록 결과에는 구조 경고(FR-019)가 0개 이상 붙을 수 있다.
- **FR-006**: 파일 하나의 실패가 같은 실행의 다른 파일 처리를 멈추지 않는다(C-08).
- **FR-007**: 청커가 내는 기록·오류·경고·요약에는 본문 원문, 시그니처, 심볼 이름을 넣지 않는다. 자료 식별자·위치는 QK-SEC-001 기록 출력 규칙(그 명세 FR-023)을 거친다.
- **FR-008**: 청킹 전에 줄 바꿈을 LF로 통일하고 본문 앞 BOM을 뺀다. 그 밖에는 원문을 바꾸지 않는다. 줄 번호는 원문의 1번 줄부터 센다.
  코드 청킹 결과의 문서 제목은 원본 위치의 파일 이름(확장자 포함)이다.

**원문 청크와 원본 위치 (US1)**

- **FR-009**: 청크는 원문 청크와 요약 청크(FR-013) 두 가지다. 원문 청크마다 원본 위치와 시작·끝 줄 번호(양 끝 포함)를 갖고, 본문은 그 줄 범위의 원문 그대로다.
  원문의 공백 아닌 줄은 모두 정확히 한 원문 청크에 들어가고 원문 청크끼리 겹치지 않는다. 청크 앞뒤의 빈 줄은 본문과 줄 범위에서 뺀다.
- **FR-010**: 원문 청크의 단위는 다음과 같다. (1) 파일 머리: 첫 형식 선언(또는 Kotlin 최상위 선언) 앞의 줄. (2) 형식 선언 머리: 형식 선언의 문서 주석·어노테이션·선언 줄부터
  첫 멤버 앞까지(Java 열거형 상수, Kotlin 주 생성자 포함). 첫 멤버가 필드·프로퍼티 선언이면 형식 선언 머리와 (4)의 첫 필드 묶음을 한 원문 청크로 합친다
  (종류는 형식 선언 머리, 2026-10-26 사용자 결정, plan research R-04). (3) 멤버: 메서드·생성자·초기화 블록·Kotlin 최상위 함수는 문서 주석·어노테이션부터 닫는 줄까지 하나다.
  (4) 연속한 필드·프로퍼티 선언(Kotlin 최상위 프로퍼티 포함)은 목표 크기(FR-016) 안에서 한 청크로 묶는다. (5) 중첩 형식 선언은 (2)~(4)를 다시 적용한다.
  형식 선언의 닫는 줄과 멤버 사이의 단독 주석은 바로 앞 원문 청크에 붙는다. 서로 다른 메서드·생성자를 한 청크로 합치지 않는다. 상한을 넘는 원문 청크는 FR-017로 나눈다.
- **FR-011**: 그래서 원본 위치, 파일 머리, 형식 선언 머리가 그대로이고 한 멤버의 본문 줄(시그니처 줄이 아닌 줄)만 바뀌면 그 멤버의 원문 청크만 바뀐다. 멤버의 시그니처·선언 어노테이션이 바뀌면
  그 멤버 원문 청크와 감싼 형식 선언의 요약 청크가 바뀐다. 멤버 문서 주석만 바뀌면 그 멤버 원문 청크만 바뀐다. 형식 선언의 어노테이션·선언 줄이 바뀌면 그 형식 선언 안의
  모든 청크의 임베딩 입력 텍스트가 바뀐다(FR-021). 원본 위치가 바뀌면 모든 청크의 검색 헤더가 바뀐다.
- **FR-012**: 청크 순서는 파일 안에서 0부터 빈틈없이 매긴다. 파일 머리 청크가 맨 앞이고, 파일 요약 청크(FR-014)는 그 다음, 형식 선언의 요약 청크는 그 형식 선언의
  첫 원문 청크 바로 앞에 오고, 나머지는 원문 순서다. 결과의 청크 항목은 QK-STO-001 청크 입력 검증을 그대로 통과한다.

**요약 청크 (US2)**

- **FR-013**: 본문이 있는 멤버가 하나 이상인 형식 선언마다 요약 청크를 하나 이상 만든다. 본문이 있는 멤버는 메서드·생성자·초기화 블록 가운데 본문 줄이 시그니처 줄 밖에 있는 것과
  중첩 형식 선언이다(중첩 형식만 담은 컨테이너 형식은 생김새가 원문 청크 하나에 모이지 않으므로 요약을 둔다). 그런 멤버가 없는 형식 선언(필드·프로퍼티·추상 메서드·한 줄 선언만 있는
  DTO, 레코드, 인터페이스 등)은 형식 선언 머리 원문 청크가 이미 생김새를 담으므로 요약 청크를 만들지 않는다(2026-10-26 사용자 결정, plan research R-04). 본문은 그 형식 선언의 문서 주석, 어노테이션, 선언 줄, 필드·프로퍼티 선언 줄, 멤버(생성자·메서드·중첩 형식)의
  선언 어노테이션과 시그니처 줄을 원문 순서대로 모은 원문 줄이다. 메서드 본문, 여러 줄 필드 초기값의 나머지 줄, 멤버 문서 주석은 넣지 않는다.
  시그니처 줄은 선언이 시작하는 줄부터 본문을 여는 줄(`{`나 Kotlin 식 본문의 `=`가 있는 줄)까지이고, 본문이 없는 선언(추상 메서드, 인터페이스 메서드)은 선언 전체다.
  요약 청크의 위치는 형식 선언 전체 줄 범위이고 요약 청크 표시를 갖는다. 요약 청크 본문의 모든 줄은 그 범위 안의 원문 줄과 같다.
- **FR-014**: Kotlin 파일에 본문 줄이 시그니처 줄 밖에 있는 최상위 함수가 하나 이상 있으면 파일 이름(확장자 포함)을 심볼로 쓰는 파일 요약 청크를 만든다.
  최상위 프로퍼티·한 줄 함수만 있는 파일(상수 파일 등)은 파일 요약을 만들지 않는다(FR-013과 같은 규칙, 2026-10-26 사용자 결정). 본문은 최상위 함수·프로퍼티의 시그니처 줄이고,
  위치는 파일 전체 줄 범위다.
- **FR-015**: 요약 청크가 상한(FR-016)을 넘으면 멤버 경계에서 여럿으로 나눈다. 뒤 조각의 임베딩 입력 텍스트에는 형식 선언의 선언 줄을 반복해 붙인다.
  요약 청크는 원문 줄 셈(FR-009)에서 빠진다.

**크기 (US5)**

- **FR-016**: 크기, 상한, 목표 크기, 예상 토큰 계산은 QK-CHK-002 FR-013·FR-014와 같은 정의를 쓴다(임베딩 입력 텍스트의 예상 토큰, bge-m3 입력 한도에서 안전 여유를 뺀 상한).
  코드용 상한과 목표 크기는 따로 둘 수 있고, 코드용 상한은 검색 Context 예산(QK-RET-001, 지금 2,000토큰)보다 크지 않아야 한다. 그보다 큰 청크는 검색되어도
  Context에 들어가지 못한다(`retrieval/pack.py:63-64`, `LARGER_THAN_BUDGET`). 상한이 예산과 같으면 그 크기 청크는 첫 중심 청크일 때만 들어가므로, 초기값은 예산보다 여유 있게 작게 고른다.
  예산은 설정으로 바꿀 수 있으므로(`domain/retrieval.py`) 두 설정 사이 검사를 어디에 둘지, 초기값, 안전 여유의 근거(대상 코드의 실제 토크나이저 토큰 수와 예상 토큰 수 비교)는 `plan.md`에서 정한다.
- **FR-017**: 상한을 넘는 원문 청크(멤버, 형식 선언 머리, 파일 머리, 필드 묶음, 대체 청크)는 그 안의 줄 경계에서 목표 크기 근처로 나눈다. 멤버는 가능하면 최상위 문장 경계
  (괄호 깊이가 멤버 본문 첫 단계인 줄의 끝)를 고르고, 없으면 아무 줄 경계를 고른다. 뒤 조각의 임베딩 입력 텍스트에는 반복 줄을 붙인다. 반복 줄은 멤버면 시그니처 줄,
  형식 선언 머리와 필드 묶음이면 형식 선언의 선언 줄이고, 파일 머리와 대체 청크는 없다. 나뉜 조각은 같은 심볼 경로와 메타데이터를 갖는다. 줄 중간에서 나누지 않는다.
- **FR-018**: 크기 판정은 "검색 헤더 + 형식 선언 맥락 줄(FR-021) + 반복 줄 + 후보 본문"으로 한다. 이 합이 상한을 넘으면 먼저 맥락 줄을 바깥 형식부터 형식 단위로 빼고,
  뺀 청크에 "맥락 줄 생략" 구조 경고(줄 번호)를 붙인다. 맥락 줄은 원문 청크가 아닌 보조 텍스트라 빼도 원문 보존 원칙과 충돌하지 않는다. 맥락 줄을 모두 빼도
  검색 헤더만으로 상한에 닿으면 "청킹 실패(헤더 길이 초과)", 원문 한 줄에 검색 헤더·반복 줄을 붙여 상한을 넘으면 "청킹 실패(줄 길이 초과)"이고 그 파일 전체가 실패다.
  원문을 버리거나 잘라 담지 않는다(QK-CHK-002 FR-015와 같다). 맥락 줄 생략 규칙은 청크를 바꾸므로 코드 청킹 규칙 버전의 재료다(FR-027).

**구문 해석 실패 (US5)**

- **FR-019**: 형식 선언·멤버 경계를 해석할 수 없는 곳이 하나라도 있는 파일(괄호 불일치, 처리기가 모르는 문법)은 실패시키지 않고 파일 전체를 줄 단위 대체 청킹한다.
  대체 청크는 빈 줄로 나뉜 블록 사이에서 목표 크기 근처로 나눈 원문 청크이고, 심볼 경로는 비어 있으며 종류는 대체 청크다. 요약 청크는 만들지 않는다.
  결과에 "구문 해석 실패" 구조 경고를 붙인다. 대체 청킹도 FR-009·FR-017·FR-018을 지킨다. 이 판정은 청크를 바꾸므로 판정 규칙은 코드 청킹 규칙 버전의 재료다(FR-027).

**심볼 경로와 검색 헤더 (US1·US3)**

- **FR-020**: 심볼 경로는 청크가 속한 형식 선언부터 멤버까지 바깥에서 안쪽 순서의 심볼 이름 목록이고, 저장 스키마의 제목 경로 자리에 넣는다. 청크 종류별 심볼 이름과 심볼 경로는 다음과 같다.

  | 청크 종류 | 심볼 이름 | 심볼 경로 |
  | --- | --- | --- |
  | 파일 머리 | 없음 | 빈 목록 |
  | 파일 요약 | 파일 이름(확장자 포함) | (파일 이름) |
  | 형식 요약, 형식 선언 머리 | 형식 이름 | (바깥 형식들…, 형식 이름) |
  | 메서드, 생성자, 최상위 함수 | 이름 + `(`매개변수 형식 목록`)` | (바깥 형식들…, 심볼 이름). 최상위 함수는 (파일 이름, 심볼 이름) |
  | 필드 묶음 | 첫 필드 이름 | (바깥 형식들…, 첫 필드 이름) |
  | 최상위 프로퍼티 묶음 | 첫 프로퍼티 이름 | (파일 이름, 첫 프로퍼티 이름) |
  | 초기화 블록 | `<init>` 또는 `<clinit>`(정적) | (바깥 형식들…, 심볼 이름) |
  | 대체 청크 | 없음 | 빈 목록 |

  매개변수 형식 목록은 선언 순서대로 각 매개변수의 형식 원문에서 어노테이션·이름·기본값·수식어(`final`, `vararg`)를 빼고 공백을 없앤 값을 쉼표로 이은 것이다
  (`find(Long)`, `of(String,List<Int>)`, Kotlin `onClick: () -> Unit` → `()->Unit`, `content: @Composable () -> Unit` → `()->Unit`). 함수 형식·괄호 형식도 형식 원문 전체를 쓴다. 가변 인자는 `형식...`(Java `String...`, Kotlin `vararg xs: String` → `String...`), nullable 표시 `?`는 남기고, 형식 이름은 원문대로
  쓴다(패키지까지 쓴 이름도 그대로, 이름 해석은 하지 않는다). Kotlin 확장 함수는 이름 앞에 수신 형식을 붙인다(`String.toSlug()`). 생성자 이름은 형식 이름이다.
  Kotlin 백틱 이름은 백틱을 뺀다. 그래서 오버로드와 수신 형식만 다른 확장 함수도 심볼 경로가 다르다. 그래도 같은 심볼 경로가 이어지는 드문 경우는 위치와 시그니처로 구분하고,
  문맥 확장이 앞 청크를 절 첫 청크로 붙이는 한계를 받아들인다(Assumptions).
- **FR-021**: 검색 헤더는 원본 위치, 언어, 패키지, 심볼 경로, 청크 종류, (테스트 메서드면) 표시 이름으로 만든다. 패키지 이름을 `/`로 바꾼 값이 원본 위치의 경로 구성 요소 경계에 맞게(앞뒤가 `/`이거나 위치 처음) 들어 있으면
  패키지는 헤더에서 뺀다(메타데이터에는 남는다, 2026-10-26 사용자 결정, plan research R-04). 형식 선언 맥락 줄은 청크를 감싼 형식 선언들의 선언 어노테이션과 선언 줄을
  바깥부터 차례로 모은 원문 줄이다(형식 선언 머리 청크와 그 형식의 요약 청크는 자기 선언이 본문에 있으므로 바깥 형식의 맥락 줄만 붙는다). 선언 줄은 FR-013의 시그니처 줄과 같은 규칙으로,
  형식 선언이 시작하는 줄부터 본문을 여는 `{`가 있는 줄까지다(Kotlin 주 생성자, `extends`·`implements` 목록, 레코드 구성 요소 포함). 본문이 없는 형식 선언은 선언 전체다.
  상한을 넘으면 FR-018대로 바깥부터 뺀다. 임베딩 입력 텍스트는 검색 헤더,
  형식 선언 맥락 줄, (나뉜 청크의 뒤 조각이면) 반복 줄, 청크 본문 순서로 이어 붙인 텍스트다. 청크 본문에는 헤더와 맥락 줄을 넣지 않는다.
  QK-CHK-002 FR-019처럼 검색 헤더와 임베딩 입력 텍스트는 청킹 결과로 넘기고 저장 스키마에 두지 않는다.
- **FR-022**: 키워드 검색용 텍스트는 QK-CHK-002와 같은 색인 쪽 키워드 규칙 설정 하나(지금 `kw-index-baseline-v1`, `kw-index-idsplit-v1`, `domain/keyword_rules.py`)를 따르고,
  규칙 입력은 검색 헤더, 형식 선언 맥락 줄, 청크 본문이다. 규칙 자체는 바꾸지 않는다. ADR-010이 운영 규칙을 확정한다. 코드 청킹을 켜서 새 인덱스 버전이 생기면
  인덱스 버전과 키워드 규칙 대응표(`INDEX_KEYWORD_RULES`)에 그 값을 더한다. 더하지 않으면 검색 요약의 키워드 규칙이 `unknown`이 된다.

**코드 메타데이터 (US3·US4)**

- **FR-023**: 청크마다 다음 메타데이터를 붙인다.
  - 언어(`java`, `kotlin`), 패키지(없으면 빈 값), 심볼 이름, 심볼 경로(FR-020)
  - 청크 종류: 파일 머리, 파일 요약, 형식 요약, 형식 선언 머리, 메서드, 생성자, 최상위 함수, 필드 묶음, 최상위 프로퍼티 묶음, 초기화 블록, 대체 청크 중 하나
  - 시그니처: 메서드·생성자·최상위 함수·형식 선언이면 선언 어노테이션과 본문을 뺀 선언 원문(매개변수 어노테이션은 남긴다)을 공백 하나로 정리한 값, 나머지는 빈 값
  - 형식 선언 종류: 감싼 형식 선언의 종류(클래스, 인터페이스, 열거형, 레코드, 어노테이션 형식, Kotlin `object`)와 원문 수식어(`data`, `sealed`, `abstract` 등)
  - 어노테이션 이름 목록: 그 선언에 직접 붙은 어노테이션의 단순 이름(패키지 이름·인자 제외, 매개변수 어노테이션 제외)
  - 테스트 코드 여부, 테스트 메서드 여부, 표시 이름(FR-025), Android 컴포넌트 종류(FR-024)
  판정할 수 없는 항목은 빈 값이고 실패가 아니다.
- **FR-024**: Android 컴포넌트 종류는 Activity, Fragment, ViewModel, Service, BroadcastReceiver, ContentProvider, Application, Composable이다. 파일에 `android.`나 `androidx.`로 시작하는
  import가 있을 때만 판정한다. 형식 선언의 상위 클래스(Java는 `extends`, Kotlin은 상위 형식 목록에서 생성자 호출 `(...)`이 붙은 형식, 인터페이스 제외)의 단순 이름이
  Android 기본 형식(`Activity`, `AppCompatActivity`, `ComponentActivity`, `Fragment`, `DialogFragment`, `ViewModel`, `AndroidViewModel`, `Service`, `BroadcastReceiver`,
  `ContentProvider`, `Application` 등, 목록은 `plan.md`에서 확정)이면 그 종류다. 아니면 상위 클래스 이름이 그 종류 이름으로 끝나는지(`BaseFragment` → Fragment) 본다.
  `@Composable` 어노테이션이 붙은 함수는 Composable이다. 형식 선언의 컴포넌트 종류는 그 멤버 청크에도 붙는다. 다른 파일을 읽어 간접 상속을 따라가지 않는다(FR-003).
- **FR-025**: 테스트 코드는 위치의 경로 구성 요소에 테스트 소스 세트 디렉터리(`src/test/`, `src/integrationTest/`, `src/androidTest/`, `src/testFixtures/`)가 있는 파일이다.
  경로 어느 깊이에 있어도 된다(다중 모듈 `order/src/test/…` 포함). 파일 이름으로는 판정하지 않는다. 테스트 메서드는 테스트 코드 안에서 JUnit 4·5 테스트 어노테이션
  (`Test`, `ParameterizedTest`, `RepeatedTest`, `TestFactory`, `TestTemplate` 등, 목록은 `plan.md`에서 확정)이 직접 붙은 메서드다. `@Nested` 클래스의 테스트 메서드도 같다.
  표시 이름은 `@DisplayName` 값, 없으면 Kotlin 백틱 이름이다. DSL 방식 테스트(Kotest 등)의 테스트 단위는 판정하지 않는다. 테스트와 대상 코드를 잇는 일은 QK-CHK-004다.
- **FR-026**: 코드 메타데이터는 청크와 함께 저장되고, 검색 결과·문맥 확장·청크 추적의 출처 정보로 돌아온다(QK-STO-001 `Provenance`). Markdown 청크의 저장 값과
  출처 정보는 바뀌지 않는다. 저장 방식(기존 위치 값에 새 키를 더할지, 새 열을 둘지)과 마이그레이션은 `plan.md`에서 정한다. 어느 방식이든 메타데이터 스키마가 바뀌므로
  메타데이터 스키마 버전을 `meta-v1`에서 올린다(AGENTS.md 3.3, 2026-10-26 사용자 결정). 메타데이터 스키마 버전은 인덱스 버전 재료라(`sync/keys.py:18-26`), 올리는 순간 인덱스 버전이 바뀐다.
  그래서 새 메타데이터 스키마 버전은 코드 청킹이 켜졌을 때만 인덱스 버전 재료가 된다. 저장 스키마 마이그레이션이 필요하면 코드 청킹을 켜는 변경(FR-030)에 함께 넣는다.
  꺼짐 배포에서는 저장 스키마와 `meta-v1`이 지금과 같다.

**버전과 켜기 (C-07, US6)**

- **FR-027**: 코드 청킹 규칙 버전 값을 둔다. 코드 청크 결과(경계, 본문, 심볼 경로, 메타데이터, 키워드 검색용 텍스트, 임베딩 입력 텍스트)에 영향을 주는 규칙이나 설정값이
  하나라도 바뀌면 값이 바뀌고, 같으면 같다. 재료에는 구문 해석 실패 판정 규칙, 맥락 줄 생략 규칙, 해석기 식별자·버전이 들어간다(Markdown 버전 재료의 해석기 버전과 같은 원칙, `chunking/version.py`).
  코드 청크마다 이 값을 붙인다. 형식과 첫 값은 `plan.md`에서 정한다.
- **FR-028**: 코드 청킹이 켜져 있으면 인덱스 버전은 Markdown 청킹 규칙 버전과 코드 청킹 규칙 버전, 메타데이터 스키마 버전(FR-026의 올린 값)을 모두 반영한다. 셋 중 하나라도 바뀌면
  인덱스 버전이 바뀐다. 지금 인덱스 버전 계산(`sync/keys.py:18-26`)은 청킹 규칙 버전 하나만 받으므로, 합치는 방식은 `plan.md`에서 정한다.
  새 인덱스 버전의 생성·평가·활성화는 QK-STO-002·QK-SYN-001이 한다.
- **FR-029**: 동기화의 문서별 변경 판정은 그 문서를 맡은 청커의 청킹 규칙 버전과 비교한다. 지금은 모든 문서를 Markdown 청킹 규칙 버전 하나와 비교하므로
  (`sync/plan.py:87`, `sync/decide.py:11`), 이대로 두면 코드 문서는 실행마다 "청킹 규칙 바뀜"으로 다시 처리된다. 실행 요약과 실행 기록은 두 청킹 규칙 버전을 함께 남긴다
  (지금 `ChunkingSummary.chunking_version`은 결과 하나의 값이다, `domain/chunking.py:117`). 저장 열(`qk.sync_run`, `qk.index_version`의 `chunking_version`)을 어떻게 맞출지는 `plan.md`에서 정한다.
- **FR-030**: 코드 청킹 켜기 설정을 둔다. 기본값은 꺼짐이다. 꺼져 있으면 코드 자료는 "대상 아님"이고(FR-001), 인덱스 버전 재료(메타데이터 스키마 버전 `meta-v1` 포함)·
  저장 스키마·Markdown 청킹 규칙 버전·Markdown 청킹 결과·키워드 규칙 대응표가 지금과 한 글자도 다르지 않다. 켜짐일 때의 계산 코드는 이번 구현에 미리 두고 시험한다.
  다만 켜짐 설정에서 계산한 인덱스 버전이 키워드 규칙 대응표(`INDEX_KEYWORD_RULES`)에 없으면 설정 검사(`qk-index check`)와 동기화 실행(`qk-index run`)이 오류로 멈춘다.
  그래서 환경값만 바꿔서는 켜지지 않는다(2026-10-26 사용자 결정, plan research R-09). 실제로 켜는 일은 QK-STO-002 절차와 사람 승인 뒤 별도 변경으로 한다.
  그 변경에서 대응표에 새 인덱스 버전을 더하고, 필요하면 저장 스키마 마이그레이션도 넣는다(FR-026).

**요약**

- **FR-036**: 코드 자료원을 켜기 전에 자료원별 식별이 먼저 있어야 한다. 지금 동기화는 같은 종류(`github_repo_files`) 자료원을 하나만 받는다. 둘 이상 켜면 실행 전 점검이
  `duplicate_source_kind`로, 저장된 다른 이름의 같은 종류 자료원이 있으면 `source_replacement`로 실행 전체를 멈춘다(`sync/identity.py:17-25`). 검사를 풀어도 저장 문서를 자료원 종류로만

### Key Entities

- **코드 청크(Code Chunk)**: 검색·임베딩 단위. QK-STO-001 청크 항목(순서, 위치, 본문, 제목 경로 자리의 심볼 경로, 키워드 검색용 텍스트, 청킹 규칙 버전)에 코드 메타데이터가 더해진다.
  원문 청크와 요약 청크 두 가지다.
- **원문 청크(Source Chunk)**: 연속한 원문 줄 범위 하나. 파일의 공백 아닌 줄을 빠짐·겹침 없이 덮는다.
- **요약 청크(Summary Chunk)**: 형식 선언이나 Kotlin 파일 최상위 선언의 생김새(선언·필드·시그니처 줄)를 모은 청크. 위치는 형식 선언(또는 파일) 전체 줄 범위이고 원문 줄 셈에서 빠진다.
- **형식 선언(Type Declaration)**: 클래스·인터페이스·열거형·레코드·어노테이션 형식·Kotlin `object`. 중첩될 수 있다.
- **멤버(Member)**: 메서드, 생성자, 초기화 블록, 필드·프로퍼티, 중첩 형식 선언, Kotlin 최상위 함수·프로퍼티.
- **심볼 경로(Symbol Path)**: 바깥 형식 선언부터 멤버까지의 심볼 이름 목록(FR-020 표). 제목 경로 자리에 저장된다.
- **형식 선언 맥락 줄(Type Context Lines)**: 청크를 감싼 형식 선언들의 선언 어노테이션과 선언 줄. 임베딩 입력과 키워드 검색용 텍스트에만 붙는다.
- **코드 메타데이터(Code Metadata)**: 언어, 패키지, 심볼 이름·경로, 시그니처, 청크 종류, 형식 선언 종류, 어노테이션 이름, 테스트 여부·표시 이름, Android 컴포넌트 종류.
- **구조 경고(Structure Warning)**: "구문 해석 실패"(FR-019)와 "맥락 줄 생략"(FR-018) 두 가지. 실패가 아니다.
- **코드 청킹 설정(Code Chunking Settings)**: 켜기 여부, 상한, 안전 여유, 목표 크기, 헤더 형식, 키워드 규칙, Android 기본 형식 목록, 테스트 소스 세트·어노테이션 목록, 해석기 식별자·버전.
  켜기 여부를 뺀 항목이 바뀌면 코드 청킹 규칙 버전이 바뀐다.
- **코드 자료원(Code Source)**: 백엔드 코드와 Android 코드 두 자료원. 비활성으로 등록하고 결정 기록·확인 기록 뒤 켠다.
- **청킹 결과·요약**: QK-CHK-002와 같은 결과 종류(청크 목록, 빈 문서, 대상 아님, 청킹 실패)와 실행 요약에 코드 항목(FR-031)이 더해진다.

  어노테이션 이름과 시그니처를 메타데이터로 남기는 데까지만 한다.
- 검색 동작(문맥 확장 규칙, 필터, 가중치, 테스트 코드 순위 조정)은 바꾸지 않는다(QK-RET-001). 메타데이터로 거르는 일은 QK-TRK-001 필터 추론이 다룬다.
- 인덱스 버전 생성·평가 게이트·활성화는 QK-STO-002다. ADR-010(키워드 검색 텍스트 규칙)은 QK-EVL-001 비교 리포트 뒤에 확정한다. 이 명세는 두 후보 규칙을 모두 지원한다(FR-022).
- 단계 게이트 1.G는 미완료다. 사용자 결정(2026-10-26, TASK.md)에 따라 명세를 먼저 쓴다. 구현 시작 시점은 spec 승인 때 다시 정한다.

**환경과 기본값**

- 구조 해석은 파일 하나의 구문만 본다. 형식 이름 해석(같은 이름의 다른 패키지 형식, 간접 상속)은 하지 않는다. 그래서 Android 컴포넌트 판정은 Android import가 있는 파일에서
  상위 클래스 이름과 이름 규칙에만 기댄다(FR-024). 이름 규칙에 맞지 않는 기반 클래스의 비율은 plan에서 대상 저장소로 센다.
- 해석 방법(구문 분석 라이브러리 사용 여부, 의존성 추가)은 `plan.md`에서 결정 기록으로 정한다. 의존성은 색인 쪽에만 두고 질의응답 번들(Workers)에는 넣지 않는다
  (`pyproject.toml` QK-CHK-002 주석과 같은 원칙).
- 구문 해석 실패 시 실패 대신 파일 전체 줄 단위 대체 청킹을 한다(FR-019, 작성 세션 판단). 코드는 검색에서 빠지는 비용이 크고, 대체 청크도 원문 위치로 되돌아갈 수 있다.
  대체 청크가 많으면 해석 방법을 다시 정한다.
- 요약 청크는 원문 줄을 겹쳐 쓴다(FR-009의 겹침 없음은 원문 청크에만 적용). 요약 청크는 독립 검색 대상이고, 검색 문맥 확장은 요약 청크를 메서드 청크의 상위로 붙이지 않는다
  (QK-RET-001 FR-014). 클래스 맥락은 형식 선언 맥락 줄(FR-021)로 임베딩 입력과 키워드 검색용 텍스트에만 붙는다. 생성 모델이 받는 Context에는 청크 본문과 심볼 경로만 들어가므로,
  클래스 어노테이션은 검색에는 쓰이지만 답변 근거로는 보이지 않을 수 있다 `(추론)`. Context 쪽 보완이 필요하면 QK-RET-001·QK-GEN-001 변경으로 다룬다.
- 요약 청크와 그 형식의 형식 선언 머리 청크는 심볼 경로가 같고 요약이 바로 앞에 온다(FR-012). 그래서 형식 선언 머리 청크가 검색 중심이면 문맥 확장이 요약을 절 첫 청크로 붙여
  선언 줄이 Context에 두 번 들어갈 수 있다(`0005_retrieval.sql:96-104`). 형식 선언 머리 청크는 대개 작아 이 중복을 받아들인다(2026-10-26 plan 검토 L2, 작성 세션 판단).
- 심볼 경로를 제목 경로 자리에 넣으면 QK-GEN-001 출처 줄이 `클래스 > 메서드(…)` 꼴로 보인다(`generation/render.py:55-59`). 매개변수 형식으로 오버로드를 구분하므로(FR-020)
  같은 심볼 경로가 이어지는 경우는 수신 형식만 다른 Kotlin 확장 함수 같은 드문 경우뿐이다 `(추론)`. 그 경우 문맥 확장(`0005_retrieval.sql:96-104`)이 앞 함수를 절 첫 청크로 붙이고,
  생성 렌더링이 절 구분을 넣지 않는 한계(`generation/render.py:90`)를 받아들인다.
- 코드 청킹을 켜면 FR-028 때문에 새 인덱스 버전이 생긴다. QK-SYN-001은 활성 인덱스 버전과 다르면 바뀐 문서 처리를 멈추므로(그 명세 FR-020), 켜는 일은 QK-STO-002의 새 인덱스 버전
  생성·평가·활성화와 함께 한다(FR-030). 새 버전을 만들 때 Markdown 청크의 임베딩 입력은 그대로라 임베딩 캐시 적중이고, 새 Neurons는 코드 청크에만 든다 `(추론, plan에서 확인)`.
- 작은 청크: plan 측정(research R-04, 승인판 규칙)에서 헤더·맥락 줄이 원문 바이트의 약 56%를 더하고, 본문 32토큰 미만 청크가 전체의 약 22%였다. 그 결과로 세 규칙(패키지 중복 제거 FR-021,
  형식 선언 머리와 첫 필드 묶음 합치기 FR-010, 본문 있는 멤버가 없는 형식의 요약 생략 FR-013)을 더했다(2026-10-26 사용자 결정). 메서드끼리는 여전히 합치지 않는다(수정 국소성 SC-003).
- 예상 비용: plan 측정(research R-02)에서 본문 코드 첫 색인은 보정 계수(Neurons 전용 1.4바이트/토큰, 1,075 Neurons/백만 토큰) 기준 약 2,960 Neurons,
  테스트 포함 약 7,000이었다. 토크나이저 토큰 수 기준으로는 본문 약 1,360이다. 하루 색인 예산은 5,000이다. 이 명세의 검증은 0 Neurons이고, 첫 활성화는 본문 코드만 권고한다(결정 기록, AGENTS.md 3.5).
- 같은 저장소 두 자료원: 백엔드 코드를 `dnd-backend-docs`에 더하지 않고 별도 자료원으로 두는 것은, 기존 자료원의 확인 기록과 결정 기록(ADR-019)을 건드리지 않고 따로 켜고 끌 수 있게 하려는 것이다.
  지금 동기화는 같은 종류 자료원을 하나만 받으므로(FR-036, QK-SYN-001이 정한 제약) 켜려면 자료원별 식별을 맡는 별도 명세가 먼저 끝나야 한다. 그 명세는 로드맵 백로그에 아직 없다.
  백로그 추가와 WBS 배치는 사람이 정한다.
- 해석기: 한 곳이라도 해석할 수 없으면 파일 전체를 대체 청킹하므로(FR-019), 백엔드 Java 버전(인벤토리 1.1)과 Kotlin 문법을 해석기가 지원하는지 plan에서 대상 저장소로 확인하고
  대체 청킹될 파일 수를 센다. Android import 없이 프로젝트 기반 클래스만 상속하는 컴포넌트 후보 파일 수(FR-024가 놓치는 경우)도 함께 센다.
- 비밀값: 테스트 코드의 가짜 토큰·고정값이 비밀값 규칙에 걸리면 파일 전체가 빠진다(QK-SEC-001 FR-011). 걸리는 파일 수와 오탐 예외 등록 필요는 plan에서 대상 저장소로 센다.
- 성능 기준(SC-012)은 인벤토리 규모의 초기값이다.
