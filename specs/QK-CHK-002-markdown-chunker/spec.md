# Feature Specification: QK-CHK-002 Markdown 청커·검색 헤더

**Feature Branch**: `feat/SCRUM-101-gh-46-markdown-chunker`

**Created**: 2026-10-21

**Status**: Draft

**Input**: 로드맵 4절 명세 백로그 QK-CHK-002 "Markdown 청커(저장소 문서·ClickUp 페이지 공용), 검색 헤더". 선행은 QK-ING-001이다.
백로그 행의 요구사항 ID(FR-CHK-01~05, 08)는 원문이 없어(Assumptions 참조) 백로그 제목, constitution C-06·C-07·C-08, AGENTS.md 3.3,
ADR-002와 스파이크 W-02, 0.3 ClickUp 조사(2절·F-03·F-04), ClickUp 작성 규칙, QK-ING-001·QK-SEC-001·QK-STO-001·QK-EMB-001 명세,
첫 실제 수집 측정(`docs/sdd/research/github-source-measurement.md`)을 근거로 썼다.

## User Scenarios & Testing *(mandatory)*

이 명세의 사용자는 청크를 쓰는 구현자(QK-SYN-001 동기화, QK-EMB-001 임베딩, QK-RET-001 검색·문맥 확장, QK-GEN-001 출처 표시),
이 청커 위에 코드 청커를 올릴 구현자(QK-CHK-001), ClickUp 페이지를 넘길 수집기 구현자(QK-ING-003), PR 리뷰어다.
최종 수혜자는 Discord에서 출처가 붙은 답을 받는 팀원이다.

청커는 보안 필터(QK-SEC-001)를 통과한 Markdown 자료 하나를 받아, 검색과 임베딩의 단위인 청크 목록으로 바꾼다. 청크마다 원본 위치와
제목 경로를 붙이고, 조각만 떼어 봐도 어느 문서의 어느 절인지 알 수 있게 검색 헤더를 만든다. 외부 호출과 저장은 하지 않는다.

### User Story 1 - 청크마다 원본 위치로 되돌아가고, 다시 나눠도 같다 (Priority: P1)

같은 원본과 같은 설정이면 언제 몇 번을 나눠도 같은 청크가 나온다. 청크마다 원본 경로와 줄 범위가 있어서, 답변의 출처를 눌렀을 때 그 줄을
찾아갈 수 있다. 문서의 한 절 본문만 고치면 다른 절의 청크는 그대로라서 다음 동기화에서 다시 임베딩하지 않는다.

**Why this priority**: C-07("같은 원본과 같은 설정이면 같은 청크 경계와 같은 해시", "모든 청크는 원본 위치로 되돌아갈 수 있다")을 직접 구현한다.
로드맵 1.G 완료 조건 "변경이 없는 재동기화에서 임베딩 호출이 0건", "문서 1개를 고치면 그 문서의 청크만 교체"는 결과가 결정적이어야 성립한다.

**Independent Test**: 사람이 기대 청크(줄 범위, 제목 경로)를 미리 적어 둔 합성 Markdown 문서 묶음을 청킹해 기대값과 비교하고, 두 번 청킹해 결과를 비교한다.
청크마다 위치의 줄 범위를 원문에서 잘라 본문과 대조한다. 절 하나의 본문만 고친 문서, 제목 하나만 고친 문서를 다시 청킹해 바뀐 청크를 센다.

**Acceptance Scenarios**:

1. **Given** 기대 청크를 적어 둔 합성 문서, **When** 청킹한다, **Then** 청크마다 줄 범위와 제목 경로가 기대값과 같다.
2. **Given** 같은 본문과 같은 설정, **When** 두 번 청킹한다, **Then** 청크 수, 순서, 본문, 위치, 제목 경로, 검색 헤더, 임베딩 입력 텍스트,
   키워드 검색용 텍스트, 청킹 규칙 버전이 모두 같다.
3. **Given** 청킹한 결과, **When** 아무 청크나 골라 위치의 줄 범위를 원문에서 잘라 본다, **Then** 청크 본문과 같다.
4. **Given** 청크 목록으로 성공한 결과, **When** 원문의 공백 아닌 줄을 모두 센다, **Then** 모든 줄이 정확히 한 청크에 들어 있다(빠짐 0, 겹침 0).
5. **Given** 세 절로 된 문서에서 가운데 절 본문 한 줄만 고친 판(제목 줄과 절 경계는 그대로), **When** 다시 청킹한다, **Then** 첫째·셋째 절 청크의
   본문, 제목 경로, 임베딩 입력 텍스트는 바뀌지 않는다(순서 번호와 줄 번호는 바뀔 수 있다).
6. **Given** `## B` 제목 줄 글자만 고친 판, **When** 다시 청킹한다, **Then** 제목 경로에 B가 든 청크만 바뀌고 나머지 청크의 임베딩 입력 텍스트는 그대로다.
   문서 제목을 고친 판에서는 모든 청크의 검색 헤더가 바뀐다.
7. **Given** 줄 바꿈 문자만 다른(CRLF·LF) 두 본문, **When** 청킹한다, **Then** 위치 줄 번호와 청크 내용이 같다.

### User Story 2 - 청크는 추정 상한 안으로 나뉘고, 원문은 잘려 나가지 않는다 (Priority: P1)

긴 문서는 임베딩 모델 입력 한도에서 안전 여유를 뺀 추정 상한 안으로 나뉜다. 원문은 버리거나 잘라 담지 않는다. 담을 수 없는 자료는
"청킹 실패"로 알린다. 추정이 빗나가 실제 한도를 넘는 청크는 QK-EMB-001이 "입력 한도 초과"로 알리고 자르지 않는다.

**Why this priority**: bge-m3는 8,192토큰을 넘는 입력을 400 오류로 거절하고(ADR-002), QK-EMB-001은 한도 초과 입력을 자르지도 다시 나누지도 않는다
(QK-EMB-001 FR-003, 그 명세 Assumptions "청크 크기를 입력 한도 안으로 맞추는 일은 QK-CHK-002 몫"). 첫 실제 수집에서 가장 큰 문서가 65,365바이트였다
(측정 기록 2절). 바이트당 토큰 추정(3.5바이트/토큰)으로 약 18,700토큰이라 나누지 않으면 한도를 넘는다 `(추론)`.

**Independent Test**: 상한의 몇 배인 문서, 상한보다 큰 단일 절, 상한보다 큰 단일 표·코드 블록, 상한보다 긴 한 줄, 그리고 헤더와 합쳐야 상한을 넘는
경계값 사례가 든 합성 문서를 청킹한다. 시험용 상한은 작게 설정해 경계를 만든다.

**Acceptance Scenarios**:

1. **Given** 예상 토큰이 상한의 3배이고 어느 한 줄도 헤더와 합쳐 상한을 넘지 않는 문서, **When** 청킹한다, **Then** 모든 청크의 임베딩 입력 텍스트가 상한 이하이고 원문 줄은 모두 어딘가의 청크에 있다.
2. **Given** 하위 제목 없이 상한보다 긴 절(각 블록은 헤더와 합쳐 상한 이하), **When** 청킹한다, **Then** 빈 줄로 나뉜 블록 경계에서 나뉘고, 줄 중간에서 나뉘지 않는다.
3. **Given** 상한보다 큰 표 하나(각 행은 헤더·머리글 행과 합쳐 상한 이하), **When** 청킹한다, **Then** 행 경계에서 나뉘고, 뒤 조각의 임베딩 입력 텍스트에는 표 머리글 행이 붙는다.
   청크 본문은 원문 줄 그대로다.
4. **Given** 검색 헤더와 따로는 상한 이하지만 헤더를 붙이면 상한을 넘는 한 줄, **When** 청킹한다, **Then** 그 문서는 청크 0개와
   "청킹 실패(줄 길이 초과)"로 돌아오고, 같은 실행의 다른 문서는 정상 처리된다.
5. **Given** 검색 헤더만으로 상한에 닿는 문서(아주 긴 경로나 제목), **When** 청킹한다, **Then** 그 문서는 "청킹 실패(헤더 길이 초과)"다.
6. **Given** 헤더를 붙인 크기가 목표 크기보다 크고 상한보다 작은 여러 줄 문단 하나, **When** 청킹한다, **Then** 그 문단은 나뉘지 않고 청크 하나다.

### User Story 3 - 조각만 봐도 어느 문서의 어느 절인지 안다 (Priority: P1)

청크마다 문서 제목과 절 제목 경로로 검색 헤더를 만든다. 검색 헤더는 임베딩 입력과 키워드 검색용 텍스트 앞에 붙고, 제목 경로는 따로
저장돼 출처 표시와 상위 절 조회에 쓰인다.

**Why this priority**: "Status: Accepted"처럼 짧은 절은 본문만으로는 어느 결정 기록인지 알 수 없다. 헤더가 없으면 "ADR-007 상태는?" 같은 질문에서
검색이 그 청크를 찾지 못한다 `(추론)`. QK-STO-001의 상위 절 조회(FR-011)는 앞선 청크 중 제목 경로가 앞부분으로 일치하는 청크를 찾으므로
(`0002_search_functions.sql` parents 조회), 상위 절마다 그 경로를 가진 청크가 있어야 한다.

**Independent Test**: 제목 수준을 건너뛰는 문서, 본문 없는 상위 제목이 있는 문서, 수준-1 제목이 없는 문서, 원본 제목이 목록·본문 중 한쪽에만 있거나
둘이 다른 자료, 제목에 강조·링크·코드 표기가 든 문서를 청킹해 검색 헤더와 제목 경로를 확인한다.

**Acceptance Scenarios**:

1. **Given** `# 결정 기록 A` 아래 `## 결정` 아래 `### 근거` 절, **When** 청킹한다, **Then** `### 근거` 절 청크의 제목 경로는
   (`결정 기록 A`, `결정`, `근거`)이고, 임베딩 입력 텍스트는 문서 위치, 문서 제목, 제목 경로가 든 검색 헤더로 시작한다.
2. **Given** `# A` 바로 다음 줄에 `## B`가 오는 문서, **When** 청킹한다, **Then** 제목 경로가 (`A`)인 청크(제목 줄만 든 청크)가 있고,
   `## B` 절 청크보다 순서가 앞선다.
3. **Given** 제목이 하나도 없고 원본 제목도 없는 문서, **When** 청킹한다, **Then** 문서 제목은 파일 이름이고 제목 경로는 비어 있으며 검색 헤더는 있다.
4. **Given** 본문 조회 결과의 제목과 목록 항목의 제목이 다른 자료, **When** 청킹한다, **Then** 본문 조회 결과의 제목을 문서 제목으로 쓴다.
   본문 조회 결과에 제목이 없으면 목록 항목의 제목을 쓴다.
5. **Given** `## **중요** [링크](x) \`code\``처럼 꾸밈이 든 제목, **When** 청킹한다, **Then** 제목 경로에는 꾸밈 기호를 뺀 글자(`중요 링크 code`)가 들어간다.
6. **Given** 같은 절이 나뉜 여러 청크, **When** 검색 헤더를 본다, **Then** 모두 같은 제목 경로를 갖는다.
7. **Given** 문서 제목이 첫 제목과 같은 문서, **When** 검색 헤더를 본다, **Then** 같은 제목이 두 번 반복되지 않는다.

### User Story 4 - Markdown 구조를 깨지 않고 나눈다 (Priority: P2)

코드 블록 안의 `#` 줄을 제목으로 잘못 읽거나, 표·코드 블록·목록 항목을 중간에서 갈라 의미를 잃지 않는다. ClickUp에서 옮겨 온 문서처럼
구조가 조금 깨진 Markdown도 고치려 하지 않고 원문 그대로 나누되, 깨진 곳은 경고로 알려 사람이 검토할 수 있게 한다.

**Why this priority**: 0.3 조사가 "코드 펜스 내부의 `#`는 헤딩에서 제외", "표는 헤더·행을 함께 유지", "표시 언어를 의미 판정의 유일한 근거로 삼지 않음",
"셀 줄바꿈으로 깨진 표는 자동 보정하지 말고 경고·검토 대상으로 분리"를 이 명세로 넘겼다(`clickup-migration-check.md` 2절, F-03·F-04).
다만 Phase 1 자료는 저장소 문서라 ClickUp 특유의 깨짐은 Phase 2(QK-ING-003)부터 실제로 나온다. 그래서 P2로 둔다.

**Independent Test**: 코드 펜스 안의 `#` 줄, 물결표 펜스, 닫히지 않은 펜스, 들여쓴 코드, 인용·목록 안의 제목 모양 줄, 밑줄형 제목, 앞머리 메타데이터,
셀 수가 머리글과 다른 표 행, 언어 표시가 틀린 다이어그램 코드 블록을 넣은 합성 문서를 청킹한다. 크기 판정은 상한·목표 크기에서 충분히 먼 입력으로 한다.

**Acceptance Scenarios**:

1. **Given** 코드 펜스 안에 `# 주석` 줄이 있는 문서, **When** 청킹한다, **Then** 그 줄은 제목이 아니고 절 경계도 아니다.
2. **Given** 상한 안이지만 목표 크기보다 큰 표나 코드 블록, **When** 청킹한다, **Then** 그 블록은 한 청크에 통째로 들어간다.
3. **Given** 닫는 펜스가 없는 코드 블록, **When** 청킹한다, **Then** 문서 끝까지를 코드 블록으로 보고, 그 안의 `#` 줄을 제목으로 읽지 않으며,
   "닫히지 않은 코드 펜스" 경고를 남긴다. 실패시키지 않는다.
4. **Given** 같은 다이어그램 내용에 언어 표시만 `mermaid`와 `css`로 다른 두 문서(크기 경계에서 먼 입력), **When** 청킹한다, **Then** 두 결과의 청크 줄 범위와
   제목 경로가 같고, 각 청크 본문은 각자의 원문 줄(언어 표시 포함) 그대로다.
5. **Given** 셀 줄바꿈 때문에 일부 행의 셀 수가 머리글과 다른 표, **When** 청킹한다, **Then** 원문을 고치지 않고 해석 규칙대로 나온 블록 그대로 다루며,
   "표 셀 수 불일치" 경고를 줄 번호와 함께 남긴다. 실패시키지 않는다.
6. **Given** 문서 맨 앞에 `---`로 감싼 앞머리 메타데이터, **When** 청킹한다, **Then** 그 `---`를 밑줄형 제목으로 읽지 않고, 메타데이터의 제목 값을 문서 제목 후보로 쓴다.

### Edge Cases

- 빈 문서, 공백만 있는 문서: 청크 0개이고 실패가 아니다. "빈 문서"로 요약에 센다. 이전 청크를 지울지는 QK-SYN-001이 정한다.
- 제목만 있고 본문이 없는 절(바로 하위 제목이 오거나 문서 끝인 경우): 그 제목 줄만으로 청크 하나를 만든다(FR-011). 상위 절 조회가 이 청크를 찾는다.
- 제목 수준을 건너뛴 문서(수준-1 다음 수준-3): 제목 경로에는 실제로 있는 제목만 순서대로 들어간다. 빈 자리를 채우지 않는다.
- 수준-1 제목이 여러 개인 문서: 각각 최상위 절이다. 문서 제목은 FR-017 순서로 하나만 정한다.
- 같은 제목 경로가 문서에 두 번 나오는 경우(같은 이름의 절 두 개): 둘 다 그대로 쓰고, 구분은 위치(줄 범위)와 순서로 한다. 현재 상위 절 조회는
  경로마다 가장 앞선 청크를 고르므로 두 번째 절의 하위 청크가 첫 번째 절을 상위로 받을 수 있다. 이 한계는 Assumptions에 적고 이 명세에서 고치지 않는다.
- 헤더를 붙인 한 줄이 상한보다 긴 경우(압축된 HTML, 아주 긴 표 행): 그 문서는 "청킹 실패(줄 길이 초과)"다. 줄을 잘라 담지 않는다(FR-015).
- 검색 헤더만으로 상한에 닿는 경우: 그 문서는 "청킹 실패(헤더 길이 초과)"다.
- 한 블록(표·코드·목록)이 상한보다 클 때: 줄 경계에서 나눈다. 나눈 조각들은 같은 제목 경로를 갖는다.
- 본문 형식이 Markdown이 아닌 자료(코드, JSON, 일반 텍스트): 처리하지 않고 "대상 아님"으로 돌려준다. 코드는 QK-CHK-001이 맡는다.
- 본문 앞의 바이트 순서 표시(BOM), 탭과 공백이 섞인 들여쓰기, 줄 끝 공백: 줄 바꿈 정규화와 BOM 제거 외에는 원문을 바꾸지 않는다.
- HTML 블록, `<details>`, HTML 주석, 이미지 링크, 각주: 원문 그대로 일반 블록으로 다룬다. 안의 제목 모양 줄은 제목이 아니다.
- 파일 이름이나 경로가 바뀐 문서: 검색 헤더에 위치가 들어가므로 모든 청크의 임베딩 입력 텍스트가 바뀐다. 다시 임베딩하는 것이 맞다.
- 비밀값: 청커는 QK-SEC-001을 통과한 자료만 받으므로 비밀값 검사를 다시 하지 않는다. 임베딩 직전 검사는 QK-EMB-001이 QK-SEC-001 전송 직전 검사로 한다.
- 청커 자체 오류(예상하지 못한 입력): 그 자료는 청크 0개와 "청킹 실패(처리 오류)"로 돌아오고 다른 자료 처리는 계속된다(C-08).

## Requirements *(mandatory)*

### Functional Requirements

**공통**

- **FR-001**: 입력은 QK-SEC-001 필터를 통과한 자료(원본 목록 항목, 본문 조회 결과, 접근 범위, 보안 규칙 버전)다. 본문 형식이 Markdown인 자료만 청킹하고,
  나머지 형식은 청크 0개와 "대상 아님"으로 돌려준다.
- **FR-002**: 청킹 결과는 입력 본문, 원본 위치, 원본 제목, 청킹 설정으로만 정해진다. 자료원 종류·자료원 이름에 따라 규칙이 갈리지 않고(C-06),
  실행 시각·처리 순서·실행 환경에 따라 결과가 달라지지 않는다.
- **FR-003**: 청커는 외부 API를 호출하지 않고, 원본에 쓰지 않고, 저장하지 않는다(C-09). 결과를 돌려주기만 한다. 저장은 QK-SYN-001이 한다.
- **FR-004**: 자료 하나의 결과는 청크 목록(1개 이상), 빈 문서(0개), 대상 아님, 청킹 실패 중 하나다. 청킹 실패에는 정해진 실패 유형
  (줄 길이 초과, 헤더 길이 초과, 처리 오류)만 붙는다. 실패한 자료는 일부 청크만 내지 않는다. 청크 목록 결과에는 구조 경고(FR-024)가 0개 이상 붙을 수 있다.
- **FR-005**: 자료 하나의 실패가 같은 실행의 다른 자료 처리를 멈추지 않는다(C-08).
- **FR-006**: 청커가 내는 기록·오류·경고·요약에는 본문 원문을 넣지 않는다. 자료 식별자·위치·제목은 QK-SEC-001 기록 출력 규칙(그 명세 FR-023)을 거친다.

**원본 위치와 재현성 (US1)**

- **FR-007**: 청킹 전에 줄 바꿈을 LF로 통일하고 본문 앞 BOM을 뺀다. 그 밖에는 원문을 바꾸지 않는다. 줄 번호는 원문의 1번 줄부터 센다.
- FR-008~011은 청크 목록 결과(FR-004)에 적용한다. 빈 문서·대상 아님·청킹 실패 결과는 청크 0개다.
- **FR-008**: 청크마다 원본 위치와 시작·끝 줄 번호(양 끝 포함)를 갖는다. 원본 위치는 본문 조회 결과의 위치 값이다(줄 번호가 그 본문 기준이기 때문이다.
  Phase 1은 저장소 안 경로). 청크 본문은 그 줄 범위의 원문 그대로다. 청크 앞뒤의 빈 줄은 본문과 줄 범위에서 뺀다.
- **FR-009**: 원문의 공백 아닌 줄은 모두 정확히 한 청크에 들어간다. 청크끼리 겹치지 않는다(겹침 없음). 앞뒤 문맥은 검색 단계의 문맥 확장(QK-RET-001,
  QK-STO-001 FR-011)으로 얻는다.
- **FR-010**: 청크 순서는 자료 안에서 0부터 빈틈없이 매기고, 원문 순서와 같다. 결과의 청크 항목은 QK-STO-001 청크 입력 검증을 그대로 통과한다.
- **FR-011**: 절은 제목 줄 하나와 다음 제목(수준 무관) 전까지의 줄이다. 첫 제목 앞에 공백 아닌 줄이 있으면 그 줄들은 제목 경로가 빈 머리 절이다.
  모든 절은 청크 1개 이상이 되고, 본문 없는 절은 제목 줄만 든 청크가 된다. 절 경계는 항상 청크 경계이고, 서로 다른 절을 한 청크로 합치지 않는다.
  그래서 문서 제목·제목 줄·절 경계가 그대로이고 한 절의 본문 줄만 바뀌면, 그 절 밖 청크의 본문·제목 경로·임베딩 입력 텍스트는 바뀌지 않는다.
  제목 줄이 바뀌면 그 제목을 경로에 가진 청크가, 문서 제목이나 원본 위치가 바뀌면 모든 청크의 검색 헤더가 바뀐다.
- **FR-012**: 청킹 규칙 버전 값을 둔다. 청크 결과(경계, 본문, 제목 경로, 키워드 검색용 텍스트, 임베딩 입력 텍스트)에 영향을 주는 규칙이나 설정값
  (상한, 안전 여유, 목표 크기, 헤더 형식, 키워드 검색용 텍스트 규칙, 임베딩 입력 텍스트 구성 등) 중 하나라도 바뀌면 값이 바뀌고, 같으면 같다. 청크마다 이 값을 붙인다. 값이 바뀌면 인덱스 버전을 올려야 한다(AGENTS.md 3.3). 값의 형식과 첫 값은
  `plan.md`에서 정한다. 인덱스 버전을 만들고 활성화하는 일은 QK-STO-002·QK-SYN-001이 한다.

**크기 (US2)**

- **FR-013**: 청크 크기는 그 청크 임베딩 입력 텍스트(FR-019)의 예상 토큰 수다. 예상 토큰은 QK-EMB-001 미리 보기와 같은 계산을 쓴다. 모든 청크의 크기는
  상한 이하다. 상한은 대상 임베딩 모델의 입력 한도(bge-m3 8,192토큰)에서 안전 여유를 뺀 값이다. 이 명세가 보장하는 것은 예상 토큰 기준의 상한 준수다.
  안전 여유 값은 `plan.md`에서 정하고, 그 근거로 보안 필터를 통과한 Phase 1 대상 문서에서 실제 토크나이저 토큰 수와 예상 토큰 수를 비교한 측정을 남긴다.
- **FR-014**: 목표 크기를 연성 목표로 둔다. 절의 크기가 목표 크기 이하이면 한 청크다. 넘으면 블록 사이(FR-015 (1))에서만 목표 크기 근처로 나누고,
  목표 크기를 넘는 블록 하나는 상한 이하이면 나누지 않는다(FR-016). 그래서 목표 크기를 넘는 청크가 있을 수 있지만 상한을 넘는 청크는 없다.
  목표 크기는 상한 이하이고, 초기값은 `plan.md`에서 정하며 검색 평가(QK-EVL-001)로 조정한다.
- **FR-015**: 나누는 지점은 다음 순서로 고른다. (1) 빈 줄로 나뉜 블록(문단, 목록, 표, 코드 블록, 인용) 사이, (2) 블록이 상한을 넘으면 그 블록 안의
  줄 경계(표의 행, 코드의 줄, 목록 항목). 줄 중간에서 나누지 않는다. 나누기·합치기 판정은 모두 "검색 헤더 + (필요하면) 반복 머리글 + 후보 본문"의 크기로 한다.
  검색 헤더만으로 상한에 닿으면 "청킹 실패(헤더 길이 초과)", 원문 한 줄에 검색 헤더와 필요한 반복 머리글을 붙여 상한을 넘으면 "청킹 실패(줄 길이 초과)"이고,
  그 자료 전체가 실패다. 어떤 원문도 버리거나 잘라서 담지 않는다.
- **FR-016**: 블록(문단, 표, 코드 블록, 목록 항목, 인용 블록)은 FR-015 기준 크기가 상한 이하이면 목표 크기를 넘어도 나누지 않는다.

**검색 헤더 (US3)**

- **FR-017**: 문서 제목은 다음 순서로 처음 나오는 값이다. 원본 제목(QK-ING-001 data-model 규칙대로 본문 조회 결과의 제목, 없으면 목록 항목의 제목),
  앞머리 메타데이터의 제목 값, 문서의 첫 수준-1 제목, 원본 위치의 파일 이름.
- **FR-018**: 제목 경로는 청크가 속한 절까지 바깥 제목부터 안쪽 제목 순서의 제목 글자 목록이다. 문서에 실제로 있는 제목만 넣는다.
  제목 글자는 Markdown 꾸밈(강조, 링크 표기, 인라인 코드 표시, 이미지 표기, 끝의 `#`)을 빼고 앞뒤 공백을 정리한 글자다.
  같은 절에서 나온 청크는 모두 같은 제목 경로를 갖는다.
- **FR-019**: 검색 헤더는 원본 위치, 문서 제목, 제목 경로로 만든다. 문서 제목이 제목 경로 첫 항목과 같으면 한 번만 쓴다. 임베딩 입력 텍스트는
  검색 헤더, (나뉜 표·코드 블록의 뒤 조각이면) 그 블록의 머리글 행이나 여는 펜스 줄, 청크 본문 순서로 이어 붙인 텍스트다. 청크 본문 자체에는
  헤더를 넣지 않는다(FR-008). 청킹 결과는 청크마다 저장 스키마의 청크 항목과 함께 검색 헤더와 임베딩 입력 텍스트를 넘긴다. 이 두 값은 저장 스키마에
  두지 않는다. 저장된 청크 하나만으로는 임베딩 입력 텍스트를 다시 만들 수 없을 수 있으므로(반복 머리글), 다시 필요하면 같은 원문과 설정으로 다시 청킹한다(C-07).
- **FR-020**: 키워드 검색용 텍스트의 청커 기본값은 검색 헤더와 청크 본문을 이어 붙인 텍스트다. 식별자 분해 같은 키워드 검색 텍스트 규칙(FR-CHK-07, ADR-010)은
  QK-RET-001이 정하고, 그 규칙을 바꾸면 FR-012에 따라 청킹 규칙 버전이 바뀐다.

**Markdown 구조 (US4)**

- **FR-021**: 제목은 최상위 블록의 `#`~`######` 제목과 밑줄형(`===`, `---`) 제목이다. 코드 펜스, 들여쓴 코드, HTML 블록, 인용, 목록 안의 제목 모양 줄과
  앞머리 메타데이터의 구분선은 제목이 아니다. Markdown 해석은 CommonMark 규칙을 기준으로 하고, 표는 GitHub 표 확장 규칙을 기준으로 한다.
- **FR-022**: 코드 펜스는 여는 펜스와 같은 문자(백틱·물결표)이고 길이가 같거나 긴 펜스로 닫힌다. 닫히지 않은 펜스는 문서 끝까지 코드 블록이다.
- **FR-023**: 코드 블록의 언어 표시는 원문에 그대로 남기고, 블록 종류·제목 판정·나누는 지점 판정에 쓰지 않는다. 그래서 크기 판정을 빼면 언어 표시만 다른
  두 문서의 청크 줄 범위와 제목 경로는 같다. 내용 기반 언어 판별(다이어그램 코드 등)은 이 청커가 하지 않는다. 코드 의미 단위 청킹은 QK-CHK-001,
  ClickUp 다이어그램 블록 처리 방식은 QK-ING-003이 필요하면 정한다.
- **FR-024**: 구조가 깨진 Markdown은 원문을 고치지 않고 해석 규칙(FR-021)대로 나온 블록 그대로 다루며, 그것 때문에 실패시키지 않는다. 대신 다음 경우에
  구조 경고(경고 유형, 줄 번호)를 결과에 붙여 사람이 검토할 수 있게 한다. 표 행의 셀 수가 머리글 행의 셀 수와 다름("표 셀 수 불일치"), 닫히지 않은 코드 펜스
  ("닫히지 않은 코드 펜스"). 경고 판정만 바꾸거나 경고 유형을 더하는 일은 청크 결과를 바꾸지 않으므로 FR-012의 청킹 규칙 버전을 바꾸지 않는다.
- **FR-025**: 문서 맨 앞의 앞머리 메타데이터(`---`로 감싼 블록)는 제목 후보(FR-017)로 읽고, 원문 그대로 머리 절의 본문에 남긴다.

**공용 (ClickUp 페이지)**

- **FR-026**: 청커는 수집기 공통 형식(QK-ING-001)만 알면 쓸 수 있다. ClickUp 페이지처럼 줄 범위 말고 다른 위치 정보(블록 ID 등)가 필요한 자료원은
  그 자료원 명세가 위치 값에 더하는 방식을 정하고, 이 명세의 규칙은 바꾸지 않는다.

**요약**

- **FR-027**: 실행마다 자료 수(결과별), 청크 수, 실패 유형별 수, 경고 유형별 수, 청크 예상 토큰 분포(최소·중앙값·최대), 상한 때문에 나뉜 블록 수를 요약한다.
  요약 수치는 자료별 결과를 센 값과 같다. QK-SYN-001 실행 기록과 목표 크기 조정(FR-014)에 쓴다.

### Key Entities

- **청크(Chunk)**: 검색·임베딩 단위. 순서, 원본 위치(경로, 시작·끝 줄), 본문, 제목 경로, 키워드 검색용 텍스트, 청킹 규칙 버전. QK-STO-001 청크 항목과 같다.
- **절(Section)**: 제목 줄 하나와 다음 제목 전까지의 줄. 청크 경계의 기본 단위이고, 모든 절은 청크 1개 이상이 된다.
- **제목 경로(Heading Path)**: 바깥 제목부터 안쪽 제목까지 꾸밈을 뺀 제목 글자 목록.
- **검색 헤더(Search Header)**: 원본 위치, 문서 제목, 제목 경로로 만든 짧은 텍스트. 임베딩 입력과 키워드 검색용 텍스트 앞에 붙는다.
- **임베딩 입력 텍스트(Embedding Input)**: 검색 헤더 + (나뉜 블록의 머리글) + 본문. QK-EMB-001로 보내는 텍스트이고 캐시 키의 바탕이다. 청킹 결과로 함께 넘기고 저장 스키마에는 두지 않는다.
- **구조 경고(Structure Warning)**: 경고 유형(표 셀 수 불일치, 닫히지 않은 코드 펜스)과 줄 번호. 실패가 아니다.
- **청킹 설정(Chunking Settings)**: 상한, 안전 여유, 목표 크기, 헤더 형식. 바뀌면 청킹 규칙 버전이 바뀐다.
- **청킹 결과(Chunking Outcome)**: 자료 하나의 결과(청크 목록과 청크별 검색 헤더·임베딩 입력 텍스트·구조 경고, 빈 문서, 대상 아님, 청킹 실패와 실패 유형).
- **청킹 요약(Chunking Summary)**: 실행 단위의 결과별 자료 수, 청크 수, 실패·경고 유형별 수, 예상 토큰 분포, 나뉜 블록 수.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사람이 기대 결과를 적어 둔 합성 시험 문서 묶음(US1~4의 사례를 모두 담은 것)에서 기대값과 다른 결과 수가 0이다. 청크 목록 결과의 기대값은
  청크마다 순서(0부터 빈틈없이), 줄 범위, 제목 경로, 키워드 검색용 텍스트, 임베딩 입력 텍스트(나뉜 표·코드 뒤 조각의 머리글 행·여는 펜스 줄 포함) 전체이고,
  나머지 결과의 기대값은 결과 종류와 실패 유형이다. 같은 묶음을 두 번, 그리고 처리 순서를 섞어 청킹했을 때 결과가 다른 자료 수가 0이다.
- **SC-002**: 같은 묶음의 청크 목록 결과에서 청크 본문이 위치의 줄 범위 원문과 다른 청크 수가 0이고, 청크에 들어가지 않았거나 두 청크에 들어간
  공백 아닌 원문 줄 수가 0이며, 청크가 없는 절 수가 0이고, QK-STO-001 청크 입력 검증에 실패한 결과 수가 0이다.
- **SC-003**: 상한의 3배 이상인 문서, 상한보다 큰 절·표·코드 블록, 목표 크기와 상한 사이의 문단을 담은 성공 사례에서 임베딩 입력 텍스트의 예상 토큰이
  상한을 넘는 청크 수가 0이고, 잘려 나간 원문 줄 수가 0이며, 상한 이하인 블록이 나뉜 건수가 0이다. 이와 따로, 헤더를 붙여야 상한을 넘는 한 줄과
  헤더만으로 상한에 닿는 경계값 사례는 100% 해당 실패 유형과 청크 0개로 돌아온다.
- **SC-004**: 문서 제목·원본 위치·설정·제목 줄·절 경계를 그대로 두고 절 하나의 본문만 고친 문서를 다시 청킹했을 때, 그 절 밖 청크의 임베딩 입력 텍스트가
  바뀐 건수가 0이다. 문서 제목으로 쓰이지 않는 제목 줄 하나만 고친 문서에서는 바뀐 청크가 그 제목을 경로에 가진 청크뿐이다. 문서 제목을 고친 문서에서는
  모든 청크의 검색 헤더가 새 제목을 담는다.
- **SC-005**: 코드 펜스·들여쓴 코드·인용·목록·HTML 블록 안의 제목 모양 줄과 앞머리 메타데이터 구분선이 제목으로 인식된 건수가 0이고,
  상한 이하인 표·코드 블록이 둘 이상으로 나뉜 건수가 0이다. 셀 수가 다른 표 행과 닫히지 않은 펜스를 넣은 사례는 100% 해당 경고가 붙고 실패는 0건이다.
- **SC-006**: 모든 청크의 임베딩 입력 텍스트가 검색 헤더로 시작한다. 제목도 원본 제목도 없는 문서를 포함해 문서 제목이 빈 청크 수가 0이고,
  본문 없는 상위 제목마다 그 제목 경로를 가진 청크가 있다.
- **SC-007**: 실패를 주입한 시험(줄 길이 초과, 헤더 길이 초과, 처리 오류)에서 실패한 자료가 청크를 낸 건수가 0이고 나머지 자료는 100% 처리되며,
  기록·경고·요약·로그에 본문 원문이 나온 건수가 0이다. Markdown이 아닌 자료는 100% "대상 아님"이고 청크 0개다.
- **SC-008**: 자료원 종류가 다른 두 가짜 자료원에 같은 본문·위치·제목을 넣었을 때 청킹 결과가 다른 건수가 0이다.
- **SC-009**: 청크 결과에 영향을 주는 설정·규칙 항목을 하나씩 바꾼 시험에서 청킹 규칙 버전이 바뀌지 않은 경우가 0이고, 같은 설정으로 다시 만든 버전이
  달라진 경우가 0이며, 구조 경고 판정만 바꾼 경우 버전이 바뀐 경우가 0이다. 모든 청크에 청킹 규칙 버전이 있다.
- **SC-010**: 요약의 모든 수치가 자료별 결과를 직접 센 값과 같다.
- **SC-011**: 보안 필터를 통과한 Phase 1 대상 규모(Markdown 79개, 측정 기록 2절)의 자료를 청킹하는 데 10초가 넘지 않는다. 고정 입력, 측정 장비, 반복 횟수,
  시간 집계 방식은 `plan.md`에서 정한다.

**범위**

- 코드 청킹(Java·Kotlin 심볼 단위)은 QK-CHK-001이다. 이 청커는 Markdown 안의 코드 블록을 일반 블록으로만 다룬다.
- 키워드 검색 텍스트 규칙(FR-CHK-07, ADR-010)은 QK-RET-001이다. 이 명세는 청커 기본값만 정한다(FR-020).
- ClickUp 수집, ClickUp 위치 정보, 다이어그램 블록 처리는 QK-ING-003이다. 이 청커는 그때 규칙을 바꾸지 않고 쓸 수 있어야 한다(FR-026).
- 임베딩 호출, 캐시, 전송 직전 비밀값 검사는 QK-EMB-001이다. 청크 저장, 이전 청크와의 교체, 빈 문서·실패 자료의 이전 청크 처리는 QK-SYN-001이다.
- 인덱스 버전 생성·평가 게이트·활성화는 QK-STO-002다. 이 명세는 청킹 규칙 버전 값만 낸다(FR-012).
- 저장 스키마와 검색 SQL은 바꾸지 않는다(TASK.md 제외 범위). 그래서 임베딩 입력 텍스트는 저장하지 않고 청킹 결과로만 넘기며(FR-019),
  같은 제목 경로가 두 번 나올 때의 상위 절 조회 한계(Edge Cases)도 이 명세에서 고치지 않는다. 문맥 확장에서 문제가 되면 QK-RET-001이 다룬다.

**환경과 기본값**

- 첫 청킹 규칙 버전은 처음 만드는 값이라 바꿀 이전 버전이 없다. 아직 저장된 청크가 없으므로(QK-SYN-001 미구현) 재임베딩 대상도 없다 `(추론)`.
- 임베딩 모델은 ADR-002의 bge-m3(8,192토큰)를 기준으로 한다. ADR-002의 Status는 아직 Proposed다. 모델이 바뀌면 상한도 바뀌고 FR-012에 따라 청킹 규칙 버전도 바뀐다.
- 예상 토큰 계산(UTF-8 바이트 ÷ 3.5)과 실제 토크나이저의 차이는 입력에 따라 다르다. 스파이크의 합성 한국어 텍스트에서는 bge-m3 1토큰이 약 1.87자(약 5.6바이트)여서
  추정이 토큰을 크게 잡았지만, 이는 한 텍스트의 측정이다. 영문·기호·코드에서는 추정이 작게 잡을 수 있다 `(추론)`. 그래서 이 명세는 예상 토큰 기준 상한만 보장하고(FR-013),
  안전 여유는 대상 문서 측정으로 정한다. 측정에 외부 호출 비용이 들면 실행 전에 예상 사용량을 적는다(AGENTS.md 3.5). 남는 위험은 QK-EMB-001이 한도 초과를
  자르지 않고 알리는 것으로 드러난다.
- 겹침(overlap)을 두지 않는다. 겹침이 있으면 FR-009의 "원문 줄은 정확히 한 청크"를 지킬 수 없고, 앞뒤 문맥은 QK-STO-001 FR-011 앞뒤 청크 조회로 얻을 수 있다.
  검색 평가에서 겹침이 필요하다고 나오면 청킹 규칙 버전을 올려 다시 정한다.
- 서로 다른 절을 합치지 않고, 본문 없는 절도 제목 줄 청크를 만든다(FR-011). 작은 청크가 늘지만 검색 헤더가 문맥을 채운다고 보고, 수정 국소성(SC-004)과
  상위 절 조회(SC-006)를 우선한다. 작은 청크가 검색 품질을 떨어뜨린다고 평가에서 나오면 다시 정한다. 제목 줄만 든 청크의 임베딩 비용은 작다 `(추론)`.
- 헤더를 붙여 상한을 넘는 한 줄이 Phase 1 대상에 얼마나 있는지는 아직 모른다. 가장 큰 파일 크기(65,365바이트)만으로는 줄 길이 분포를 알 수 없다.
  `plan.md`에서 보안 필터를 통과한 대상 문서의 최대 줄 길이와, 줄 길이 초과로 실패할 문서 수·비율을 확인한다. 비율이 크면 FR-015 기본값(실패)을 다시 정한다.
- 구조 경고는 표 셀 수 불일치와 닫히지 않은 코드 펜스 두 가지로 시작한다. 0.3 조사의 다른 관찰(코드 경계 합침, 이미지 자리표시자)은 원문만으로 판정할 수 없어 다루지 않는다.
- 성능 기준(SC-011)은 Phase 1 규모의 초기값이다. Phase 2에서 규모가 커지면 다시 정한다.
