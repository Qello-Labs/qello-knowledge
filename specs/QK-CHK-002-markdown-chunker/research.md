# Research: QK-CHK-002 Markdown 청커·검색 헤더

이 문서는 저장소 코드, QK-ING-001·QK-SEC-001·QK-STO-001·QK-EMB-001 산출물, 첫 실제 수집 측정(`docs/sdd/research/github-source-measurement.md`)과
아래 R-02·R-03의 로컬 측정으로 정했다. 측정은 대상 저장소의 로컬 사본을 읽어 했으므로 GitHub API 호출 0건, Workers AI 호출 0건(0 Neurons)이다.
토크나이저 파일 하나를 Hugging Face에서 내려받았고(GET만, 문서 데이터 전송 없음, 2026-10-21 사용자 허용), 프로젝트 의존성에는 넣지 않았다.
측정 결과에는 문서 원문을 적지 않는다.

## R-01 Markdown 해석기: `markdown-it-py`를 색인 전용 선택 의존성으로

- **Decision**: 블록 해석은 `markdown-it-py`(`MarkdownIt("commonmark").enable("table")`)로 한다. 버전은 `==4.2.0`으로 고정하고,
  `pyproject.toml`의 선택 의존성 `index`와 `dev` 그룹에 넣는다. 런타임 `dependencies`는 비워 둔다. 해석기 이름·버전·설정은 청킹 규칙 버전(R-07)의
  재료에 넣는다. 해석기를 가져오는 코드는 `chunking/blocks.py` 한 곳이고, `domain`·`ports`·`embedding`·`query`는 `chunking`을 가져오지 않는다(R-10).
- **Rationale**: 청커에 필요한 것은 최상위 블록의 줄 범위다. `markdown-it-py`는 CommonMark를 따르고 블록 토큰마다 줄 범위(`map`)를 주며,
  GitHub 표 확장 규칙을 내장한다(spec FR-021). 목록의 느슨한 이어짐, HTML 블록 7종, 밑줄형 제목과 문단의 관계처럼 직접 구현하기 까다로운 경계를
  해석기가 맡는다. 순수 Python이고 의존성은 `mdurl` 하나다. 이미 `uv.lock`에 4.2.0이 있다(`rich` 경유). 청커는 색인 쪽에서만 쓰므로 Workers 질의
  번들에 들어가지 않는다(QK-FND-001 R-03, QK-STO-001 R-09의 `postgres` 선택 의존성과 같은 방식). 사용자 결정(2026-10-21).
- **Alternatives considered**: 표준 라이브러리로 블록 규칙을 직접 구현(의존성 0이지만 CommonMark 경계 사례를 맞추는 비용이 크기 S를 넘는다),
  `mistune`(줄 범위를 주지 않는다), `commonmark.py`(유지보수 중단).

## R-03 상한과 안전 여유: 예상 2,800토큰

- **측정 조건**: R-02와 같은 79개 문서. 실제 토큰은 `tokenizers` 0.23.3 + `BAAI/bge-m3` 토크나이저(리비전 `5617a9f61b028005a4858fdac845db406aefb181`,
  `tokenizer.json` SHA-256 `21106b6d7dab2952c1d496fb21d5dc9db75c28ed361a05f5020bbba27810dd08`, 특수 토큰 포함 `encode().ids` 길이).
  비교 단위는 문서 전체와, 200바이트 이상인 최상위 블록(문단·목록·인용 등 일반 1,163개, 코드 255개, 표 145개). 분위수 계산과 재현 명령은 R-02 "재현"과 같다.
- **결과**: "실제 ÷ 예상" 비율

| 단위 | 표본 | 중앙값 | p95 | 최대 | 실제 1토큰당 바이트 최소 |
| --- | --- | --- | --- | --- | --- |
| 문서 | 79 | 0.957 | 1.143 | 1.408 | 2.49 |
| 일반 블록 | 1,163 | 0.932 | 1.276 | 1.702 | 2.03 |
| 코드 블록 | 255 | 1.176 | 1.467 | 1.769 | 1.97 |
| 표 | 145 | 1.316 | 1.762 | 2.303 | 1.51 |

  가장 큰 문서의 실제 토큰은 22,098이었다.
- **Decision**: 상한(예상 토큰)은 2,800이다. 실제 1토큰당 바이트가 1.2까지 내려가도 2,800 × 3.5 ÷ 1.2 = 8,167 ≤ 8,192가 되도록 잡았다.
  관측 최솟값(1.51)에서는 실제 약 6,490토큰(한도의 79%)이다. 설정 검사로 `상한 × 3.5 ÷ 1.2 ≤ 모델 입력 한도`를 강제한다(data-model `ChunkingSettings`).
- **Rationale**: 바이트 ÷ 3.5 추정은 이 문서들에서 한국어 스파이크와 반대로 토큰을 적게 잡는다(표 최대 2.3배). 영문·기호·표 구분자가 많기 때문이다 `(추론)`.
  한도의 50%(4,096)로는 표 최댓값 비율에서 9,433토큰이 되어 넘을 수 있다. 상한을 2,800으로 두어도 R-02의 최상위 블록 중 3개만 줄 단위로 나뉜다.
  spec FR-013은 예상 토큰 기준 상한만 보장하고, 남는 위험은 QK-EMB-001이 "입력 한도 초과"로 알린다.
- **Alternatives considered**: 실제 토크나이저를 청커에 넣기(토크나이저 파일과 `tokenizers` 네이티브 의존성이 색인에 필요해지고 QK-EMB-001 예상과
  기준이 갈린다), 상한 4,096(표에서 넘을 수 있다), 표·코드에 다른 환산 계수(규칙이 늘고 관측 최대만으로 계수를 정하기 어렵다).
- **남는 위험**: 1.2바이트/토큰보다 촘촘한 텍스트(긴 한자·기호 나열 등)는 상한 안에서도 실제 한도를 넘을 수 있다. QK-SYN-001 첫 색인에서
  "입력 한도 초과" 건수를 보고 다시 판단한다.

## R-04 목표 크기: 예상 512토큰 (연성 목표)

- **Decision**: 목표 크기는 예상 512토큰이다(spec FR-014). 검색 평가(QK-EVL-001)로 조정한다.
- **Rationale**: R-02에서 절 중앙값이 173, p90이 580이라 512면 절 127개(12%)만 나뉘고 나머지는 절 그대로 한 청크다. 이 문서들의 실제 토큰은
  예상과 비슷하거나(중앙값 0.93~0.96) 조금 많아, 청크 대부분이 실제 수백 토큰이 된다. QK-RET-001의 문맥 토큰 예산과 상위 5개 검색(로드맵 1.G
  Recall@5)을 생각하면 1,024보다 작은 쪽이 출처를 좁히기 쉽다 `(추론)`.
- **Alternatives considered**: 1,024(나뉘는 절 45개로 적지만 문맥 예산에서 청크 하나가 차지하는 몫이 커진다), 256(절 341개가 나뉘어 표·목록 사이가
  자주 끊긴다).

## R-05 블록과 절 만들기

- **Decision**:
  1. 줄 바꿈을 LF로, BOM을 뺀다(spec FR-007). 앞머리 메타데이터(R-06)를 찾아 그 줄을 빈 줄로 바꾼 사본을 해석기에 넘긴다. 이 사본은 LF로 끝나지 않으면 LF 하나를 붙인다
     (R-11 펜스 판정 조건). 원문 줄 수와 줄 번호는 그대로다.
  2. 해석 결과에서 `level == 0`이고 `map`이 있는 여는 토큰·단독 토큰만 최상위 블록으로 쓴다(제목, 문단, 목록, 인용, 표, 코드 펜스, 들여쓴 코드,
     HTML 블록, 구분선). 인용·목록 안의 제목은 `level > 0`이라 제목이 아니다(spec FR-021).
     블록은 나무 구조로 기억한다. 목록의 자식은 목록 항목, 목록 항목과 인용의 자식은 그 안의 바로 아래 블록(문단, 하위 목록, 표, 코드 펜스 등)이다.
     토큰의 여닫음 짝으로 부모를 정하므로 절대 수준에 기대지 않는다(하위 목록 항목은 `level == 3`이다). 상한을 넘는 블록을 나눌 때 이 자식 경계를
     재귀적으로 쓴다(R-08).
  5. 부모 범위 안에서 자식 범위에 들지 않는 줄(인용 문단 사이의 `>` 줄, 목록 항목 사이 빈 줄 등)은 바로 다음 자식에 붙이고, 마지막 자식 뒤에 남은 줄은
     마지막 자식에 붙인다. 그래서 자식 단위들이 부모 범위를 빈틈없이 덮고, 크기도 붙은 줄까지 포함해 잰다.
  3. 어느 블록에도 들지 않은 공백 아닌 줄(링크 참조 정의처럼 해석기가 토큰을 만들지 않는 줄)은 "원문 블록"으로 메운다. 그래야 모든 공백 아닌 줄이
     청크에 들어간다(spec FR-009). 앞머리 메타데이터도 원문 블록이다.
  4. 최상위 제목 토큰마다 절을 나눈다. 첫 제목 앞의 블록은 머리 절이다(spec FR-011).
- **Rationale**: 해석기는 줄 범위만 주고, 경계·크기 판단은 우리 규칙으로 한다. 원문은 해석 결과가 아니라 줄 범위로 잘라 쓰므로 본문이 원문 그대로다(FR-008).
- **Alternatives considered**: 해석기 렌더링 결과를 본문으로 쓰기(원문과 달라져 C-07 위반).

## R-06 앞머리 메타데이터와 문서 제목

- **Decision**: 1번 줄이 정확히 `---`이고 그 뒤에 `---` 또는 `...`만 있는 줄이 있으면 그 사이가 앞머리 메타데이터다. 제목 값은 `title:` 로 시작하는 줄의
  값(앞뒤 따옴표 제거)만 읽는다. YAML 해석기는 쓰지 않는다. 문서 제목 순서는 spec FR-017이다.
- **Rationale**: CommonMark로 읽으면 1번 줄 `---`는 구분선, 닫는 `---`는 바로 앞 줄을 밑줄형 제목으로 만든다(spec US4 시나리오 6이 막으려는 경우).
  R-02에서 앞머리 메타데이터가 있는 문서는 9개이고, 필요한 값은 제목 하나라 YAML 의존성을 들일 이유가 없다.
- **Alternatives considered**: `mdit-py-plugins`의 front_matter(의존성 하나 추가), PyYAML(제목 하나 때문에 의존성 추가).

## R-07 청킹 규칙 버전: `chk-md-<12자리 해시>`

- **Decision**: 값은 `"chk-md-" + sha256(직렬화한 재료).hexdigest()[:12]`다. 직렬화는
  `json.dumps(재료, sort_keys=True, ensure_ascii=False, separators=(",", ":"))`를 UTF-8로 인코딩한 바이트다. 재료 객체는 다음과 같다.

  ```json
  {"embedding_input_format":1,"header_format":1,
   "parser":{"enable":["table"],"name":"markdown-it-py","preset":"commonmark","version":"4.2.0"},
   "rules_revision":1,"search_text_format":1,
   "settings":{"limit_tokens":2800,"model_version":"@cf/baai/bge-m3","target_tokens":512,"worst_bytes_per_token":1.2}}
  ```

  판수 4개(`rules_revision`·`header_format`·`search_text_format`·`embedding_input_format`)는 모두 1에서 시작하는 정수이고, 해당 규칙 코드를 바꿀 때 사람이 올린다.
  해석기 `version`은 설치된 패키지 버전을 그대로 쓴다. 첫 값은 **`chk-md-20d966f730bb`**(2026-10-21 계산)이고 구현의 기대값 시험에 고정한다.
  구조 경고 판정은 재료에 넣지 않는다(spec FR-024).
- **Rationale**: 보안 규칙 버전(`sec-` + 12자리, `security/policy.py`의 `_version`)과 같은 형식이다. 설정이 바뀌면 자동으로 바뀌고(spec SC-009),
  규칙 코드 변경은 판수로 드러낸다. 판수를 올리지 않고 규칙 코드를 바꾸면 기대값 시험(spec SC-001)이 깨져 알 수 있다.
- **Alternatives considered**: 사람이 붙이는 이름만(`md-v1`. 설정 변경을 놓친다), 코드 파일 해시(공백·주석 수정에도 바뀌어 불필요한 재색인).

## R-08 나누기·합치기

- **Decision**: 절마다 독립으로 처리한다(spec FR-011).
  1. 크기는 항상 `예상토큰(임베딩 입력 텍스트)`로 잰다. 즉 검색 헤더 + (반복 머리글) + 후보 본문이다(spec FR-015).
  2. 검색 헤더만으로 상한 이상이면 문서 전체가 `HEADER_TOO_LONG` 실패다.
  3. 블록을 순서대로 쌓는다. 다음 블록을 더하면 목표를 넘고 쌓인 것이 있으면 거기서 끊는다. 블록 하나가 목표를 넘어도 상한 이하면 그 블록만으로 청크다
     (spec FR-014·016, US2 시나리오 6).
  4. 블록 하나가 상한을 넘으면 나누기(`split(블록)`)를 한다. 자식이 있으면 자식 단위(R-05 5번의 덮기 규칙을 적용한 범위)를 3과 같은 규칙으로 쌓는다.
     상한 이하인 자식 단위는 나누지 않는다(spec FR-016). 상한을 넘는 자식 단위는 같은 `split`을 재귀로 적용한다. 자식이 없는 블록(문단, 표, 코드 펜스,
     들여쓴 코드, HTML 블록, 원문 블록)만 줄을 순서대로 쌓아 상한 안에서 끊는다. 표는 머리글 행 + 구분 행 두 줄을, 코드 펜스는 여는 펜스 줄을 뒤 조각의
     반복 머리글로 쓴다(원문 줄 그대로, 인용·목록 접두사 포함). 줄 하나에 헤더와 필요한 반복 머리글을 붙여 상한을 넘으면 문서 전체가 `LINE_TOO_LONG` 실패다.
     `split`이 한 번이라도 일어난 최상위 블록마다 `split_blocks`를 1 센다.
  5. 청크 본문은 첫 블록 시작 줄부터 마지막 블록 끝 줄까지의 원문이고, 블록 사이 빈 줄은 본문 안에 그대로 남는다. 청크 앞뒤의 공백뿐인 줄은
     본문과 `locator`의 줄 범위에서 함께 뺀다(spec FR-008).
- **Rationale**: 탐욕적 쌓기는 결정적이고 절 밖에 영향을 주지 않는다(SC-001·004). 목표를 넘는 블록을 깨지 않으므로 표·코드가 갈리지 않는다(SC-005).
- **Alternatives considered**: 절 전체를 균등 분할(블록 경계를 무시하게 된다), 동적 계획으로 크기 편차 최소화(결과 설명이 어렵고 S 범위를 넘는다).

## R-09 검색 헤더·키워드 검색용 텍스트·임베딩 입력 텍스트 형식

- **Decision**:
  - 검색 헤더는 두 줄이다. 1줄은 원본 위치, 2줄은 `문서 제목 > 제목1 > 제목2`(제목 경로 첫 항목이 문서 제목과 같으면 한 번만, 제목 경로가 비면 문서 제목만).
  - 키워드 검색용 텍스트 = 검색 헤더 + 빈 줄 + 본문(spec FR-020).
  - 임베딩 입력 텍스트 = 검색 헤더 + 빈 줄 + (반복 머리글 + 줄 바꿈) + 본문(spec FR-019).
  - 제목 글자는 제목 토큰 안쪽 inline 자식의 `text`·`code_inline` 내용과 이미지 대체 글자를 이어 붙이고(`softbreak`·`hardbreak`는 공백 하나),
    연속 공백을 하나로 줄여 앞뒤를 정리한 값이다(spec FR-018). 여러 줄 밑줄형 제목(`first` / `second` / `---`)은 `first second`가 된다.
- **Rationale**: 꼬리표(`경로:` 등)를 붙이지 않아 검색어와 상관없는 같은 글자가 모든 청크에 들어가지 않는다. 위치 줄이 있어 파일 이름(`ADR-007`)으로도 찾힌다.
- **Alternatives considered**: 한 줄 헤더(위치와 제목 구분이 흐려진다), 꼬리표 붙이기(모든 청크에 같은 낱말이 들어가 키워드 점수가 흐려진다).

## R-10 모듈 경계와 결과 전달

- **Decision**: 규칙 타입은 `domain/chunking.py`(표준 라이브러리만), 해석기 호출은 `chunking/blocks.py`, 나머지 규칙은 `chunking/` 아래에 둔다.
  공개 진입점은 `chunking/service.py`의 `chunk_markdown`(자료 하나)과 `chunk_screened`(필터 통과 자료 묶음 + 요약)다. 결과는 QK-STO-001 `ChunkInput`을
  감싼 `ChunkDraft`(검색 헤더, 임베딩 입력 텍스트 포함)다. 저장 스키마와 `ChunkInput`은 바꾸지 않는다(spec FR-019).
  `tests/unit/test_boundaries.py`에 "`domain`·`ports`·`embedding`·`query`는 `chunking`과 `markdown_it`를 가져오지 않는다"를 더한다.
- **Rationale**: QK-EMB-001(`embedding/` + `domain/embedding.py`)과 같은 나눔이다. QK-SYN-001은 `ChunkDraft.chunk`를 저장하고 `embedding_text`를 임베딩에 넘긴다.
- **Alternatives considered**: `ChunkInput`에 필드 추가(QK-STO-001 코드 변경으로 이 작업의 제외 범위).

## R-11 구조 경고 판정

- **Decision**:
  - 표 토큰(어느 수준이든)의 줄 범위 안 각 줄에서 컨테이너 표지를 뗀다. 표를 둘러싼 컨테이너(인용, 목록 항목) 수를 N이라 할 때, 줄 앞에서
    `^[ \t]*(?:>[ \t]?|(?:[-+*]|\d{1,9}[.)])[ \t]+)` 표지를 있는 만큼 최대 N번 지우고(이어지는 줄에는 표지가 없다) 앞뒤 공백을 지운다.
    그다음 이스케이프되지 않은 `|`로 나눠(앞뒤 `|` 제외) 셀 수를 세고, 머리글 행과 다르면 `TABLE_CELL_MISMATCH`(원문 줄 번호).
    해석기가 표 행으로 받아들인 파이프 없는 줄은 셀 1개로 센다. 2026-10-21에 6사례로 확인했다(최상위, 인용 안·바깥 파이프 없는 행, 목록 첫 줄,
    목록 안 인용, 순서 목록 첫 줄은 경고 없음, 파이프 없는 행은 경고).
  - 코드 펜스 토큰(어느 수준이든) `map = [s, e]`에서 내용의 LF 개수(`content.count("\n")`)가 `e - s - 2`이면 닫힌 것이고, 아니면
    `UNCLOSED_FENCE`(여는 줄 번호)다. 해석기에 넘기는 입력은 LF로 끝난다(R-05 1번). `splitlines()`는 U+2028·수직 탭도 줄로 세므로 쓰지 않는다.
    해석기가 이미 컨테이너 접두사와 닫는 펜스 문법을 판정했으므로 원문 줄을 다시 보지 않는다.
    2026-10-21에 16개 사례로 확인했다. 닫힘: 일반, 빈 내용, 빈 줄 내용, 인용 안, 목록 안, 마지막 줄 바꿈 없음, 내용에 U+2028, 내용에 수직 탭.
    열림: 여는 줄만, 내용만, 내용만이고 마지막 줄 바꿈 없음, 뒤 빈 줄, 네 칸 들여쓴 닫는 펜스 모양, 코드 안 `> ```` 줄, 인용이 끝나 펜스가 끝난 경우.
- **Rationale**: 해석기는 셀 수가 다른 행을 조용히 채우거나 자르고(파이프 없는 `onecell` 줄도 표 행이 되어 두 번째 칸이 빈 값으로 채워졌다), 펜스가 닫혔는지
  토큰에 남기지 않는다(여는 펜스 한 줄 → `map = [0, 1]`, 인용 안 펜스 → 인용이 끝나는 줄에서 끝남). 그래서 표는 원문 줄로, 펜스는 줄 범위와
  내용 줄 수의 차이로 판정한다. 2026-10-21 Codex plan 검토에서
  `markdown-it-py` 4.2.0으로 확인했다. 셀 안 줄바꿈 뒤 줄이 표 행이 아니라 문단으로 읽히는 경우는 경고 대상이 아니다(spec Assumptions의 한계).

## R-12 실측 경로와 성능 시험

- **Decision**:
  - 실제 대상 확인은 기존 `qk-dev source measure`에 `--chunk`를 더해, 보안 필터 통과 자료를 청킹하고 요약·소요 시간·실패·경고(위치는 QK-SEC-001
    기록 출력 규칙 `safe_text`)만 출력한다. 원본 호출은 지금 측정과 같다(GitHub 약 83회, 0 Neurons).
  - **SC-011 완료 판정(고정 입력)**: 대상 저장소 로컬 사본의 커밋 `6aeccd039b825dcd7a2b6c046a34ef72089a1f78`, 이 브랜치의 `config/sources.toml`
    포함·제외 패턴, 보안 필터에 막힌 계획 문서 1개 제외로 고른 79개 문서(R-02와 같은 표본, 1,017,913바이트)를 쓴다.
    `measurement/measure_inputs.py --time-chunking`이 `chunk_markdown`을 문서마다 부르는 구간 전체를 `time.perf_counter`로 1회 재고, 문서 수·총 바이트·
    결과별 수·청크 수·소요 시간·장비(`platform.platform()`, Python 버전)를 출력한다. `files == 79`, `total_bytes == 1017913`, 결과가 모두 `CHUNKED`,
    `chunk_count > 0`이고 반올림하지 않은 소요 시간이 10초 이하이면 통과다. 기준 장비는 이 작업의 개발 환경(macOS arm64, Python 3.13)이다.
  - **회귀 시험(CI)**: 시드 `20261021`의 `random.Random`으로 합성 문서 79개를 만든다. 문서마다 절 13개(수준-1 하나 + 수준-2·3), 절마다 한국어·영문 섞인
    문단 2~4개, 표 1개(4열 × 6~12행), 코드 펜스 1개(10~40줄), 목록 1개(3~8항목)를 넣는다. 생성 함수는 시험 코드에 두고, 구현 때 계산한 입력 전체의
    SHA-256과 총 바이트를 시험에 고정해 입력이 바뀌면 시험이 알린다. `chunk_screened` 구간 1회가 10초 이하인지 `ubuntu-latest` 러너에서 확인한다.
    완료 판정이 아니라 성능 회귀 감시다.
  - **관찰값**: `qk-dev source measure --name dnd-backend-docs --chunk --json`(실행 시점 `main`)의 `chunking.elapsed_seconds`와 커밋은 측정 기록에 덧붙이는
    관찰값이다. 문서 수가 79와 다를 수 있다.
- **Rationale**: 대상 문서 원문을 저장소에 넣지 않으면서(AGENTS.md 6절) 같은 규모로 잴 수 있다. 실제 문서 확인은 사람이 실행하는 측정 명령으로 한다.
- **Alternatives considered**: 대상 문서를 시험 자료로 복사(원문을 저장소에 남긴다), 별도 CLI(`qk-dev chunk`. 수집·필터 경로를 다시 만들어야 한다).
