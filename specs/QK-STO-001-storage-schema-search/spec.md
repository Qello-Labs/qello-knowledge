# Feature Specification: QK-STO-001 저장 스키마·마이그레이션·검색 질의

**Feature Branch**: `docs/SCRUM-92-gh-24-phase1-first-specs`

**Created**: 2026-10-18

**Status**: Draft

**Input**: 로드맵 4절 명세 백로그 QK-STO-001 "저장 스키마·마이그레이션·검색 SQL". 선행은 QK-FND-001이다.
백로그 행의 요구사항 ID(FR-STO-01~03, ADR-006·007) 중 FR-STO-01~03과 ADR-006은 원문이 없어(Assumptions 참조)
2026-10-18 사용자 결정에 따라 백로그 제목, constitution, ADR-002·008, 로드맵 Phase 1, Confluence `설계` 페이지를 근거로 설계했다.
ADR-007은 로드맵 3절에 "자체 스키마 vs PGVectorStore"로 정의돼 있고, 이 명세의 스파이크에서 정한다.

## User Scenarios & Testing *(mandatory)*

이 명세의 사용자는 저장소 위에 기능을 쌓는 후속 명세 구현자(QK-EMB-001 임베딩, QK-SYN-001 동기화, QK-RET-001 검색,
QK-STO-002 인덱스 버전), 마이그레이션을 적용하는 운영 담당자, PR 리뷰어다. 최종 사용자(Discord에서 질문하는 팀원)는
이 명세의 결과를 직접 보지 않지만, 권한 미확인 자료가 답변에 나오지 않는다는 보장은 여기서 시작한다.

### User Story 1 - 모든 청크를 원본 위치로 되돌릴 수 있게 저장한다 (Priority: P1)

동기화 구현자가 원본 자료 하나와 그 자료의 청크·임베딩을 저장하면, 나중에 어떤 청크든 원본 링크, 원본 버전,
원본 안의 위치(경로·줄 범위·절 제목 경로 등)로 되돌아갈 수 있다. 청크마다 어떤 청킹 규칙과 어떤 임베딩 모델로
만들었는지도 남는다.

**Why this priority**: C-01(근거가 있는 것만 말한다)과 C-07(색인 재현 가능)의 바탕이다. 출처를 되짚을 수 없는 청크는
답변 근거로 쓸 수 없다. QK-GEN-001의 출처 표시도 이 정보에 기댄다.

**Independent Test**: 샘플 원본 자료 몇 개를 저장한 뒤, 임의로 고른 청크마다 원본 링크·버전·위치·청킹 규칙 버전·
임베딩 모델 버전을 조회한다. 하나라도 비어 있으면 실패다.

**Acceptance Scenarios**:

1. **Given** 원본 자료 1개와 청크 5개를 저장한 상태, **When** 청크 하나를 조회한다, **Then** 원본 링크, 원본 버전,
   원본 안 위치, 청킹 규칙 버전, 임베딩 모델 버전, 인덱스 버전이 함께 나온다.
2. **Given** 필수 출처 정보(원본 링크나 원본 버전)가 빠진 청크, **When** 저장을 시도한다, **Then** 저장이 거부된다.
3. **Given** 임베딩 차원이 활성 모델 차원(ADR-002: 1,024)과 다른 벡터, **When** 저장을 시도한다, **Then** 저장이 거부된다.

### User Story 2 - 권한·상태·버전 조건을 지킨 벡터 검색과 키워드 검색 질의를 제공한다 (Priority: P1)

검색 구현자(QK-RET-001)가 질의 벡터 또는 키워드를 넘기면, 저장소는 조건을 만족하는 청크 중 상위 N개를 순위와 함께
돌려준다. 벡터 검색과 키워드 검색은 각각 따로 부를 수 있고, 같은 조건(활성 인덱스 버전, 팀 공용으로 확인된 접근 범위,
활성 상태 자료, 선택적 자료원·자료 종류 필터)을 질의 안에서 적용한다. 두 결과를 합치는 순위 통합(RRF)은 QK-RET-001 몫이다.

**Why this priority**: 1.G 완료 조건 "접근 범위를 확인할 수 없는 샘플 문서가 검색되지 않는다"와 C-14를 저장소 질의 단계에서
보장해야 한다. 검색 뒤에 거르면 상위 N개가 모자라거나 실수로 노출될 수 있다. 하이브리드 검색(QK-RET-001)은 이 두 질의 없이는
시작할 수 없다.

**Independent Test**: 접근 범위가 팀 공용·미확인·제한인 청크, 활성·삭제 상태 청크, 활성·비활성 인덱스 버전 청크를 섞어 넣고
두 검색 질의를 실행한다. 결과에는 팀 공용·활성 상태·활성 버전 청크만 나와야 한다.

**Acceptance Scenarios**:

1. **Given** 질의와 가까운 청크가 접근 범위 "미확인"으로만 저장된 상태, **When** 벡터 검색을 실행한다, **Then** 그 청크는
   결과에 없다.
2. **Given** 삭제 상태로 바뀐 원본 자료의 청크, **When** 벡터 검색이나 키워드 검색을 실행한다, **Then** 결과에 없다.
3. **Given** 비활성 인덱스 버전에만 있는 청크, **When** 검색을 실행한다, **Then** 결과에 없다.
4. **Given** 함수명 `retryPayment`, 경로 `/payments/{id}/cancel`, `snake_case` 식별자가 본문에 그대로 있는 청크,
   **When** 그 식별자를 원형 그대로 키워드 검색한다, **Then** 해당 청크가 결과에 나온다.
5. **Given** 한국어 본문 청크, **When** 본문에 있는 한국어 단어로 키워드 검색을 실행한다, **Then** 해당 청크가 결과에 나온다.
6. **Given** 자료원 필터(예: 저장소 문서만)를 준 상태, **When** 검색을 실행한다, **Then** 다른 자료원 청크는 결과에 없다.
7. **Given** 같은 조건, **When** 검색 결과를 받는다, **Then** 결과마다 순위와 점수, 청크 식별자, 출처 정보가 함께 온다.

### User Story 3 - 스키마 변경을 버전 순서대로, 다시 실행해도 안전하게 적용한다 (Priority: P1)

운영 담당자와 개발자는 같은 마이그레이션 묶음을 로컬 데이터베이스(QK-FND-001)와 운영 저장소에 적용해 같은 스키마를 얻는다.
이미 적용한 마이그레이션은 다시 실행해도 아무것도 바꾸지 않는다. 실패한 마이그레이션은 부분 반영을 남기지 않는다.

**Why this priority**: AGENTS.md 4절(재실행 안전, 부분 반영 금지, 공유 DB 초기화 금지)을 저장소 변경에서 지키는 방법이다.
로컬과 운영 스키마가 다르면 로컬 테스트를 믿을 수 없다.

**Independent Test**: 빈 로컬 데이터베이스에 전체 마이그레이션을 두 번 적용하고, 두 번째 적용에서 변경이 0건인지 본다.
중간에 실패하도록 만든 마이그레이션을 적용해 이전 상태가 그대로인지 본다.

**Acceptance Scenarios**:

1. **Given** 빈 데이터베이스, **When** 전체 마이그레이션을 적용한다, **Then** 정해진 스키마와 적용 기록(버전, 적용 시각, 결과)이 남는다.
2. **Given** 모두 적용된 데이터베이스, **When** 같은 마이그레이션을 다시 적용한다, **Then** 변경 0건으로 끝난다.
3. **Given** 중간에 실패하는 마이그레이션, **When** 적용한다, **Then** 그 마이그레이션의 변경이 하나도 남지 않고 실패가 기록된다.
4. **Given** 테이블 삭제나 데이터 삭제를 포함한 마이그레이션, **When** 운영 저장소에 적용하려 한다, **Then** 사람 확인 없이는
   적용되지 않는다(AGENTS.md 4절).

### User Story 4 - 문서 하나의 청크를 한 번에 교체한다 (Priority: P2)

동기화 구현자(QK-SYN-001)가 원본 자료 하나의 새 청크 묶음을 준비해 교체를 요청하면, 저장소는 이전 청크 묶음을 새 묶음으로
한 번에 바꾼다. 교체 도중에는 검색에 이전 묶음만 보이고, 교체가 실패하면 이전 묶음이 그대로 남는다.

**Why this priority**: C-08(멱등, 실패 격리)과 1.G 완료 조건 "문서 1개를 고치면 그 문서의 청크만 교체된다"의 저장소 쪽 기반이다.
교체 절차 자체(언제 무엇을 바꿀지)는 QK-SYN-001 몫이라 P2로 둔다.

**Independent Test**: 청크 5개인 문서를 청크 3개로 교체하면서 중간에 실패를 넣는다. 실패 뒤 검색에 원래 5개만 보이는지,
실패 없이 다시 실행하면 3개만 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 문서 A의 청크 5개가 저장된 상태, **When** 새 청크 3개로 교체한다, **Then** 검색에는 새 청크 3개만 보이고 다른 문서의
   청크는 바뀌지 않는다.
2. **Given** 교체 도중 실패, **When** 검색한다, **Then** 이전 청크 5개만 보이고 새 청크는 하나도 보이지 않는다.
3. **Given** 같은 교체 요청(같은 원본 버전·같은 청크 묶음), **When** 두 번 실행한다, **Then** 결과가 한 번 실행한 것과 같다.
4. **Given** 같은 문서에 대한 교체 요청 두 개가 동시에 들어온 상태, **When** 둘 다 실행된다, **Then** 둘 중 하나의 결과만 남고
   두 묶음이 섞인 상태는 생기지 않는다.

### User Story 5 - 같은 임베딩 입력의 벡터를 다시 쓴다 (Priority: P2)

임베딩 구현자(QK-EMB-001)가 임베딩 입력의 해시와 모델 버전으로 저장소를 조회하면, 이미 만든 벡터가 있을 때 그 벡터를 돌려받는다.

**Why this priority**: 1.G 완료 조건 "변경이 없는 재동기화에서 임베딩 호출이 0건이다"와 C-05(비용 상한)를 위한 저장소 쪽 기반이다.
캐시 정책(언제 쓰고 언제 지울지)은 QK-EMB-001 몫이다.

**Independent Test**: 같은 입력 해시·같은 모델 버전으로 벡터를 한 번 저장한 뒤 조회해 같은 벡터가 나오는지, 모델 버전만 다르게 조회하면
없다고 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 입력 해시 H, 모델 버전 M의 벡터가 저장된 상태, **When** (H, M)으로 조회한다, **Then** 저장된 벡터가 나온다.
2. **Given** 같은 상태, **When** (H, 다른 모델 버전)으로 조회한다, **Then** 없음이 나온다.

### User Story 6 - 운영 저장소를 쓰기 전에 데이터 처리 정책과 한국어 검색 기능을 확인한다 (Priority: P3)

운영 담당자는 운영 저장소(ADR-008: Supabase 무료 플랜)에 실제 팀 자료를 넣기 전에, 제공자의 데이터 처리 정책(학습 사용 여부,
보존 기간)과 한국어 키워드 검색 확장 기능(PGroonga)이 실제로 켜지는지 확인하고 결과를 결정 기록에 남긴다.

**Why this priority**: ADR-008 Follow-ups가 이 두 확인을 이 명세에 넘겼다. AGENTS.md 3.1은 새 외부 서비스의 데이터 처리 정책 확인을
요구한다. 로컬 개발(US1~5)은 이 확인 없이 진행할 수 있어 P3로 둔다. 다만 첫 실제 색인(QK-SYN-001) 전에는 끝나야 한다.

**Independent Test**: 결정 기록에 정책 확인 결과(출처 URL, 조회일)와 확장 기능 활성화 결과(확인 일자, 확인 방법)가 있는지 본다.

**Acceptance Scenarios**:

1. **Given** 운영 저장소에 팀 자료가 아직 없는 상태, **When** 정책을 확인한다, **Then** 학습 사용 여부와 보존 기간이 출처 URL·조회일과
   함께 결정 기록에 남는다.
2. **Given** 운영 저장소 프로젝트, **When** 한국어 키워드 검색 확장 기능을 켜 본다, **Then** 성공 여부가 기록되고, 실패하면 ADR-008
   Revisit conditions에 따라 대안 비교로 넘어간다.
3. **Given** 두 확인 중 하나라도 끝나지 않은 상태, **When** 운영 저장소에 실제 팀 자료를 넣으려 한다, **Then** 넣지 않는다.

### Edge Cases

- 접근 범위 값이 비어 있는 청크: "미확인"으로 취급해 검색에서 뺀다. 저장은 허용하되 노출하지 않는다(QK-SEC-001이 값 체계를 정한다).
- 원본 자료가 삭제됐을 때: 자료 상태를 삭제로 바꾸면 그 자료의 청크가 모든 검색에서 즉시 빠진다. 물리 삭제 시점은 QK-SYN-003 몫이다.
- 활성 인덱스 버전이 하나도 없을 때: 검색은 빈 결과와 "활성 인덱스 없음" 상태를 함께 돌려준다. 오류 없이 빈 목록만 주지 않는다.
- 활성 인덱스 버전이 둘 이상이 되려 할 때: 허용하지 않는다. 활성 버전은 언제나 하나 이하다.
- 키워드 검색어가 비었거나 공백뿐일 때: 질의를 실행하지 않고 빈 결과를 돌려준다.
- 키워드 검색어에 검색 문법 특수 문자(따옴표, 괄호, 연산자)가 들어 있을 때: 문법 오류 없이 글자 그대로 검색한다.
- 요청한 상위 N이 지나치게 클 때: 정해진 상한으로 자른다.
- 같은 청크 내용이 다른 문서에 있을 때: 각자 별도 청크로 저장하고 출처를 섞지 않는다. 벡터만 공유할 수 있다(US5).
- 운영 저장소가 비활성 기간 뒤 일시정지된 상태(ADR-008 위험)에서 질의할 때: 저장소 쪽 오류를 "저장소 사용 불가"로 구분해 돌려준다.
  호출한 쪽(QK-BOT-001)이 사용자 안내를 정한다.
- 저장 용량이 무료 한도에 가까워질 때: 사용량을 조회할 수 있어야 한다(SC-006 확인용). 알림은 QK-OBS-002 몫이다.

## Requirements *(mandatory)*

### Functional Requirements

**저장 구조 (US1, US5)**

- **FR-001**: 원본 자료(문서·파일 하나)마다 자료원 종류, 원본 식별자, 원본 링크, 원본 버전, 원본 수정 시각, 수집 시각, 내용 해시,
  자료 종류, 제목, 접근 범위, 자료 상태(활성·보관·삭제)를 저장한다. 같은 자료원 안에서 원본 식별자는 중복되지 않는다.
- **FR-002**: 청크마다 소속 원본 자료, 원본 버전, 원본 안 위치(경로·줄 범위·블록 ID 등), 제목 경로, 같은 자료 안 순서, 청크 본문,
  키워드 검색용 텍스트, 청킹 규칙 버전, 인덱스 버전을 저장한다. 키워드 검색용 텍스트는 본문과 별도로 둘 수 있어, ADR-010 후보를
  스키마 변경 없이 비교할 수 있다.
- **FR-003**: 임베딩은 임베딩 입력 해시, 모델 버전, 차원, 벡터로 저장하고 청크와 연결한다. 같은 (입력 해시, 모델 버전)의 벡터는
  하나만 두고 여러 청크가 함께 쓴다.
- **FR-004**: 출처 정보(원본 링크, 원본 버전, 원본 안 위치)가 빠진 청크와 차원이 맞지 않는 벡터는 저장을 거부한다.
- **FR-005**: 인덱스 버전마다 임베딩 모델 버전, 차원, 청킹 규칙 버전, 메타데이터 스키마 버전, 상태(준비·활성·보관)를 저장한다.
  활성 상태는 동시에 하나 이하다(C-07, AGENTS.md 3.3). 활성화 절차와 평가 게이트는 QK-STO-002 몫이다.

**검색 질의 (US2)**

- **FR-006**: 질의 벡터와 상위 N을 받아 거리 순으로 청크를 돌려주는 벡터 검색 질의를 제공한다.
- **FR-007**: 검색어와 상위 N을 받아 관련도 순으로 청크를 돌려주는 키워드 검색 질의를 제공한다. 한국어 단어와 코드 식별자
  (camelCase, snake_case, URL 경로)를 원형 그대로 찾을 수 있어야 한다.
- **FR-008**: 두 질의는 활성 인덱스 버전, 팀 공용으로 확인된 접근 범위, 활성 상태 자료만 대상으로 한다. 이 조건은 질의 안에서
  적용하며, 결과를 받은 뒤 거르는 방식으로 대신하지 않는다(C-14). 자료원 종류와 자료 종류 필터를 선택적으로 받는다.
- **FR-009**: 검색 결과 한 건은 청크 식별자, 순위, 점수, 청크 본문, 출처 정보(원본 링크·버전·위치·제목 경로·원본 수정 시각·수집 시각)를
  담는다. 수집 시각은 C-02(현재 상태 질문에 수집 시각 표시)에 쓴다.
- **FR-010**: 상위 N은 정해진 상한(기본 50)을 넘지 않는다. 검색어 특수 문자는 글자 그대로 처리한다.
- **FR-011**: 청크 식별자로 같은 원본 자료 안의 앞뒤 청크와 상위 절을 조회하는 질의를 제공한다. 문맥 확장(QK-RET-001)에 쓴다.

**쓰기 연산 (US4)**

- **FR-012**: 원본 자료 하나의 청크 묶음을 새 묶음으로 바꾸는 교체 연산을 제공한다. 교체는 전부 반영되거나 전혀 반영되지 않고,
  도중에는 검색에 이전 묶음만 보인다. 같은 요청을 다시 실행해도 결과가 같다(C-08).
- **FR-013**: 같은 원본 자료에 대한 교체가 동시에 실행돼도 두 묶음이 섞이지 않는다.
- **FR-014**: 원본 자료의 상태를 삭제로 바꾸는 연산을 제공하고, 상태가 바뀐 즉시 그 자료의 청크가 모든 검색에서 빠진다.
- **FR-015**: 저장소 접근은 QK-FND-001의 저장소 경계(인터페이스) 뒤에 둔다. 검색·쓰기 연산의 입력과 출력에 저장소 제품 고유 타입이
  나오지 않는다(C-06).

**마이그레이션 (US3)**

- **FR-016**: 스키마는 버전이 붙은 마이그레이션 묶음으로만 바꾼다. 마이그레이션마다 버전, 설명, 내용 체크섬을 갖고, 적용 기록(버전, 적용 시각,
  결과)을 저장소 안에 남긴다.
- **FR-017**: 이미 적용한 마이그레이션은 다시 적용해도 변경이 없다. 적용한 마이그레이션의 내용이 바뀌었으면(체크섬 불일치) 적용을 멈추고 보고한다.
- **FR-018**: 마이그레이션 하나는 전부 반영되거나 전혀 반영되지 않는다.
- **FR-019**: 테이블·컬럼·데이터를 지우는 마이그레이션은 표시를 붙이고, 운영 저장소에는 사람 확인 뒤에만 적용한다(AGENTS.md 4절).
- **FR-020**: 같은 마이그레이션 묶음을 로컬 데이터베이스와 운영 저장소에 적용하면 같은 스키마가 된다. CI(QK-FND-001)는 빈 로컬 데이터베이스에
  전체 마이그레이션을 적용하는 검사를 포함한다.

**결정과 운영 저장소 확인 (US6)**

- **FR-021**: ADR-007(자체 스키마 vs PGVectorStore)을 스파이크로 비교해 `templates/decision-record.md` 양식으로 남긴다. 비교 기준은
  FR-002(별도 키워드 텍스트), FR-005(인덱스 버전), FR-008(질의 안 필터), FR-012(문서 단위 교체), FR-016(마이그레이션 통제)을 만족하는지다.
  이 결정은 계획(`/speckit-plan`) 확정 전에 끝낸다.
- **FR-022**: 운영 저장소에 실제 팀 자료를 넣기 전에 제공자의 데이터 처리 정책(학습 사용 여부, 보존 기간)과 한국어 키워드 검색 확장 기능
  활성화를 확인하고, 결과를 ADR-008 기록에 추가한다(ADR-008 Follow-ups, AGENTS.md 3.1).
- **FR-023**: 저장소 사용량(전체 크기, 청크 수, 벡터 수)을 조회할 수 있다.

### Key Entities

- **원본 자료(Artifact)**: 자료원의 문서·파일 하나. 자료원 종류, 원본 식별자, 원본 링크, 원본 버전, 수정 시각, 수집 시각, 내용 해시,
  자료 종류, 제목, 접근 범위, 상태를 가진다. 청크 여러 개를 가진다.
- **청크(Chunk)**: 검색 단위. 원본 자료, 원본 버전, 원본 안 위치, 제목 경로, 순서, 본문, 키워드 검색용 텍스트, 청킹 규칙 버전,
  인덱스 버전을 가진다. 임베딩 하나를 가리킨다.
- **임베딩(Embedding)**: 입력 해시, 모델 버전, 차원, 벡터. 같은 입력·모델이면 여러 청크가 공유한다.
- **인덱스 버전(Index Version)**: 모델·차원·청킹 규칙·메타데이터 스키마 조합과 상태. 활성은 하나 이하다.
- **마이그레이션 기록**: 버전, 설명, 체크섬, 적용 시각, 결과.
- **검색 결과**: 청크 식별자, 순위, 점수, 본문, 출처 정보.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 샘플 데이터에서 무작위로 고른 청크 100%가 원본 링크·버전·위치·청킹 규칙 버전·임베딩 모델 버전으로 추적된다.
- **SC-002**: 접근 범위 미확인·제한, 삭제 상태, 비활성 인덱스 버전 청크를 섞은 검증 세트에서 검색 결과에 그런 청크가 나온 사례가 0건이다.
- **SC-003**: 교체 도중 실패를 넣은 시험 전부에서 검색 결과가 교체 전과 같다(새 청크 노출 0건).
- **SC-004**: 빈 데이터베이스에 전체 마이그레이션을 두 번 적용했을 때 두 번째 적용의 변경이 0건이고, 로컬과 운영의 스키마 비교 차이가 0건이다.
- **SC-005**: Phase 1 대상 규모(원문 약 1.1 MB, inventory.md 1.2절)의 샘플에서 벡터 검색과 키워드 검색 상위 20건 질의가 각각
  p95 1초 안에 끝난다. 측정 조건(데이터 규모, 반복 횟수, 실행 환경)을 함께 기록한다(C-13).
- **SC-006**: Phase 2 예상 규모(원문 약 10 MB, ADR-008)를 넣었을 때 저장 사용량이 운영 저장소 무료 한도(500 MB)의 50% 이하로 추정된다.
- **SC-007**: 식별자 원형 검색 시험(함수명, URL 경로, snake_case 각 5개 이상)에서 해당 청크가 상위 20건 안에 나온 비율이 100%다.
- **SC-008**: 운영 저장소에 실제 팀 자료를 넣기 전에 데이터 처리 정책과 한국어 검색 확장 기능 확인 결과가 결정 기록에 있다.

## Assumptions

**요구사항 원문 부재**

- FR-STO-01~03과 ADR-006은 저장소(git 이력 포함), Confluence `SCRUM` 스페이스, 로컬 파일 어디에도 원문이 없다(2026-10-18 확인).
  뜻을 추측해 대응시키지 않았다. 원문이 나오면 이 명세와 대조해 고친다.
- 백로그 제목 요소와 이 명세의 대응은 아래와 같다.

| 백로그 제목 요소 | 이 명세 | 근거 |
| --- | --- | --- |
| 저장 스키마 | FR-001~005, FR-012~015, US1·US4·US5 | C-07, C-08, ADR-002(1,024차원), Confluence `설계` 메타데이터 표 |
| 마이그레이션 | FR-016~020, US3 | AGENTS.md 4절 |
| 검색 SQL | FR-006~011, US2 | C-14, 로드맵 1.G, Confluence `설계` Step04(벡터 20 + 키워드 20 → RRF) |
| ADR-007 | FR-021 | 로드맵 3절 Phase 1 진행 순서 1 |
| ADR-008 Follow-ups | FR-022, US6 | ADR-008 |

**범위**

- 순위 통합(RRF), 문맥 확장 범위, 토큰 예산, 키워드 검색 텍스트 생성 방식(ADR-010)은 QK-RET-001 범위다. 이 명세는 두 검색 질의와
  주변 청크 조회만 제공한다.
- 접근 범위 값 체계와 판정은 QK-SEC-001 범위다. 이 명세는 "팀 공용으로 확인됨"만 검색 대상으로 삼는 규칙을 둔다.
- 인덱스 버전 활성화 절차와 평가 게이트는 QK-STO-002 범위다. Phase 1에서는 첫 인덱스 버전 하나를 쓴다(QK-EMB-001).
- 임베딩 캐시 정책은 QK-EMB-001, 교체 시점 판단과 실행 기록은 QK-SYN-001, 물리 삭제·백업은 QK-SYN-003 범위다.
- 질의 로그·피드백 저장(ADR-016)은 QK-OBS-001 범위다. 이 명세의 스키마에 넣지 않는다.
- 코드 전용 메타데이터(심볼, 시그니처 등, Confluence `설계` 2절)는 Phase 2 QK-CHK-001에서 추가한다. 이 명세는 공통 메타데이터만 다룬다.

**환경**

- 운영 저장소는 Supabase 무료 플랜의 관리형 PostgreSQL(pgvector·PGroonga)이다(ADR-008). 로컬 데이터베이스는 QK-FND-001이 같은 기능으로
  제공한다.
- 접속 정보는 QK-FND-001 설정 로딩의 비밀 항목으로 다루고 문서·코드·로그에 남기지 않는다(AGENTS.md 6절).
- 상위 N 상한 50과 검색 지연 목표(p95 1초)는 초기값이다. QK-RET-001 평가 결과로 조정한다.
- 질의응답이 Workers에서 돌아 요청당 CPU 10 ms·subrequest 50개 제약을 받는다(ADR-008). 그래서 벡터·키워드 검색을 저장소 질의 한 번씩으로
  끝낼 수 있게 설계한다고 가정한다. 저장소 연결 방식은 계획 단계에서 정한다.
